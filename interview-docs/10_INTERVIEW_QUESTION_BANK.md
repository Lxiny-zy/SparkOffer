## 模块A：项目定位与自进化闭环

#### A1 ⭐ 用 30 秒介绍一下这个项目
**考察点**：能否一句话讲准项目定位，抓住"闭环"而不是罗列功能
**口播答案**：我做的是面向技术求职者的个性化 AI 面试训练系统。它跟市面上 AI 面试工具最大的不同是：不是"每次从零出题"，而是跨会话闭环——训练完由 LLM 逐题评估，更新长期画像和领域掌握度，洞察向量化入库，SM-2 排出复习计划；下一轮出题融合长期画像、领域掌握度、知识库 RAG 三层上下文针对性出题。系统能持续理解你的能力变化，越用越懂你。技术栈 FastAPI + LangGraph + LlamaIndex 后端，React 19 前端。
**追问链**：
- 追问：核心价值到底是什么 → 答法要点：解决"每次从零开始"——传统工具不知道你答过什么、哪些点反复错、什么难度合适；我的系统把训练结果沉淀成状态反哺下一轮。
- 追问：这段话里哪个词最重要 → 答法要点："闭环"。评估结果回流成画像/记忆/调度/下次出题，这才是价值所在。
**红线**：不要说成"多 Agent 系统"，不要吹"支撑大规模用户"——当前是单机完整产品原型。

#### A2 ⭐ 和 ChatGPT 套壳面试机器人有什么本质区别
**考察点**：讲清"有状态有记忆"对"无状态问答"的价值
**口播答案**：三个词：记忆、调度、可控。套壳是无状态的，不知道你是谁、弱在哪、进步没有；我把每次训练压缩成结构化画像 + 向量记忆——画像记录稳定薄弱点、掌握度、思维习惯，向量库支持按语义召回"你以前错过什么"。调度上有 SM-2 主动安排"三天前错的题今天该复习"。可控上出题要过语义重复、薄弱点覆盖、难度分布三个校验器，不合格局部重生成。本质区别：它是问答工具，我是训练系统。
**追问链**：
- 追问：为什么不把全部历史对话直接塞给模型 → 答法要点：成本和上下文线性膨胀、噪声大、新旧事实冲突；结构化画像可精确读取，向量记忆按需召回。
- 追问：记忆和聊天历史差在哪 → 答法要点：历史记录"说过什么"（审计用），记忆记录"对未来出题有价值的用户事实"（决策用）。

#### A3 ⭐ 把自进化闭环完整讲一遍
**考察点**：是否真的理解每环的输入输出，而不是背概念
**口播答案**：五个环节。①出题：装配三层上下文（画像/领域状态/知识库 RAG），按薄弱点拆多路检索、融合去重，按掌握度规划难度混合生成，过三项校验。②评估：作答后 LLM 并发逐题打分再出整体总结。③记忆：双轨更新——分数、掌握度、SM-2 这些可计算的走确定性算法；薄弱点、思维模式这些要语义理解的走 Mem0 风格 ADD/UPDATE/IMPROVE/NOOP 合并进画像并向量化。④复习：SM-2 按表现排下次复习时间，连续 3 次高分的薄弱点自动毕业。⑤再出题：下一轮读取更新后的状态，环闭上了。
**追问链**：
- 追问：哪一环最容易被质疑"这不就是流水线" → 答法要点：双轨更新和三层上下文——题目内容和难度是被状态驱动动态决定的，不是固定 A→B。
- 追问：确定性和 LLM 的分界在哪 → 答法要点：能精确计算的绝不交给 LLM；只有语义判断（合并/抽取/总结）用 LLM。这是全项目的设计红线。

#### A4 三层上下文是哪三层，为什么分层
**考察点**：三层上下文构成与各自作用
**口播答案**：口诀"像域知"。第一层长期画像：跨会话跨领域——稳定弱点、思维模式、沟通风格。第二层当前领域状态：这个领域的掌握度、近期得分、领域薄弱点、到期的 SM-2 复习项。第三层知识库 RAG：按训练目标从 Qdrant 检索的知识片段。分层的意义：出题是"这个人是谁 + 他在这个领域什么水平 + 这个领域考什么"三者共同决定，才能做到针对性和难度自适应。
**追问链**：
- 追问：三层会不会撑爆上下文 → 答法要点：ContextBudget 按优先级 + 最小保留额分配 token，超预算尾部截断；详见模块 D。
- 追问："到期复习项"从哪来 → 答法要点：SM-2 调度，next_review ≤ 今天且未毕业的薄弱点，按 ease_factor 升序（最难的优先）。

#### A5 ⭐ 为什么说这是 Agent 项目，不是聊天机器人
**考察点**：Agent 判定标准，抗"你这不就是调 LLM"的质疑
**口播答案**：判定标准是有没有持久状态、条件决策、工具调用、环境反馈、跨轮执行——这几个都有。简历面试根据阶段和评估决定追问、切阶段还是结束；学习助手根据意图动态选 18 个工具；训练流水线根据画像和检索结果动态生成并校验。这些是系统在感知状态→决策→调工具→拿反馈再决策。但我也会诚实地说：不是每个调 LLM 的函数都叫 Agent——项目里真正自由选工具的只有浮动助手，其他是受控编排。
**追问链**：
- 追问：真正"自由选工具"的 Agent 是哪个 → 答法要点：FloatingAssistant，单 Agent + 18 工具 allowlist + 有限循环；简历面试是"外层确定性状态机 + 节点内 LLM 决策"。
- 追问：Agent 和 Workflow 边界 → 答法要点：Workflow 路径由程序预定义；Agent 下一步由模型根据观察决定。生产做法是外层 Workflow 保边界、局部 Agent 处理不确定性。

#### A6 ⭐ 三种编排为什么不统一成一种
**考察点**：架构决策判断力
**口播答案**：一句话：流程形状决定编排形式，本质是确定性程度不同。简历面试阶段明确、人在回路、要断点续接——有环状态流程，用 LangGraph 状态机。专项训练步骤稳定、要质量门控和进度可观测——单向流水线，普通 async pipeline，零状态机开销。学习助手面对开放意图——单 Agent + Function Calling。原则：确定性越强的部分越该程序控制，只把真正需要语义判断的局部交给模型——这样成本、延迟、权限、停止条件、失败恢复都可控。
**追问链**：
- 追问：是不是过度设计 → 答法要点：反了——全做成一个 ReAct 循环才是失控：循环、权限、成本、不可复现全来了。
- 追问：各举一个"换成另一种会怎样" → 答法要点：简历面试用自由 Agent→阶段顺序和题数失控；专项训练用状态机→质量门控和局部重生成不好表达；助手用状态机→开放意图没法枚举成节点。

#### A7 用了 LangGraph 就算 Agent 吗
**考察点**：区分"用了框架"和"具备 Agent 特征"
**口播答案**：不是。LangGraph 只是编排工具，图如果只是固定 A→B 本质还是 workflow。我的 Agent 特征来自条件路由、人在回路、状态恢复和节点内语义决策——路由函数同时看 LLM 评估信号和确定性题数上限决定 ask/advance/END。价值不在用了框架，在把阶段推进和人机交互建模成可持久化状态机。流程只有一次调用的话，用 LangGraph 反而是过度设计。
**追问链**：
- 追问：LangGraph 带来了什么 while 循环给不了的 → 答法要点：显式状态结构、条件路由、interrupt/resume、checkpoint、节点级观测；代价是 state schema 和副作用幂等更复杂。
- 追问：checkpoint 会导致副作用重复吗 → 答法要点：会，所以节点区分纯计算和写操作，关键写入放受控结束链路并用状态标记去重。

#### A8 为什么不做一个万能 ReAct Agent
**考察点**：护栏 vs 自由度权衡
**口播答案**：训练系统里大量规则必须稳定——阶段顺序、题数上限、评分持久化、用户隔离，不能让模型即兴发挥。万能 ReAct 带来更多循环、权限风险、成本和不可复现。我的做法是外层程序建护栏，局部开放模型决策。Agent 工程的重点不是把更多决策交给模型，而是建立清晰的状态、工具、权限、上下文、停止条件和失败边界。
**追问链**：
- 追问：哪些地方确实放开给模型了 → 答法要点：面试官追问措辞、逐题评分、画像语义抽取合并——规则写不死的地方。
- 追问：什么时候值得上多 Agent → 答法要点：角色具备独立上下文/权限/并行价值时（如独立 Safety Reviewer）；否则通信 token 和状态一致性成本不划算。

#### A9 训练结束的"双轨更新"为什么分两轨
**考察点**：确定性算法与 LLM 的分工（核心论点）
**口播答案**：两类信息性质完全不同。可精确计算的——分数、掌握度、SM-2 间隔、趋势——必须稳定、可解释、可回归测试，走确定性算法，模型漂移不会让掌握度无故波动。需要语义理解的——从多段评价抽取共同薄弱点、判断两条记忆是否同一事实——只有 LLM 做得了。拆成两轨，避免 LLM 控制本可精确计算的状态。
**追问链**：
- 追问：LLM 轨挂了确定性轨受影响吗 → 答法要点：不受，两轨解耦；LLM 合并失败降级到 embedding 确定性合并，掌握度/SM-2 照常更新。
- 追问：掌握度为什么不能 LLM 打 → 答法要点：要可复现、可单测、可跨版本比较；难度和分数能直接算（难度/5 × 得分/10），确定性公式更合适。

#### A10 这是多 Agent 系统吗
**考察点**：真实性边界，顶住诱导不夸大
**口播答案**：不是，这点我必须讲准。真正自由选工具的只有浮动助手，而且是单 Agent + 18 个工具，不是多 Agent 协作。简历面试是受控状态机，训练是 Workflow。职责分离我用状态机、流水线、不同模型分工已经实现了，没必要为概念好听包装成多 Agent。要聊"要不要改多 Agent"我可以聊演进方向，但现状要说实话。
**追问链**：
- 追问：职责分离体现在哪 → 答法要点：逐题评分小模型并发、整体总结大模型；出题/评估/画像合并是不同链路不同 prompt。
- 追问：什么情况会真的上多 Agent → 答法要点：角色需要独立上下文/权限/并行价值时；否则不划算。
**红线**：绝不说成多 Agent；绝不声称用了 MCP——工具直接定义在应用代码里。

#### A11 项目现在最大的不足是什么
**考察点**：自我批判能力
**口播答案**：三点。一，它是完整的单机产品原型不是生产架构：SQLite 主库、单 worker、画像存本地 JSON——单机成立，多实例下文件锁和并发模型失效。二，测试覆盖不足：算法层有 pytest 但没接 CI。三，个性化的长期学习效果只有离线评测，还没过线上 A/B——离线不能替代生产实验。我能清楚区分已实现的能力和未来演进。
**追问链**：
- 追问：文件画像并发现在怎么兜 → 答法要点：per-user 锁 + 临时文件原子替换 + 锁外计算锁内提交；规模化要迁 DB 行 + 乐观锁。
- 追问：知道不足为什么不先修 → 答法要点：项目定位是验证闭环设计；还债顺序明确——先 CI 门禁再迁存储。

#### A12 扩展到十万用户怎么演进
**考察点**：系统设计视野（详细展开见模块 H）
**口播答案**：核心是把有状态的部分外部化。FastAPI 无状态可水平扩；SQLite→PostgreSQL 解决多实例写并发；画像 JSON→带版本号的表 + 乐观锁；checkpoint 迁共享后端；重活（embedding/评估/画像总结）进分布式队列；Qdrant 按租户规划分片；加 LLM Gateway 统一路由限流计费；SSE 事件持久化支持断线续传；接 OpenTelemetry 做链路追踪。
**追问链**：
- 追问：迁 PG 后画像并发一致性 → 答法要点：version 列乐观锁，写回校验版本，冲突重试；改动事件日志化可审计回滚。
- 追问：是做了还是设想 → 答法要点：诚实说是演进设想，但每步对应现架构一个具体瓶颈点。

## 模块B：长期记忆与用户画像

#### B1 ⭐ Mem0 风格两阶段更新具体怎么做
**考察点**：画像更新机制的核心流程
**口播答案**：第一阶段"抽取"：训练结束后 LLM 从面试记录抽取新发现——薄弱点、优势、思维模式。第二阶段"合并"：把新发现和已有画像一起给 LLM，对每条做四选一：ADD 新问题、UPDATE 已有问题的新表现、IMPROVE 已有问题变好了、NOOP 重复无价值。口诀"增改优跳"。关键设计：LLM 只做语义决策不碰数字——掌握度是确定性公式，复习间隔是 SM-2 算的。画像的文字部分有 LLM 的语义理解力，数值部分可解释可回放。
**追问链**：
- 追问：为什么要两阶段，一步到位不行吗 → 答法要点：抽取和合并的失败模式不同——抽取错是漏发现，合并错会污染已有画像；分开后合并阶段能看到完整旧画像做对比决策，也便于分别调 prompt。
- 追问：合并把两个不同问题误判成同一个怎么办 → 答法要点：有语义去重阈值兜底（0.75 相似度才候选合并）+ 操作日志可回放定位是哪次合并引入的。

#### B2 ⭐ 为什么掌握度不让 LLM 打分
**考察点**：设计红线的理由
**口播答案**：稳定性和可解释性。LLM 打分两个问题：同样表现打分抖动；跨模型跨版本不可比。掌握度要用来做难度规划和趋势图，必须确定性：难度/5 × 得分/10，输入相同输出相同，可单测可回归。LLM 的判断力用在它擅长的地方——"这两个薄弱点是不是同一个问题"这类语义判断。总纲一句话：语义归 LLM，数值归算法。
**追问链**：
- 追问：难度本身是 LLM 出题时自报的，那不还是 LLM 影响了掌握度 → 答法要点：所以另有难度校准——离线锚点题库 k-NN 修正 LLM 自报难度（模块 E 展开），进入公式的难度是校准后的。
- 追问：得分不也是 LLM 评的吗 → 答法要点：是，这是必要的 LLM 输入，但它是"单点评分"而非"状态维护"——评分进公式后的累积、衰减、调度全是确定性的，LLM 的抖动不会被状态放大。

#### B3 ⭐ 向量记忆的去重和时间衰减怎么设计的
**考察点**：记忆治理参数背后的思考
**口播答案**：去重解决"同一个坑反复摔"造成的膨胀：新记忆入库前和已有记忆算余弦，≥0.75 视为同一条，合并不新增。时间衰减解决"三个月前的薄弱点还该不该影响今天"：14 天半衰期，但衰减权重封顶 30%——老记忆影响力下降但不清零，因为薄弱点复发是常态。每用户 500 条上限，超限淘汰最旧的。这三个参数都是成本、检索质量和记忆有效性的平衡点。
**追问链**：
- 追问：0.75 怎么定的 → 答法要点：经验值起步 + 中文技术文本实测校正："Redis 持久化没讲清"和"RDB/AOF 区别不清楚"应该合并（相似度约 0.8），"Redis 持久化"和"Redis 集群"不应该（约 0.6），0.75 是分界。
- 追问：为什么衰减要封顶 30% → 答法要点：不封顶的话老记忆权重趋近 0 等于遗忘，但求职者的薄弱点是会复发的——封顶保证"曾经弱过"永远保留最低限度的影响力。
- 追问：500 条满了怎么办 → 答法要点：淘汰 created_at 最旧的；因为有去重，500 条已经代表 500 个不同语义的记忆点，对单用户绰绰有余。

#### B4 ⭐ SM-2 是什么？你们怎么改的？
**考察点**：间隔重复算法与业务适配
**口播答案**：SM-2 是 Anki 用的间隔重复算法：答得好间隔指数拉长，答得差重置，ease_factor 有 1.3 下限防"永久惩罚"。我做了两个改造：一是复习对象从"卡片"换成"薄弱点"——复习的不是题目而是能力短板；二是加了毕业机制：连续 3 次 ≥7 分的薄弱点自动退出复习队列，否则薄弱点列表只增不减，复习队列会通胀。到期复习按 ease_factor 升序出题，最难的先来。口诀"三高毕业"。
**追问链**：
- 追问：为什么下限是 1.3 → 答法要点：SM-2 原始设计——ease_factor 再低，间隔增长会慢到复习压力爆炸；1.3 意味着最难的项目间隔也按 1.3 倍缓慢增长。
- 追问：毕业后又答错了呢 → 答法要点：重新入列，从头积累连击；毕业不是删除，是降优先级，历史记录还在。
- 追问：为什么是 3 次和 7 分 → 答法要点：1 次可能是运气，2 次仍有偶然，3 次连续是趋势；7 分是评分体系里"合格偏上"的分界。都是可调参数，关键是"连续"——中间断一次就重置计数。

#### B5 画像文件为什么用 JSON 不进数据库
**考察点**：存储选型的场景理由
**口播答案**：画像是"低频写、整体读、人可审"的数据：每次训练结束写一次，出题时整体读入，格式是嵌套结构。JSON 文件三个好处：结构自由（画像 schema 一直在演进）、人可直接打开审查（调试个性化问题时非常关键）、天然按用户目录隔离。并发用 per-user 锁 + 临时文件原子替换兜住。它的适用边界是单机——多实例部署就要迁带版本号的 DB 行，这是明确的演进路径。
**追问链**：
- 追问：原子替换怎么做的 → 答法要点：写临时文件→fsync→rename 覆盖，rename 在同文件系统是原子的，读者永远看到完整旧版或完整新版。
- 追问：锁外计算锁内提交是什么 → 答法要点：LLM 合并耗时几秒，不能拿着锁等 LLM；先无锁计算合并结果，进锁后重读最新画像做快速合并提交，缩短临界区。

#### B6 记忆检索时怎么排序
**考察点**：多因素融合排序
**口播答案**：语义相似度为主，时间衰减做调制：最终分 = 余弦相似度 × (1 - 衰减权重) + 新鲜度 × 衰减权重，衰减权重由记忆年龄按 14 天半衰期算出、封顶 30%。效果是：语义高度相关的老记忆仍然能排上来（衰减封顶保证），语义相近时新记忆优先。这比"只看相似度"多了时间维度，比"硬性过期删除"保留了长尾价值。
**追问链**：
- 追问：为什么不直接把过老的记忆过滤掉 → 答法要点：求职场景的知识短板生命周期很长，半年前的弱点可能依然弱；衰减是降权不是否决。

#### B7 画像被 LLM 合并坏了怎么恢复
**考察点**：可恢复性设计
**口播答案**：三层保障。第一，合并是操作式的（ADD/UPDATE/IMPROVE/NOOP 逐条执行），不是"整个画像重写"——LLM 输出异常时影响面是单条目不是全画像。第二，操作日志：每次合并的操作序列有记录，可以定位"这条错误画像是哪次训练的哪个操作引入的"。第三，文件原子替换保证不会出现半写状态。最坏情况下画像文件是人可读的 JSON，手工修正也可行——这也是选 JSON 的原因之一。
**追问链**：
- 追问：LLM 返回的操作格式不合法呢 → 答法要点：解析失败该轮合并放弃，降级到 embedding 确定性合并（相似度超阈值就并入），画像不更新坏数据。

#### B8 EWMA 在掌握度里怎么用的
**考察点**：趋势 vs 快照
**口播答案**：掌握度不是"最近一次的得分"也不是"历史平均"，而是指数加权移动平均：新掌握度 = 0.7 × 旧掌握度 + 0.3 × 本次贡献，本次贡献 = 难度/5 × 得分/10 × 100。0.7/0.3 的含义是有记忆但偏保守——一次超常发挥不会让掌握度暴涨，一次失误也不会崩盘，但持续的进步/退步会稳定反映出来。这和 SM-2 是两回事：EWMA 回答"你现在什么水平"，SM-2 回答"什么时候该复习"。
**追问链**：
- 追问：为什么权重是 0.7/0.3 → 答法要点：让单次波动的影响限制在 30%，约 3~4 次持续表现才能显著改变掌握度——匹配"能力变化是渐进的"这一先验。
- 追问：难度为什么要进公式 → 答法要点：答对难题和答对简单题的信息量不同；难度/5 归一化后，答对 5 星题的贡献是 1 星题的 5 倍。

#### B9 多设备/多会话同时训练会不会把画像写坏
**考察点**：并发一致性
**口播答案**：单机内靠 per-user 锁串行化——同一用户的画像更新排队执行；进程内异步任务用每用户 asyncio 锁，文件层再加独占文件锁双保险。跨进程/多实例是已知边界：文件锁在 NFS 或多容器下不可靠，所以规模化路径是迁 DB + 乐观锁。我在简历上不写"支持多实例"，就是因为这里没做。
**追问链**：
- 追问：锁的粒度为什么是用户级 → 答法要点：不同用户的画像完全独立无共享，用户级锁是无争用的天然分片；更细（字段级）收益为零，更粗（全局锁）互相拖累。

#### B10 向量记忆和知识库都在 Qdrant，怎么隔离
**考察点**：多租户设计
**口播答案**：两种策略刻意不同。知识库按 `kb_{user}_{topic}` 分 collection——因为知识库要整库重建（换 embedding 模型、文档变更），独立 collection 支持原子重建和按 topic 生命周期管理。记忆库是单 collection + payload 里 user_id 过滤的多租户——因为记忆是细粒度小对象、每用户 ≤500 条，分 collection 会产生海量小 collection，管理成本远超收益。所有记忆查询路径都强制带 user 过滤。
**追问链**：
- 追问：payload 过滤会不会漏 → 答法要点：过滤在存储层 API 统一封装，业务代码拿不到"不带 user 过滤"的查询入口；代码审查也确认过 search/iter/count/delete 全部路径带过滤。

#### B11 为什么记忆去重是 0.75、知识 chunk 去重是 0.85
**考察点**：同类参数在不同场景的差异化
**口播答案**：因为两边"重复"的定义不同。记忆去重判断的是"这两条是不是同一个用户弱点"——"Redis 持久化没讲清"和"RDB/AOF 区别模糊"是同一个弱点的两种表述，语义距离可以较远，阈值放宽到 0.75 促进合并。知识 chunk 去重判断的是"这两段是不是同一段知识的转述"——知识文本客观、表述稳定，0.85 以上才算转述，阈值收紧防止把相关但不同的知识点误删。一句话：记忆求"并"，知识求"全"。
**追问链**：
- 追问：这两个阈值调错方向会怎样 → 答法要点：记忆阈值过高→同一弱点堆积多条、复习队列虚胖；知识阈值过低→检索结果丢失相关知识点、出题覆盖面变窄。

#### B12 画像里存了哪些东西，怎么防止无限膨胀
**考察点**：画像 schema 与治理
**口播答案**：核心字段：薄弱点列表（带 SM-2 状态）、强项列表、各 topic 掌握度（分数/趋势/复盘）、思维模式与沟通风格、统计信息（得分历史）。防膨胀三机制：合并优先于新增（四操作里 UPDATE/IMPROVE/NOOP 都不加条目）、薄弱点毕业退出、向量记忆 500 条上限 + 语义去重。画像文件始终保持在"一次 LLM 调用能整体放进上下文"的量级——这是硬约束，画像塞不进 prompt 就失去意义了。
**追问链**：
- 追问：得分历史会无限长吗 → 答法要点：统计聚合保留趋势，明细有窗口上限；出题时只装配最近若干条。

## 模块C：三种 Agent 编排选型

#### C1 ⭐ 为什么只有简历面试用 LangGraph
**考察点**：编排选型的判断标准
**口播答案**：流程形状决定编排形式。简历面试是全项目唯一的"有环状态流程"：五个阶段来回转移、每题停下来等用户作答、中途可能断线要恢复——状态机的三个典型特征全占。专项训练是单向流水线、助手是开放指令，都不需要状态机。框架有成本（state schema、checkpoint 兼容、调试复杂度），只在收益覆盖成本的场景用。反过来这也是我对"技术选型"的态度：不是会什么用什么，是场景要什么上什么。
**追问链**：
- 追问：五阶段是哪五个 → 答法要点：greeting→self_intro→technical→project_deep_dive→reverse_qa（口诀"迎自技项反"），外加 END 终态。
- 追问：其他 graphs/ 目录下的文件不是图吗 → 答法要点：目录名历史沿革，里面只有 resume_interview 是真 StateGraph，其余是普通 async 流水线——我文档里也专门修正过这点。

#### C2 ⭐ interrupt + checkpoint 断线续接的完整流程
**考察点**：LangGraph 核心机制的实操理解
**口播答案**：图编译时声明 `interrupt_before=["wait"]`——执行到 wait 节点前暂停，把控制权还给 HTTP 层，当前状态由 checkpointer 按 thread_id（就是 session_id）落盘。用户作答后，后端拿同一 thread_id 调 `invoke`，LangGraph 从 checkpoint 恢复状态、注入用户输入、从断点继续跑到下一个 interrupt。服务重启也一样：checkpoint 在 SQLite 文件里，重启后照常恢复。整场面试就是"跑到 wait→暂停落盘→用户答→恢复继续"的循环。
**追问链**：
- 追问：checkpointer 用的什么 → 答法要点：SqliteSaver 进程级单例，落盘独立的 checkpoints.db；早期用 MemorySaver，重启丢进度，这对 20 分钟一场的面试不可接受，所以换掉了。
- 追问：多 worker 下会冲突吗 → 答法要点：SqliteSaver 内部有锁 + SQLite 文件锁，单机多 worker 能工作；跨机器要迁共享后端（PG checkpointer），这是规模化清单里的一项。
- 追问：checkpoint 恢复会重复副作用吗 → 答法要点：节点区分纯计算和写操作；关键写入（评分持久化）放受控结束链路，用状态标记去重。

#### C3 ⭐ 状态机怎么防死循环
**考察点**：LLM 决策的确定性兜底
**口播答案**：双保险推进。路由函数先看确定性硬上限：当前阶段题数到顶直接 advance，不管 LLM 怎么说；没到顶才参考 LLM 评估信号（这个阶段问够了吗）决定 ask 还是 advance。LLM 判断失灵（一直说"再问问"）时，硬上限保证状态机必然前进；LLM 正常时，推进又是语义合理的。这是"LLM 决策 + 确定性兜底"模式——它在我项目里反复出现：评分有公式兜底、难度有锚点校准、这里有题数上限。
**追问链**：
- 追问：上限设多少 → 答法要点：每阶段有硬上限常量；正常流程 LLM 信号早于上限触发，上限是保险丝不是常态。
- 追问：LLM 评估信号怎么传 → 答法要点：评估结果嵌在结构化标记里随流输出，后端解析后写进 state，路由函数读 state 决策。

#### C4 ⭐ 浮动助手为什么单 Agent 不做多 Agent
**考察点**：多 Agent 的成本收益判断
**口播答案**：多 Agent 的收益是任务天然可并行分解，成本是通信协议、状态同步、调试复杂度。助手场景是"单用户单意图链"——查画像、开面试、改设置——没有可并行的子任务，多 Agent 纯属为架构而架构。我把复杂度花在单 Agent 做深上：18 个工具的结构化返回、同轮多工具并发、多轮工具链推理、工具 allowlist 权限控制。单 Agent 做深比多 Agent 做浅难得多也有用得多。
**追问链**：
- 追问：18 个工具模型会选错吗 → 答法要点：三道防线——工具描述面向场景写清适用边界；相近工具做了合并避免歧义；每轮循环数有上限，选错的探索成本有界。
- 追问：同轮并发怎么实现 → 答法要点：模型一轮返回多个 tool_call 时并发执行（asyncio.gather），结果按 call_id 结构化回填成 tool message，再进下一轮推理。
- 追问：工具失败怎么办 → 答法要点：失败信息作为 tool 结果回给模型，模型决定重试、换工具还是向用户解释——失败也是观察的一部分。

#### C5 专项训练流水线的五段各做什么
**考察点**：Workflow 的阶段划分
**口播答案**：①准备：加载画像、掌握度、到期复习项，确定薄弱点目标和难度分布规划。②检索：按薄弱点拆多路查询→RRF 融合→去重→可选重排。③生成：种子题库和 LLM 混合出题，流式逐题推送前端。④校验：语义重复/薄弱点覆盖/难度分布三个 validator，不合格局部重生成。⑤校准与持久化：锚点 k-NN 校准难度，题目落库。每段有清晰的输入输出，进度经 SSE 可观测，失败可以定位到段。
**追问链**：
- 追问：为什么不用 LangGraph 表达 → 答法要点：无环无人在回路无中断恢复需求，普通 async 函数串联最简单直接；状态机的三个卖点一个都用不上。

#### C6 评估为什么和训练解耦
**考察点**：解耦评估链路的设计
**口播答案**：作答提交后评估是独立链路：并发逐题评分（小模型）+ 整体总结（大模型）。解耦三个好处：评估失败不影响作答数据（答案已持久化，可重新评估）；并发逐题把总时延从串行 N 题压到接近单题；大小模型分工控制成本——逐题评分是量大的结构化任务给小模型，总结是质量敏感任务给大模型。
**追问链**：
- 追问：评估到一半挂了怎么办 → 答法要点：transcript 已落库，历史页能识别"已作答未评估"状态给出重新评估入口——用非空 transcript 做信号。

#### C7 JD 备面和专项训练的编排差异
**考察点**：相似场景的复用与差异
**口播答案**：同为流水线，差在上下文源头：专项训练的目标来自画像薄弱点，JD 备面的目标来自 JD 解析——先 LLM 解析 JD 抽取公司/岗位/技能要求生成预览，用户确认后基于预览 + 简历 + 知识库出题。复用了检索融合、流式推送、校验这些组件，只换了"目标从哪来"这一段。组件化的流水线让新场景的成本是"写差异"而不是"重写全部"。
**追问链**：
- 追问：JD 解析失败呢 → 答法要点：解析是独立阶段，格式异常直接返回错误让用户重试，不会带着坏预览进出题。

#### C8 简历面试的评分什么时候发生
**考察点**：流程与副作用时机
**口播答案**：不是每答一题就评一题。面试进行中评估信号只用于路由（追问还是切阶段），轻量嵌在对话流里；完整的逐题评分和总结在面试结束后统一跑——这样面试中的延迟最小（用户等的是下一个问题不是评分），结束链路是唯一的写入点，副作用集中可控，checkpoint 重放也不会重复写分。
**追问链**：
- 追问：用户中途退出没走到结束呢 → 答法要点：checkpoint 里状态还在，回来可续；主动放弃的会话保持未评估状态，历史页可见。

#### C9 为什么工具定义在代码里而不是 MCP
**考察点**：对新协议的клад判断
**口播答案**：MCP 解决的是"跨进程/跨方的工具互操作"——工具由第三方提供、要跨语言跨部署共享时才有价值。我的 18 个工具全是进程内函数，调用方和提供方是同一个应用，直接函数注册表最简单：类型安全、零序列化开销、调试直接。如果未来要把工具开放给外部 Agent 用，那时上 MCP 才是对的。技术选型要看解决什么问题，不是看什么新。
**追问链**：
- 追问：那你了解 MCP 吗 → 答法要点：能讲清协议角色（host/client/server）、能力协商和工具发现机制，说明"不用"是判断不是不懂。

#### C10 三种编排的失败恢复各是什么
**考察点**：横向对比的深度
**口播答案**：状态机靠 checkpoint——失败点之前的状态都在，恢复即续跑。流水线靠幂等重试——每段输入输出明确，失败段可以重跑，落库有去重。助手靠对话上下文——工具失败作为观察回给模型，由模型决定下一步，最坏情况用户重发一句话。三种恢复语义正好匹配三种流程形状：长流程要断点、批处理要重跑、交互要即时兜底。
**追问链**：
- 追问：哪种最难做对 → 答法要点：状态机——checkpoint 与代码版本的兼容、副作用幂等都要设计；所以只在必须的地方用它。

#### C11 如果明天要加一个新场景，怎么选编排
**考察点**：方法论迁移
**口播答案**：三个问题定位：①流程有环吗（要不要来回转移/等待外部输入）→ 有环上状态机。②路径能预先枚举吗 → 能枚举用流水线，段间清晰交接。③意图开放吗 → 开放才上 Agent + 工具。比如"模拟群面"：多角色轮流发言有环 + 等用户输入 → 状态机；"批量导入题库"：纯单向 → 流水线；"帮我分析这周训练情况"：开放意图 → 现有助手加工具就行。
**追问链**：
- 追问：有没有场景三种都不合适 → 答法要点：长时后台任务（如全库重索引）用的是任务队列 + 熔断器，是第四种形态——编排之外还有异步任务这一层。

## 模块D：流式与上下文工程

#### D1 ⭐ 为什么全链路 SSE 而不是 WebSocket
**考察点**：协议选型
**口播答案**：流式场景全是"服务器单向推"——出题、评估、参考答案、助手回复——没有客户端流式上行的需求，SSE 更简单：纯 HTTP、自动重连语义、代理友好。WebSocket 的双向能力用不上，还要自己处理心跳协议和代理配置。工程上 SSE 做了两个加固：30 秒空闲心跳 ping 防 nginx 掐空闲连接；长任务每 200 字符发 progress 事件，前端能画进度而不是干等。
**追问链**：
- 追问：nginx 那边怎么配合 → 答法要点：禁用代理缓冲（X-Accel-Buffering: no / proxy_buffering off），否则 nginx 攒满缓冲区才发，流式变批式。
- 追问：断线怎么办 → 答法要点：SSE 自带重连；关键状态（评测任务）前端可用 job_id 轮询恢复，不依赖连接本身。

#### D2 ⭐ 前端怎么消费流式 JSON
**考察点**：流式协议的前后端契约
**口播答案**：后端发的是事件流，每个事件是单行 `data: {json}`，type 区分 token/progress/ping/complete/error/done。出题这类结构化输出用增量 JSON 解析：LLM 流式吐 JSON 数组，前端边收边解析出完整的单题就渲染一题——用户看到题目一道道出现而不是等全部生成完。渲染用 rAF 批处理 setState 防止每 token 一次重渲染。
**追问链**：
- 追问：半个 JSON 怎么处理 → 答法要点：维护缓冲区，只在括号配平/解析成功时消费；失败就继续攒。
- 追问：组件卸载了流还在推呢 → 答法要点：AbortController 中断 fetch + 卸载守卫防 setState-after-unmount——这两个是我们前端审查的标准检查项。

#### D3 ⭐ 三层上下文的预算怎么分配
**考察点**：ContextBudget 机制
**口播答案**：每个 section 声明优先级和最小保留额，ContextBudget 按优先级从高到低分配 token，但每层先扣除保底额度——这是关键设计：不设保底的话，RAG 检索结果一长就把画像层完全挤出上下文，个性化名存实亡。超预算的层做尾部截断而不是整层丢弃。优先级大致是：系统约束和当前目标最高，画像和领域状态其次，检索内容量最大但可截断性也最强。
**追问链**：
- 追问：截断会不会把关键内容截掉 → 答法要点：各层内部已按重要性排序（检索结果按融合分、复习项按 ease_factor），尾部截断丢的是层内最不重要的。
- 追问：为什么不用更聪明的压缩（LLM 摘要）→ 答法要点：出题路径对延迟敏感，摘要多一次 LLM 调用；画像本身已是压缩产物，再压缩边际收益低。

#### D4 ⭐ Prompt Cache 怎么利用的
**考察点**：成本工程
**口播答案**：消息结构设计成"稳定前缀 + 易变尾部"：系统提示在会话初始化时构建一次就冻结，逐字节不变；每轮变化的（当前阶段、最新对话、检索内容）全部追加在后面。渠道方的 prompt-prefix cache 按前缀匹配，前缀稳定每轮都命中，长会话的输入成本和首 token 延迟都显著下降。多模态同理：图片作为独立消息放前缀之后，不打断可缓存前缀。反模式是把"当前时间"这类易变量塞进系统提示——一个字符变化整个缓存作废。
**追问链**：
- 追问：怎么验证 cache 真的命中了 → 答法要点：API 响应的 usage 里有 cached token 数；设计时的自查标准是"系统提示在会话内 byte-identical"。
- 追问：cache 和个性化矛盾吗 → 答法要点：不矛盾——个性化内容（画像/检索）都在易变尾部，前缀只放与用户无关的角色定义和规则。

#### D5 SSE 的错误语义怎么设计
**考察点**：流式错误处理（有真实修复故事）
**口播答案**：事件流里 error 是显式事件类型，前端收到就终止等待展示错误。后端这边有一条我们真实踩过又修掉的坑：早期 LLM 流失败时只给客户端发 error 事件，但服务端调用方拿不到失败信号，会把空字符串当成"生成结果"持久化——最严重的场景是把知识库 README 清空。修复是给流式 helper 加显式的失败信号（error 与 result 互斥），所有调用方失败即中止，绝不落盘空结果。教训：流式接口的失败语义要同时通知两个方向——客户端和服务端调用方。
**追问链**：
- 追问：怎么发现这个 bug 的 → 答法要点：深度代码审查时发现失败路径不产生 result 且调用方无守卫；顺藤摸瓜找到三处同源隐患一次修掉。

#### D6 长任务（评测）为什么不走 SSE 而走轮询
**考察点**：连接模型选择
**口播答案**：离线评测跑几分钟，长连接挂几分钟不划算也不可靠（代理超时、页面刷新就丢）。改为任务模型：提交返回 job_id，前端轮询状态接口，轮询间隔按 1.5 倍递增、封顶 15 秒——任务刚开始密集看进度，跑久了降低频率。页面刷新后凭 job_id 恢复跟踪。原则：秒级交互用 SSE，分钟级任务用 job + 轮询。
**追问链**：
- 追问：为什么不用 SSE 推任务进度 → 答法要点：可以但收益低——进度粒度是分钟级，轮询足够；SSE 要处理断连恢复反而复杂。

#### D7 上下文里的历史对话怎么控制长度
**考察点**：会话内存管理
**口播答案**：分场景。简历面试的对话历史在 LangGraph state 里随 checkpoint 走，上下文装配时只取最近窗口 + 阶段摘要；助手对话持久化在表里，取最近 N 条进上下文。原则是"最近的原文 + 更早的摘要/丢弃"——面试官不需要逐字记得第一题，但需要知道"技术环节已经考过 Redis"。
**追问链**：
- 追问：摘要谁来做 → 答法要点：阶段切换时的阶段小结顺带产出，不额外增加调用。

#### D8 流式输出中途换模型可以吗
**考察点**：渠道切换边界
**口播答案**：不可以，首 token 之后不能切。流式响应已经开始向客户端吐内容，此时渠道失败只能把 error 事件发给客户端由用户重试——中途换渠道重新生成会导致内容拼接错乱（两个模型的风格、格式、甚至立场都可能不同）。所以 failover 的边界是"首 token 前"：建连失败、首包超时可以静默切渠道重试，开始输出后失败就如实报错。
**追问链**：
- 追问：那用户体验不是受损吗 → 答法要点：是权衡——静默重试拼接错误内容比显式失败更伤信任；且渠道池让"首 token 前失败"覆盖了大多数故障。

#### D9 React 前端消费流式时最容易犯的错
**考察点**：前端工程细节（体现全栈深度）
**口播答案**：四个：①每 token 一次 setState 导致渲染风暴——用 rAF 批处理；②组件卸载后流回调还在 setState——AbortController + 卸载守卫；③竞态：旧请求的流覆盖新请求的内容——generation 计数或 abort 旧流；④双发：用户连点两次提交打断进行中的流——用 ref 做同步守卫（state 是异步的，防不住同一帧内的第二次点击）。这四个我们前端代码里都有标准处理，代码审查时也当检查项。
**追问链**：
- 追问：为什么 state 防不住双发 → 答法要点：setState 是异步批处理的，第二次点击时 state 还是旧值；ref 的写入是同步的，isStreamingRef.current 立刻可见。

#### D10 全链路流式对后端架构的约束
**考察点**：流式的系统性影响
**口播答案**：三个约束。①异步生成器成为主要的响应形态，同步阻塞调用必须 to_thread 包装，否则单 worker 的事件循环被卡住所有流都停；②中间层（nginx）必须关缓冲、心跳保活；③失败语义要双向通知（见 D5）。收益换来的是：LLM 生成 30 秒的任务用户 1 秒就开始看到内容，感知延迟差一个数量级。
**追问链**：
- 追问：怎么发现事件循环被卡 → 答法要点：症状是所有并发请求的流同时停顿；审查时靠"async def 里找同步 IO 调用"排查，我们最近一轮审查就修了 4 处。

## 模块E：个性化 RAG 与可控出题

#### E1 ⭐ 为什么按薄弱点拆多路查询
**考察点**：检索策略的动机
**口播答案**：出题的检索需求天然多意图：用户有 3 个薄弱点，一条查询只能顾一个——单查询的结果会被语义最"热"的薄弱点垄断，其他薄弱点召回为空。按薄弱点拆成多路并发，每路拿各自 top-k 再融合，保证每个薄弱点都有材料。这个设计后来还反过来影响了评测指标：我们把在线指标从 discrimination 换成 coverage，就是为了度量"每个薄弱点是否都召回到了料"。
**追问链**：
- 追问：最多拆几路 → 答法要点：有上限（薄弱点取 top 几个），防止查询爆炸；薄弱点本身按 SM-2 的 ease_factor 排序取最需要的。
- 追问：多路并发的延迟 → 答法要点：asyncio 并发执行，总延迟≈最慢一路，不是求和。

#### E2 ⭐ RRF 是什么，为什么不用分数加权融合
**考察点**：融合算法的原理与选型
**口播答案**：Reciprocal Rank Fusion：每个文档的融合分 = Σ 1/(k + 它在每路的排名)，k=60 是原论文标准值。选 RRF 而不是分数加权，因为多路查询的相似度分数不可比——不同 query 的分数分布不同，直接加权会被分数偏高的路垄断。RRF 只用排名，天然免疫分数尺度问题。k=60 的作用是压平头部：k 太小则每路第一名权重畸高；k=60 让"在多路都排中上"的文档赢过"只在一路排第一"的——这正是多薄弱点覆盖想要的。
**追问链**：
- 追问：k 调大调小会怎样 → 答法要点：k→0 退化成"谁的第一名多谁赢"；k→∞ 趋近所有排名等权。60 是头部与长尾的经验平衡点。
- 追问：有没有试过其他融合 → 答法要点：RRF 是零调参、鲁棒的默认选择；数据规模不支撑学习式融合（learning to rank）的训练成本。

#### E3 去重和重排各解决什么，为什么重排可选
**考察点**：检索后处理管线
**口播答案**：去重解决"同一知识点的不同表述被重复召回"：融合后两两余弦 >0.85 判为转述只留一个，省 token 也防出重复题。重排解决精度：bi-encoder 检索快但只算向量距离，cross-encoder 对 query-doc 拼接打分更准但慢一个数量级。做成可选是延迟预算的权衡：出题链路里检索只是一环，rerank 走外部 API 有网络开销，所以按渠道配置开关——质量敏感场景开，延迟敏感场景关。
**追问链**：
- 追问：0.85 和记忆库的 0.75 为什么不同 → 答法要点：知识文本客观稳定，0.85 才算转述；记忆是主观描述，同一弱点表述分散，0.75 促进合并。"记忆求并，知识求全"。

#### E4 ⭐ 增量索引怎么实现，什么时候全量重建
**考察点**：索引生命周期管理
**口播答案**：文件哈希 manifest：索引旁存一份"文件→内容哈希"清单，重建时 diff 当前文件集，只对新增/修改的重嵌入、删除的清理向量，不动没变的。全量重建只有四个触发点：首次构建、embedding 模型切换导致维度不匹配、空 collection 自愈、显式 force。numpy 和 Qdrant 双后端实现同一套增量语义。效果：改一个文档的重建成本从"全库重嵌"降到"单文件重嵌"。
**追问链**：
- 追问：构建中途失败 manifest 会脏吗 → 答法要点：manifest 在成功后才更新——失败时旧 manifest 还在，下次重建会把未完成的文件重新识别为"待处理"，自愈。
- 追问：换 embedding 模型怎么发现的 → 答法要点：维度探测不匹配即触发全量重建；这套失效逻辑挂在配置切换的 invalidate 链路上。

#### E5 ⭐ 种子题库和 LLM 混合生成是什么意思
**考察点**：生成策略
**口播答案**：纯 LLM 出题有两个问题：高频经典题反而出不好（它倾向生成"看起来新"的题）、批量生成质量方差大。种子题库是策展过的高质量题源，混合生成就是一部分题从种子池按薄弱点和难度选，一部分由 LLM 基于检索内容新生成——种子保下限，生成保覆盖和新颖度。选中的种子也会经 LLM 按用户上下文改写（贴合他的薄弱点表述），不是原样照搬。
**追问链**：
- 追问：比例怎么定 → 答法要点：按薄弱点与种子池的匹配度动态定——匹配到好种子就用，匹配不到才全靠生成；不是固定比例。

#### E6 ⭐ 三项校验各怎么算，不合格怎么办
**考察点**：质量门控的实现
**口播答案**：口诀"重覆难"。语义重复：题目两两 embedding 相似度超阈值判重——LLM 批量出题爱"换皮"。薄弱点覆盖：每个目标薄弱点至少有一题语义命中——这是个性化的底线。难度分布：实际分布与按掌握度规划的分布偏差不能超限。任一不合格只**局部重生成**问题题目：把"为什么不合格"（和哪题重复了/哪个薄弱点没覆盖）回填进重生成 prompt，合格的题保持不动。整批重来会把好题洗掉且成本翻倍。
**追问链**：
- 追问：重生成还不合格呢 → 答法要点：有重试上限，到限后带着可用的题出去（宁缺勿滥不成立——训练场景 8 题可用好过 0 题完美），校验结果记录在案。
- 追问：为什么校验不用 LLM 判 → 答法要点：三项全是 embedding/统计可算的，确定性校验免费、稳定、可回归——又是"数值归算法"。

#### E7 ⭐ 难度校准为什么用锚点 k-NN 不信 LLM 自报
**考察点**：LLM 输出的系统性偏差治理
**口播答案**：LLM 自报难度有系统性偏差——它标的"难度 3"随模型、随 prompt 漂移，而难度直接进掌握度公式，偏差会污染整个数值体系。锚点方案：离线用脚本给一批人工定级的锚点题算好 embedding，在线出题时新题 embedding 对锚点矩阵做 k-NN，按相似度加权邻居难度得到校准值，和 LLM 自报差 1 级以上就覆盖。确定性、跨模型稳定、锚点集可审计——LLM 自报只做初值。
**追问链**：
- 追问：换 embedding 模型锚点怎么办 → 答法要点：锚点矩阵是离线产物，维度和模型绑定；切换模型时缓存失效 + 维度守卫降级跳过校准并提示重跑锚点脚本——这是我们最近审查刚加固过的路径。
- 追问：锚点集怎么来的 → 答法要点：bootstrap 脚本离线生成，人工定级 + embedding，按 topic 一个文件。

#### E8 检索超时或知识库为空怎么办
**考察点**：降级路径
**口播答案**：检索包了 to_thread + 60 秒超时，超时或异常降级为"无知识库上下文"继续出题——画像和掌握度两层还在，题目仍是个性化的，只是少了知识库依据；同时事件流里发 progress 提示。知识库为空同理。原则：RAG 是增强不是依赖，检索失败不能让训练不可用。
**追问链**：
- 追问：Qdrant 挂了呢 → 答法要点：qdrant-only 模式不静默降级到 numpy（两边数据不同步，降级会出错数据）；检索按空上下文处理，后台委派重建/重连，服务不崩。

#### E9 流式逐题推送怎么和校验协调
**考察点**：流式与质量门控的张力
**口播答案**：这里有个真实的工程张力：校验要看全批（重复度、分布是批级属性），流式要逐题推。解法是分层：单题级校验（格式、字段完整性）流式时就做，推给前端的是结构合法的题；批级校验（重复/覆盖/分布）在批完成后跑，不合格的题重生成后以更新事件推送。前端按题号增量渲染 + 支持单题替换。
**追问链**：
- 追问：用户已经开始答被替换的题呢 → 答法要点：重生成发生在批完成后、用户作答前的窗口，正常时序不冲突；已开始作答的批不再替换。

#### E10 出题的个性化到底体现在哪几个决策点
**考察点**：把"个性化"拆解成可指认的机制
**口播答案**：四个决策点。①出什么：检索 query 由薄弱点生成，题目内容围绕你的短板。②多难：难度分布由掌握度规划——掌握度 30 的用户和 70 的用户拿到的难度曲线不同。③考什么旧账：到期复习项强制进出题目标，SM-2 说该复习就复习。④怎么问：画像里的思维模式和沟通风格影响题目表述与追问风格。每个决策点都能指到代码里的具体输入，不是"大模型自己看着办"。
**追问链**：
- 追问：冷启动没画像怎么办 → 答法要点：走冷启动策略——按 topic 默认难度分布 + 种子题库保底，第一轮结束画像就有了；掌握度为空时有显式的冷启动判定。

#### E11 为什么不做用户间协同（别人错什么你练什么）
**考察点**：功能边界与数据设计意识
**口播答案**：做了轻量版但刻意没做推荐系统：高频错点会自动沉淀进共享知识库（脱敏的知识性内容，不是用户数据），所有人的出题都能检索到——这是"知识沉淀"而非"协同过滤"。不做协同推荐因为：用户量级不支撑协同信号、面试训练的个性化主要由自身画像决定（你弱什么练什么，跟别人弱什么关系不大）、跨用户数据流动有隐私边界问题。
**追问链**：
- 追问：高频错点回写会不会污染知识库 → 答法要点：走独立目录（high_freq），与原始知识源分开，可整体清理；进入检索时和正规知识同池但可溯源。

#### E12 RAG 这套和"把文档全塞进长上下文"比呢
**考察点**：RAG vs long-context 的判断
**口播答案**：三个理由不塞。成本：每次出题都付全库 token 不可持续，检索只付相关部分。质量：长上下文的"迷失中间"问题真实存在，针对性检索的信噪比高得多。工程：知识库是按用户按 topic 增长的，长上下文有物理上限，检索没有。长上下文适合"单文档深读"，我们的场景是"多文档选相关"，是检索的主场。
**追问链**：
- 追问：以后上下文更便宜了呢 → 答法要点：混合演进——小知识库直接放上下文、大库仍检索；架构上检索层是独立模块，替换策略不动业务。

## 模块F：RAG 评测体系

#### F1 ⭐ 两套评测为什么分开，各是什么
**考察点**：评测体系总纲
**口播答案**：口诀"在线三无、离线八有"。在线：真实出题路径上零 LLM 成本算三个健康度——relevance（检索内容与查询的相关度）、coverage（每个薄弱点是否都召回到料）、diversity（结果多样性），纯 embedding、无 ground truth，作用是监控"检索质量突然退化"。离线：RAGAS 风格基准——LLM 从知识库合成 golden set，算 hit@k、strict hit、MRR、precision/recall，再 LLM Judge 打 faithfulness/relevancy/correctness，作用是版本间回归对比。两套量纲不同刻意不放一起比：在线 relevance 0.45-0.65 就是健康区间，别拿去和 RAGAS 的 0.8+ 比。
**追问链**：
- 追问：为什么在线不能也用 RAGAS → 答法要点：RAGAS 要 LLM Judge，在线路径加 LLM 评测等于每次出题成本翻倍延迟翻倍；在线要的是廉价持续的心电图，不是全面体检。
- 追问：前端怎么防止误比较 → 答法要点：每个指标配自己的色带（METRIC_SPEC），同一个 0.6 在不同指标下颜色不同——这条约定我们前端审查还修过一处违反。

#### F2 ⭐ 讲讲那个被换掉的指标（最好的故事，务必讲熟）
**考察点**：指标批判性思维 + 完整改进闭环
**口播答案**：早期在线指标里有个 discrimination——top1 与 top2 的余弦分差，通用检索里衡量"区分度"：分差大说明检索目标明确。上线观测后发现它对出题场景**方向反了**：出题恰恰希望每个 query 召回多条同等相关的材料来支撑出题多样性，健康的"扇形召回"分差趋近 0，反被这个指标判"差"——指标在惩罚我们想要的行为。我们把它换成 coverage：最高相似度过阈值的 query 占比，即"是不是每个薄弱点都召回到了料"，这才对齐多路检索的设计意图。教训两条：通用指标直接搬到具体场景可能反向优化；指标要在上线后持续被质疑，而不是定了就完。
**追问链**：
- 追问：怎么发现方向反了的 → 答法要点：健康的检索结果（人工看质量很好）指标却持续偏低，追查发现是指标定义与场景目标冲突——是"指标错了"不是"系统错了"。
- 追问：还犯过别的评测错误吗 → 答法要点：主动讲循环评测：早期用检索出的 chunk 对着检索它的 query 算 precision/recall，永远 ~100%，是自己证明自己；后来彻底移除——ground truth 必须独立于被评测系统。敢讲错误比装完美加分。

#### F3 ⭐ golden set 怎么合成，合成的可信吗
**考察点**：评测集构建方法
**口播答案**：LLM 读知识库文档片段，反向生成"这段能回答什么问题"，形成 (question, 来源chunk) 对——来源即 ground truth。可信性三道防线：生成时约束问题必须可由该片段回答且自包含；抽样人工抽查校准生成 prompt；评测结论只用于**相对比较**（版本 A vs B、策略 A vs B），不宣称绝对水平——合成集的系统性偏差在相对比较中会两边抵消。诚实的说法是：它是"可持续回归的基准"，不是"真实用户查询分布"。
**追问链**：
- 追问：合成问题会不会太"贴"文档措辞导致虚高 → 答法要点：会有这个倾向，所以有 strict 版指标 + 生成时要求改写措辞；且虚高是系统性的，不影响版本间相对比较。

#### F4 hit@k、strict hit、MRR 各说明什么
**考察点**：检索指标的准确理解
**口播答案**：hit@k：前 k 个结果里有没有 ground truth 来源——"找没找到"。strict hit 收紧命中判定（更严格的匹配口径），防止宽松匹配虚高。MRR：第一个命中结果排名的倒数取均值——"找到的排多前"，1.0 是全部第一位命中。三个合起来看：hit@k 高 MRR 低 = 找得到但排得靠后，该调融合或加重排；hit@k 低 = 召回本身有问题，查 embedding 或切分。
**追问链**：
- 追问：你们 k 取多少 → 答法要点：与出题链路实际使用的 top-k 对齐（简历上写 Hit@8 就是 k=8）——评测口径必须和生产口径一致才有意义。

#### F5 faithfulness / relevancy / correctness 怎么评的
**考察点**：LLM Judge 的使用
**口播答案**：LLM Judge 按 rubric 打分：faithfulness——答案是否忠于检索到的上下文（不编造）；answer relevancy——答案是否切题；correctness——对照参考答案的正确性。控制偏置的做法：同一 Judge 模型固定 rubric 保证 run 间可比；Judge 只做三个维度不做总分（总分掩盖问题）；结果入库跨 run 对比看趋势而非单点。
**追问链**：
- 追问：Judge 本身不可靠怎么办 → 答法要点：承认单点不可靠，靠三点缓解——趋势比单点可靠、与确定性指标（hit/MRR）交叉印证、异常分数人工抽查。

#### F6 ⭐ 个性化出题的效果实验怎么设计的
**考察点**：实验设计能力
**口播答案**：三策略对照：个性化（全三层上下文）/仅主题（只有知识库）/随机，同一画像下各出 N 套题，比三个指标。关键设计是前两个指标**确定性可算、不依赖 Judge**：薄弱点覆盖率——题目 embedding 与薄弱点的语义匹配率；难度分布匹配度——与规划分布的偏差。第三个才是 LLM Judge 综合质量，且盲评（Judge 不知道题来自哪个策略）。结论：个性化在三项全部领先，其中薄弱点覆盖率差距最大——这正是画像层的直接贡献，逻辑自洽。
**追问链**：
- 追问：为什么强调前两个指标不依赖 Judge → 答法要点：如果三个指标全是 LLM 评的，结论就是"LLM 觉得 LLM 出得好"，自证循环；确定性指标锚住结论的下限。
- 追问：这是线上 A/B 吗 → 答法要点：诚实说是离线对照，线上 A/B 需要用户量和实验周期，是下一阶段——但离线框架已经保证了"每次改动可回归"。

#### F7 评测历史入库有什么用
**考察点**：评测的工程化
**口播答案**：每次评测 run 的配置、指标、明细落库，支持跨 run 对比。三个用处：回归——改了切分策略/融合参数跑一轮就知道有没有退化；归因——指标掉了能对照配置差异定位；防口径漂移——历史 run 的口径记录在案，不会"上次 k=5 这次 k=8"比出假进步。评测不入库等于没做评测——单次数字没有参照系。
**追问链**：
- 追问：评测任务跑几分钟怎么管理 → 答法要点：后台 job + 状态轮询 + 前端可恢复跟踪（见 D6）；跑一半服务重启，job 状态可查、可重跑。

#### F8 如果只能保留一个指标，留哪个
**考察点**：指标优先级判断
**口播答案**：在线留 coverage，离线留 hit@k。理由：coverage 直接对应产品承诺——"每个薄弱点都被照顾到"，它掉了个性化就名存实亡；hit@k 是检索的第一性指标——找都找不到，排序、生成、忠实度全是空中楼阁。反过来说明我理解指标有依赖链：先有召回（hit），才谈排序（MRR），才谈生成质量（faithfulness）。
**追问链**：
- 追问：diversity 不重要吗 → 答法要点：重要但有代偿——去重机制在流程上保证了多样性下限，指标掉了有兜底；coverage 没有流程兜底，必须靠指标看护。

#### F9 在线指标异常了会发生什么
**考察点**：监控的闭环
**口播答案**：当前阶段是"可观测"：指标随出题记录落库，Dashboard 可看趋势，异常靠人看。没做自动告警和自动降级，因为单机自用阶段人肉回路够用——这是诚实的边界。规模化的路径很清楚：指标已经结构化入库，接告警只是加阈值规则；更进一步可以做自动降级（coverage 连续低走时自动放宽检索 top-k 或触发索引重建检查）。
**追问链**：
- 追问：为什么不现在就做告警 → 答法要点：告警没有值班人就是噪音；先把指标做准（我们连指标本身都重构过一次），再做响应机制，顺序不能反。

## 模块G：工程鲁棒性与部署

#### G1 简历上写了"多渠道 failover"，先说清楚一个渠道到底是什么，为什么要多渠道？
**考察点**：能否把"渠道"这个抽象讲成具体的接入点，并说清多渠道解决的真实问题
**口播答案**：一个渠道就是一组 LLM 或 embedding 的接入点，包含 api_base、一批 key 和模型名。我给 LLM、embedding、reranker 三类服务都做了多渠道。多渠道的核心价值是可用性：单一 key 会被限流 429，单一供应商会宕机会 5xx，配多个渠道后一个挂了自动切下一个，上层业务完全无感。我把它封装成一个叫 ResilientChatModel 的类，接口和 ChatOpenAI 完全一样，invoke、astream、bind_tools 都对得上，所以 LangGraph 节点和各路由不用改一行代码就获得了 failover 能力。
**追问链**：
- 追问：三类服务都多渠道，它们共用一套逻辑吗 → 答法要点：共用 channel_manager 的状态机和选择逻辑，按 section（llm/embedding/reranker）区分渠道池；状态机、冷却、key 轮询是通用的
- 追问：failover 对上层透明，那上层怎么知道现在用的哪个渠道 → 答法要点：正常路径不需要知道，这正是 drop-in 替换的意义；排障时通过日志和 get_health 只读接口观测渠道健康

#### G2 ⭐ 渠道失败后你怎么处理？讲一下冷却和恢复的完整过程。
**考察点**：断路器的状态机在渠道层的具体实现
**口播答案**：每个渠道维护一个状态：是否健康、连续错误数、冷却截止时间、key 轮询游标。一次调用失败就 error_count 加一，达到 3 次就把渠道标记为不健康并冷却 60 秒，冷却期间这个渠道不会被选中。关键在恢复：冷却 60 秒结束后，我不是直接完全信任它，而是把它的 error_count 故意设成"差一次就再次熔断"的值，让它变得可被选中，但只要再错一次就立刻重新冷却，直到真正成功一次才彻底清零恢复健康。这就是断路器的 HALF_OPEN 半开探活思想——给一次机会，但保持警惕。
**追问链**：
- 追问：为什么是 3 次错误、60 秒，而不是 1 次立刻熔断 → 答法要点：单次错误可能是瞬时抖动，立刻熔断会误伤健康渠道；3 次是容忍瞬时抖动和快速隔离故障之间的经验平衡，是可调参数不是理论最优
- 追问：一个渠道配了多个 key 怎么用 → 答法要点：key 轮询游标每次取下一个，(idx+1) % len，多个 key 分摊单渠道限流
- 追问：查询渠道健康状态会不会触发这个"复活"副作用 → 答法要点：不会，get_health 是纯读，内联计算可用性，不调用带副作用的 is_available；读不改状态是有意为之

#### G3 ⭐ 如果所有渠道都冷却了，一次请求会发生什么？
**考察点**：全故障边界，以及是否会崩溃
**口播答案**：渠道选择是优先级加两遍 tier 过滤。第一遍尊重 tier 过滤，选符合档位且健康的渠道；如果这个 tier 一个可用的都没有，第二遍降级到任意 tier 再找。如果两遍都找不到——也就是所有渠道都在冷却——LLM 路径会抛 RuntimeError，由前端兜底提示用户稍后重试，而不是静默返回一段空内容当作正常答案。对 embedding 这种高频依赖则不一样，它有独立的熔断器，熔断打开时直接返回零向量降级，写库时零向量会被过滤掉，让检索返回空上下文而不是崩溃。
**追问链**：
- 追问：为什么 LLM 全挂是抛错，embedding 全挂是返回零向量 → 答法要点：LLM 是用户当前请求的必要产物，没有就该明确失败；embedding 多用于后台向量化和检索增强，可以降级到空上下文让主流程继续
- 追问：两遍 tier 过滤会不会每次出题都刷一堆降级警告日志 → 答法要点：降级日志做了去重，避免每次都刷一行

#### G4 ⭐ embedding 为什么要单独配一个熔断器？和渠道冷却不是重复了吗？
**考察点**：熔断器和渠道 failover 的职责区分，为什么 embedding 特殊
**口播答案**：不重复，解决的问题不同。渠道 failover 是"这个接入点坏了换一个"，熔断器是"整个下游服务持续失败时主动断路快速拒绝，别让每个请求都去撞超时白等，还可能压垮正在恢复的下游"。embedding 被画像更新、向量检索、语义去重多处高频调用，影响面最大，所以我给它专门配了三态熔断器。三个状态：CLOSED 正常放行，成功还会让失败计数递减渐进愈合；连续 5 次失败转 OPEN，直接拒绝，调用方拿零向量兜底；60 秒后转 HALF_OPEN，只放行 2 个探测请求，2 个都成功才回 CLOSED，任一失败立刻回 OPEN 重新计时。
**追问链**：
- 追问：半开只放 2 个探测，为什么不直接全放开 → 答法要点：恢复瞬间全放开可能再次击穿把刚恢复的下游打垮；只放少量探测确认稳定再完全恢复
- 追问：这个熔断器会被并发访问吗，线程安全怎么保证 → 答法要点：计数器被两处并发改——任务队列 worker loop 和跑在 asyncio.to_thread 的工作线程，所以每个状态转移都用 threading.Lock 守护，否则更新会丢、熔断不确定触发
- 追问：熔断打开期间的任务丢了吗 → 答法要点：查询路径直接零向量降级；后台任务路径执行前先查熔断器，OPEN 就延迟重排不占 worker，等恢复再做

#### G5 ⭐ 为什么 embedding 要走后台队列，不能在请求里直接 await？
**考察点**：异步化的动机和队列设计
**口播答案**：因为大知识库建索引、画像向量重建可能耗时几十秒，卡在 HTTP 请求里会超时，embedding 服务一抖动还会拖垮在线请求，客户端一断开任务就丢了。所以我做了 fire-and-forget 后台队列：提交后立即返回，慢活后台慢慢干，前端轮询进度。队列是 asyncio.PriorityQueue，增量插入优先级最高、画像重建次之、全量重建最低，小而急的活先做。还有任务去重，同一个用户和主题的重建正在飞时，重复提交是 no-op；失败按 2 秒 4 秒 8 秒指数退避重试，封顶 30 秒；两个 worker，队列上限 100，满了丢弃并计数。
**追问链**：
- 追问：重试的退避等待怎么实现，直接在 worker 里 sleep 吗 → 答法要点：绝不能 sleep，那会钉住 worker 饿死其他任务；把"延迟后重新入队"分离成独立的后台协程，worker 立即返回处理别的活
- 追问：重新入队用阻塞 put 还是 put_nowait → 答法要点：用 put_nowait，队满就丢弃；如果用阻塞 put，worker 在队满时 await put 会和"队列消费需要 worker"形成死锁
- 追问：后台任务失败会不会影响主进程 → 答法要点：不会，任务失败被隔离，绝不让主进程崩溃

#### G6 流式请求失败时，你能像非流式那样切换渠道重试吗？
**考察点**：两阶段流式 failover，一致性优先的取舍
**口播答案**：不能无条件切。流式的难点是内容已经吐给用户了。我做了两阶段：拉第一个 chunk 之前出错，用户还没看到任何字，可以安全切渠道重试；但第一个 chunk 一旦 yield 出去，就绝不能再切了——否则会把另一个渠道的完整新答案拼接到已经吐出的半截答案后面，用户看到两段重复甚至矛盾的内容。所以首 chunk 之后的错误直接抛给调用方，由调用方决定怎么呈现已经流出的部分。这是个有意的取舍：一致性优先于"看似无缝"的错误拼接。
**追问链**：
- 追问：那首 chunk 后失败用户体验不就断了吗 → 答法要点：是的，但断在明确的位置好过拼出一段错乱内容；正确做法是前端提示中断并给重试入口，生产级还可以做断点续传协议
- 追问：这个"首 chunk 后不能切"和 SSE 的关系 → 答法要点：SSE 是单向推送，token 已发即已提交，无法回滚，这正是流式 failover 提交点必须在首 chunk 前的根本原因

#### G7 哪些错误应该切渠道，哪些不该？
**考察点**：错误分类，避免用配置错误污染所有渠道
**口播答案**：不是所有错误都该切渠道，这是 failover 的灵魂。致命配置错误——400、401、403、404、422，比如 key 错、模型名错、参数非法——直接抛不切，因为换渠道也救不了，切了还白白把所有渠道都冷却。瞬时错误——408、409、429、5xx、网络错误、超时——先在同渠道重试 2 次、1.5 秒退避，还不行再切下一个。特别要说 429 是限流，不算致命，换个渠道或 key 就能继续，值得 failover，这是它和其他 4xx 的关键区别。判断状态码时我会顺着异常链的 __cause__ 和 __context__ 往里找，因为 LangChain 把 openai 和 httpx 的异常包了好几层。
**追问链**：
- 追问：如果一个错误 prompt 触发了 400，你没做这个区分会怎样 → 答法要点：每个渠道试一遍都 400，把全部渠道打进冷却，之后正常请求也没渠道可用，一个坏 prompt 拖垮整个池
- 追问：同渠道重试为什么是 2 次而不是无限 → 答法要点：无限重试放大故障和成本；有限重试处理瞬时抖动，仍失败就交给 failover 和熔断

#### G8 ⭐ 画像更新里有 LLM 调用要几十秒，并发更新同一个用户画像会不会互相覆盖？
**考察点**：长耗时计算与短临界区分离的并发一致性
**口播答案**：会，如果处理不当就是典型的旧快照覆盖新数据。我用两段式并发控制解决：第一段在锁外读取画像快照并调用 LLM，这几十秒不占锁，不阻塞其他请求；第二段在锁内重新读取最新画像，只执行已经解析好的结构化操作。关键细节是 LLM 返回的操作里带的是数组索引，我不直接信任这个索引去改列表——因为并发下列表可能已经变了、索引会漂移——而是通过快照里的原始文本重新映射到最新列表的对应项。文件保存用临时文件写完再原子替换，避免半写入损坏。
**追问链**：
- 追问：为什么全程持锁会怎样 → 答法要点：把几十秒的模型调用放进临界区，严重阻塞同一用户的所有并发请求
- 追问：per-user 锁在多进程/多实例下还成立吗 → 答法要点：不成立，threading.Lock 只在单进程有效；多实例要换文件锁或迁移到数据库事务/乐观锁，这是当前单 worker 部署的已知边界
- 追问：LLM 返回非法 JSON 合并失败怎么办 → 答法要点：降级到确定性路径——用 embedding 把新薄弱点和已有的做语义匹配，相似就更新次数，不相似就新增，embedding 也失败就当新事实处理，绝不让整次画像更新失败

#### G9 ⭐ 多用户数据是怎么隔离的？会不会 A 用户查到 B 用户的数据？
**考察点**：per-user 隔离的多个层次，纵深防御
**口播答案**：隔离是多层的。第一，user_id 来自 JWT 认证依赖，是服务端从 token 解出来的，不允许客户端或模型传入。第二，文件路径统一由 config.py 的 helper 从 data/users/{user_id} 派生，任何写用户数据的功能都必须调这些 helper，不能手拼路径。第三，SQL 查询都带 user_id 条件，索引也建成 (user_id, ...) 复合索引。第四，Docker 版 Qdrant 里知识库按 kb_{user}_{topic} 分 collection 物理隔离，长期记忆是单 collection 但用 payload 的 user_id 过滤。第五，Assistant 工具执行时注入认证 user_id，session、图片、文件接口再校验一次资源归属。
**追问链**：
- 追问：怎么防路径穿越，比如上传文件名带 ../../ → 答法要点：文件名取 basename、限扩展名和大小，resolve 之后验证目标仍在用户根目录内；user_id 本身也校验格式，只接受 8 位或 32 位十六进制，拒绝畸形 id 当路径用
- 追问：为什么 user_id 要限定 8 或 32 位十六进制 → 答法要点：老账号是 8 位，新账号用完整 32 位 uuid/hash 避免用户量上来后生日碰撞；同时这个正则校验本身就是路径穿越的第一道防线
- 追问：全局的 AI 渠道配置谁能改 → 答法要点：渠道池是全局的不是 per-user，用 require_owner 限制只有 owner 账号能改，否则任何注册用户都能改所有人的 LLM 配置或把流量指向恶意端点

#### G10 JWT 用的什么算法？为什么是 HS256 不是 RS256？如果密钥泄漏了怎么办？
**考察点**：认证设计的取舍和事故响应
**口播答案**：用的 HS256 对称签名，7 天过期，密码用 bcrypt 哈希。选 HS256 是因为这是单体应用，签发和验证都在同一个后端进程，用一个共享密钥最简单够用；RS256 的非对称价值在于多个服务各自验证、签发方和验证方分离，当前架构没这个需求，引入公私钥对是过度设计。如果 JWT_SECRET 泄漏，任何人都能伪造任意用户的 token，所以事故响应是立刻轮换 JWT_SECRET——因为是对称密钥，换掉后所有已签发的 token 立即失效，相当于强制全员重新登录。
**追问链**：
- 追问：轮换密钥会不会误伤正常用户 → 答法要点：会让所有人被登出重新登录，这是可接受代价；泄漏场景下宁可全员重登也不能让伪造 token 继续有效
- 追问：什么情况下你会考虑换成 RS256 → 答法要点：拆成多服务、有独立的认证中心签发、各业务服务只需验证不需签发时；那时用私钥签、公钥验，业务服务拿不到签发能力更安全
- 追问：bcrypt 有什么要注意的坑 → 答法要点：bcrypt 有 72 字节输入上限，超长密码要显式拒绝或截断，我在哈希和校验前都做了字节长度检查

#### G11 登录接口有没有防暴力破解？你的限流是怎么做的？
**考察点**：限流实现，以及它和单 worker 假设的绑定
**口播答案**：有，登录和注册接口都有滑动窗口限流。实现是进程内的内存限流器，和当前单 worker 部署是匹配的。有两种用法：注册是基于尝试计数的，每次调用都记一次；登录用的是基于预约的机制——密码校验期间先在相关的限流桶里预约一个带唯一 token 的事件，登录成功后凭这个 token 精确释放自己那一次预约，这样并发的多个登录请求预约同一个桶也不会互相误释放。窗口默认 15 分钟，桶数上限 1 万，满了按 LRU 淘汰。
**追问链**：
- 追问：进程内限流的最大问题是什么 → 答法要点：多 worker 或多实例下每个进程一套桶，实际限流额度被放大成 N 倍，形同虚设；扩容时必须换成 Redis 这种共享存储
- 追问：为什么登录要用预约-释放而不是简单计数 → 答法要点：登录成功不该占用失败配额；预约保证密码校验期间也算在飞的请求数，成功了精确退还，失败了才留下计数
- 追问：这套东西能防分布式撞库吗 → 答法要点：按 key（IP/账号）限流能挡单点暴力，但分布式撞库要配合别的手段，比如验证码、账号级锁定、异常登录检测；限流不是银弹

#### G12 ⭐ 讲一下 Docker 部署的整体拓扑，哪些端口对外，哪些不对外？
**考察点**：部署安全边界，最小暴露面
**口播答案**：四个服务：frontend 是 nginx，backend 是 uvicorn 跑 FastAPI，加 redis 和 qdrant。对外只有一个入口——宿主的 TLS 反向代理终止 HTTPS 后，转发到只在宿主回环 127.0.0.1:9000 监听的 frontend nginx。backend 只 expose 8000 不映射宿主端口，仅由 frontend 通过 proxy 网络访问。redis 和 qdrant 只加入一个 internal 为 true 的 data 内部网络，完全没有宿主端口映射，连回环都不监听。所以 9000、8000、6333、6334、6379 都不能直接暴露公网，防火墙也只放行 80 和 443。backend 限内存 2G，redis 限 256MB 走 LRU 淘汰。
**追问链**：
- 追问：backend 挂了 ./data 整个目录，会不会绕过服务 API 直接读 qdrant/redis 的持久化文件 → 答法要点：会，所以 backend 用只读 tmpfs 把 /app/data/qdrant 和 /app/data/redis 遮罩掉，强制走服务 API，不让它读别人的底层存储文件
- 追问：启动顺序怎么保证 → 答法要点：backend 等 redis healthy 才起，frontend 等 backend healthy 才起；backend 健康检查是访问 /docs
- 追问：qdrant 为什么不等它 healthy → 答法要点：qdrant 是 distroless 镜像没 shell/curl 配不了 exec 健康检查，用 service_started；而且 backend 是 qdrant-only 但连不上时检索降级空上下文不崩，所以不强制等它 ready

#### G13 ⭐ compose 里向量后端默认走 Qdrant，如果 Qdrant 连不上，为什么不自动降级回本地 numpy？
**考察点**：qdrant-only 不静默降级的数据一致性取舍
**口播答案**：这是有意的设计。裸 uvicorn 本地开发默认 numpy，但 Docker 部署给 backend 注入了 VECTOR_BACKEND=qdrant，是 qdrant-only，连不上也不静默切回 numpy。原因是静默切换会产生两套数据真相——Qdrant 里有一份索引，本地又建一份，之后 Qdrant 恢复了，两边数据就永久分叉，而且用户看到的是"看起来成功"的陈旧结果，这种不一致最难排查。所以我的取舍是：功能降级但不污染数据——Qdrant 不可用时检索返回空上下文，照常出题，同时委派后台重试重建，服务本身不崩。要退回本地必须显式设 VECTOR_BACKEND=numpy，是运维的明确决定，不是系统偷偷做的。
**追问链**：
- 追问：知识库和长期记忆在 Qdrant 里隔离方式一样吗 → 答法要点：不一样，知识库按 kb_{user}_{topic} 分 collection 物理隔离，因为每用户自定义文档不能混；长期记忆是单 collection 加 payload user 过滤，因为每用户记忆规模小，统一 collection 更好管理
- 追问：返回空上下文，用户不就拿到质量差的题了吗 → 答法要点：是降级不是无损，题目会少了知识库这层上下文，但仍有画像和领域状态两层，比返回错误或崩溃好；后台重建完成后下一轮恢复
- 追问：换了 embedding 模型维度变了，Qdrant 里的旧向量怎么办 → 答法要点：检测到维度不匹配触发全量重建；invalidate_singletons 会级联失效向量后端、Qdrant 维度缓存和 LlamaIndex 全局 Settings，避免混维度 cosine 崩溃

#### G14 SQLite 用了什么配置保证并发下不出问题？一共多少张表？
**考察点**：SQLite 生产化配置的细节
**口播答案**：几个关键配置：开 WAL 模式让读写可以并行，synchronous 设 NORMAL 平衡持久性和性能，busy_timeout 设 5 秒——等锁最多等 5 秒而不是直接报 database is locked。连接是线程本地的，每个线程持有独立连接，避免多线程共用一条连接导致锁定和状态污染，连接坏了会自动重建。所有业务表都在一个 interviews.db 里，大概十六七张——用户、会话、收藏、算法卡、live_sessions、assistant 聊天、记忆向量、题目 embedding、QA 会话和消息、RAG 在线指标、RAG 离线评测 run、知识训练卡、审计日志，还有几张幂等和迁移用的表。LangGraph 的 checkpoint 是独立的 checkpoints.db，和业务库分开减少锁竞争。
**追问链**：
- 追问：为什么 checkpoint 要单独一个库 → 答法要点：checkpoint 写入频率和业务表不同，分库减少和会话/评分等业务写入的锁竞争，也便于独立清理迁移；代价是产生跨库一致性问题，需要幂等同步
- 追问：WAL 在多进程下够用吗 → 答法要点：WAL 支持单机多线程读写并行，但多实例多进程高并发写仍是瓶颈，那时该换 PostgreSQL
- 追问：审计日志里会记 API key 或密码吗 → 答法要点：绝不记，audit_logs 的 detail 是 JSON，写入方只记事件名、计数、脱敏标识，永远不写密钥和密码原文

## 模块H：系统设计与扩展性

#### H1 ⭐ 现在是单机原型，如果要扩展到十万用户，你会先改哪三件事？
**考察点**：能否按瓶颈优先级排序，而不是罗列一堆
**口播答案**：按优先级，前三件是：第一，用 PostgreSQL 替换业务的 SQLite 和 LangGraph 的 checkpoint SQLite，因为单文件写锁是多实例扩展的第一道墙。第二，把进程内的东西外置到 Redis——session、缓存、限流都得共享，否则多 worker 下限流形同虚设、缓存各存各的。第三，把进程内的 embedding 队列换成 Celery、RQ 这类分布式任务队列，让后台重建能跨实例调度。做完这三件，FastAPI 才能真正无状态化、水平扩容。再往后是简历和图片放对象存储、Qdrant 集群化分片、全链路 trace、多租户配额和计费。
**追问链**：
- 追问：为什么 SQLite 是第一个要改的 → 答法要点：SQLite 是单写者模型，WAL 只缓解不解决，多实例同时写会锁竞争；而且它是本地文件，多实例根本没法共享同一份，是水平扩展的硬约束
- 追问：这三件的顺序能调换吗 → 答法要点：数据库必须先行，因为 Redis 外置 session 和队列外置都依赖"应用能无状态化"，而无状态化的前提是共享数据库；顺序反映依赖关系不是随意排的
- 追问：Qdrant 需要动吗 → 答法要点：Qdrant 本身就是独立服务、支持横向扩展，相对不那么急；十万用户主要是 collection 数量和分片规划的问题，比 SQLite 优先级低

#### H2 ⭐ 为什么说 SQLite 是第一瓶颈？WAL 不是已经支持并发了吗？
**考察点**：对 SQLite 并发模型的准确理解，不夸大 WAL
**口播答案**：WAL 支持的是"多读一写"并行——读的时候不阻塞写、写的时候不阻塞读，这在单机中低并发下很好用。但它本质还是单写者：同一时刻只有一个写事务，写多了就排队，busy_timeout 到了就报锁错。更根本的问题是 SQLite 是嵌入式的本地文件数据库，多个应用实例跑在不同机器上，根本没法安全地共享同一个文件——网络文件系统上的 SQLite 锁是出了名的不可靠。所以它卡的不是"读并发"，是"写并发"和"多实例共享"这两件扩展必须的事。PostgreSQL 是独立的多写者服务，天然解决这两点。
**追问链**：
- 追问：迁移到 PG 有什么要提前准备的 → 答法要点：先有 Repository 抽象把 SQL 收口、Schema 版本管理、数据回填脚本；当前 storage 层已经是按表分仓库的结构，迁移面比散落各处的裸 SQL 小
- 追问：迁移期间怎么保证不丢数据 → 答法要点：双写或停机窗口迁移，配合校验对账；checkpoint 库也要一起迁，否则面试恢复会断

#### H3 单进程 uvicorn 换成多 worker，哪些地方会立刻出问题？
**考察点**：识别所有进程内状态，这是最能暴露理解深度的问题
**口播答案**：所有进程内状态都会出问题。第一，限流器是进程内内存桶，多 worker 下每个进程一套，实际限流额度被放大 N 倍。第二，Redis 不可用时降级的内存 LRU 缓存各存各的，命中率掉、还可能不一致。第三，embedding 后台队列是进程内的 asyncio 队列，多 worker 会各跑各的队列，任务去重失效，同一个重建可能被多个进程重复做。第四，画像更新的 per-user threading.Lock 只在单进程有效，跨进程并发更新又会回到旧快照覆盖新数据。第五，LangGraph 的 checkpoint 虽然落 SQLite，但多 worker 抢写会加剧锁竞争。所以多 worker 不是加个参数那么简单，得先把这些状态外置。
**追问链**：
- 追问：这些里哪个最危险 → 答法要点：画像并发覆盖和限流失效最危险——前者丢用户数据，后者让暴力破解防线失效；缓存不一致相对可容忍
- 追问：最小改动让它先能多 worker 跑起来 → 答法要点：限流和锁迁 Redis、队列迁外部任务系统、缓存迁 Redis；本质就是 H1 说的那三件事

#### H4 ⭐ 怎么控制 LLM 成本？
**考察点**：成本意识的系统性，不是单点技巧
**口播答案**：多个层次。第一，大小模型 tier 路由——逐题独立评分、抽取、分类这种发给便宜的小模型并发跑，最后整体总结才用强模型，而不是所有步骤都上最强模型。第二，固定系统前缀利用 prompt cache——简历、知识库、画像在初始化时组成字节一致的固定前缀，命中缓存的模型能省首段成本。第三，上下文预算 ContextBudget，按优先级装配，超预算就压缩、截断或丢弃低优先级段，不把全部历史原文重复发。第四，RAG 只取有限 chunk，embedding 和 reranker 结果都缓存。第五，后台任务去重合并，避免重复 embedding。生产化还应该记录每场会话的 token 和成本，按用户设配额。
**追问链**：
- 追问：小模型评分会不会不准 → 答法要点：逐题评分是相对结构化的任务，小模型够用；真正需要综合判断的整体总结才上大模型，这是按任务难度分配算力
- 追问：prompt cache 命中的前提是什么 → 答法要点：前缀字节必须完全一致，所以固定部分和变化部分要分开拼，变化的阶段和已问题目追加在后面，不能插在前缀中间破坏缓存
- 追问：截断从哪里截 → 答法要点：尽量落在段落、换行、句子边界，避免从 JSON 或 Markdown 结构中间截断产生坏数据；用 tiktoken 算 token，不可用才回退字符估算

#### H5 如果要把它改成多 Agent 系统，你会怎么拆？值得拆吗？
**考察点**：对多 Agent 的清醒判断，不为概念强拆
**口播答案**：真要拆，可以拆成面试官 Agent 负责追问、评分 Agent 独立评分、记忆 Agent 负责画像合并、安全审查 Agent 做最终审查。但我的判断是当前场景不值得拆。多 Agent 会引入通信 token 开销、状态一致性问题、循环和错误定位成本。而我现在用外层状态机和流水线保证流程边界、用不同模型 tier 做职责分离，已经实现了"职责分工"这个多 Agent 想要的核心收益，没必要为了概念强拆。只有当某个角色真的需要独立的上下文、独立的权限或有并行价值时，拆分才划算。
**追问链**：
- 追问：拆成多 Agent 最难解决的是什么 → 答法要点：共享状态 schema 和冲突仲裁——多个 Agent 改同一份画像谁说了算、超时怎么传播、trace 怎么串起来定位问题
- 追问：那你现在的评分和面试算不算已经"分离"了 → 答法要点：算逻辑分离但不是自治 Agent 分离——评分是节点内的确定性链路和 LLM 调用，不是一个会自己决策下一步的独立 Agent，讲的时候要说准

#### H6 ⭐ 十万用户下 Qdrant 需要动吗？知识库按用户分 collection 会不会 collection 爆炸？
**考察点**：向量库的多租户规模化，识别当前隔离方案的规模边界
**口播答案**：会是个真问题。当前知识库按 kb_{user}_{topic} 分 collection，隔离干净，但十万用户乘每人多个主题，collection 数量会膨胀到几十万级，Qdrant 管理这么多 collection 的元数据和资源开销会成为瓶颈。所以规模化时要重新做租户规划——大概率改成少量共享 collection 加 payload 的 user_id/topic 过滤，就像现在长期记忆那样，用 payload 索引替代物理 collection 隔离，再按 tenant 做分片。长期记忆本来就是单 collection payload 过滤，那套模式反而更容易横向扩展。
**追问链**：
- 追问：共享 collection 加 payload 过滤，隔离性会变弱吗 → 答法要点：物理隔离变成逻辑隔离，要靠 payload 过滤严格性和索引保证；好处是 collection 数可控、便于分片，代价是过滤条件写错就可能串数据，要有测试兜底
- 追问：为什么当前不直接用共享 collection → 答法要点：当前是单机小规模，按用户主题分 collection 隔离最清晰、排查最直观；这是规模决定方案，不是一开始就该上复杂方案

#### H7 SSE 长连接在多实例、有负载均衡的环境下会有什么新问题？
**考察点**：把流式从单机推到分布式的认知
**口播答案**：几个新问题。第一，SSE 是长连接，负载均衡要支持会话保持或至少不要中途切后端，否则流断了。第二，当前 SSE 事件不持久化，连接一断已经生成的部分就丢了，用户刷新得从头来；规模化要做事件持久化加 last-event-id 断线续传。第三，各层超时要协同——现在后端 httpx read 设 360 秒故意比 nginx 的 300 秒高一层，让超时只由 nginx 一层兜；加了负载均衡后 LB 的空闲超时也得纳入这个链条，心跳 ping 间隔必须小于链路上最短的那个空闲超时。第四，长连接占资源，大量并发流对连接数和内存有压力。
**追问链**：
- 追问：心跳 ping 具体解决什么 → 答法要点：推理模型可能几十秒只输出 reasoning 不输出 content，nginx 或代理会当空闲连接关掉；定时发 ping 保活，reasoning 阶段还发"思考中"进度但不泄露原始思维链
- 追问：为什么不用 WebSocket → 答法要点：当前主要是服务端单向推 token，用户输入仍走普通 HTTP，SSE 更简单、能自动重连、易穿代理；要双向实时交互才需要 WebSocket

#### H8 ⭐ 假设某个 LLM 供应商突然全线 429，你的系统会怎么表现？会雪崩吗？
**考察点**：把前面的鲁棒性机制串起来应对真实故障，级联失败防护
**口播答案**：不会雪崩，因为有几层护栏叠加。429 被归类为可重试，先在同渠道退避重试 2 次；还不行 failover 切到别的供应商渠道；如果配了多个供应商，这里就切走了。如果所有渠道都是这家供应商全挂了，渠道 3 次错误后进 60 秒冷却，请求快速失败抛错而不是每个都干等超时。embedding 侧独立熔断器 5 次失败就 OPEN，直接零向量降级不再发请求，避免几百个请求一起撞墙把恢复中的服务再压垮。后台任务执行前查熔断器 OPEN 就延迟重排不空转。60 秒后半开放 2 个探测试水，确认好了才恢复。整个链条的设计原则就是快速失败优于慢慢挂、降级优于崩溃。
**追问链**：
- 追问：如果只配了单渠道单供应商呢 → 答法要点：没法 failover，但同渠道重试加冷却加熔断仍能防止请求风暴，只是功能会降级；这也是我强调多渠道是可用性基本保障的原因
- 追问：熔断打开期间用户请求怎么办 → 答法要点：LLM 主路径抛错前端提示重试；embedding 依赖的检索降级空上下文，出题少一层上下文但不崩

#### H9 你怎么判断个性化和 RAG 改造到底有没有效果，而不是自我感觉良好？
**考察点**：评测意识，区分在线离线两套体系
**口播答案**：我做了两套刻意分开的指标。在线的 rag_metrics 在真实出题链路上，零 LLM 成本，算相关性、覆盖率、多样性，没有 ground truth，主要用来发现召回质量突然退化。离线的 rag_eval 是 RAGAS 风格基准，从知识库合成 golden set，算 hit@k、MRR、precision、recall，再用 LLM judge 算 faithfulness、answer relevancy、correctness。个性化效果则用对照——personalized 对 topic-only 对 random baseline，比薄弱点覆盖率、难度分布和目标的 KL 散度、题目多样性和 judge 质量。关键是这两套指标数值范围天然不同，不能用一个全局阈值横比，每个指标按自己的 band 上色。
**追问链**：
- 追问：为什么不能只信 LLM judge → 答法要点：LLM judge 有位置偏差、模型偏好、不可复现；要和确定性指标、embedding 指标、人工抽检结合，不能用单一分数证明效果
- 追问：在线指标高就代表答案准吗 → 答法要点：不代表，在线没有 ground truth 只是代理指标，只适合异常检测和相对比较，不能当真实准确率
- 追问：离线评测能替代线上验证吗 → 答法要点：不能，离线证明检索和生成质量，真实学习效果还要靠线上 A/B 和真实用户留存；当前离线评测不能替代生产实验，这点要如实说

#### H10 这个项目现在最大的技术债是什么？
**考察点**：诚实的自我评估，给演进路线而非回避
**口播答案**：诚实说三点。第一，SQLite、进程内文件锁和进程内队列限制了多实例扩展，这是架构层面的规模天花板。第二，自动化测试覆盖不足，LLM 和 embedding 的集成测试依赖外部服务，现有单测主要覆盖纯函数和局部逻辑，还有个已知的 SM-2 测试契约没同步。第三，真实用户的长期学习效果还没通过线上实验验证，现在都是离线评测。但每一点我都有改进方向：数据库和队列按十万用户那套演进路线走，测试补契约测试和迁移测试进 CI，效果验证上线上 A/B。给出改进顺序比只说"没有技术债"可信得多。
**追问链**：
- 追问：那个 SM-2 测试契约问题具体是什么 → 答法要点：旧测试假设 repetitions=2 再来一次高分就毕业，但实现已收紧成独立的 consecutive_high 连续高分计数，旧状态没有 last_score 证据时只算第一次高分；这是测试没跟上业务契约的债，不是算法错，修法是补 legacy 迁移测试和断连重置测试
- 追问：为什么测试覆盖不足 → 答法要点：LLM/embedding 集成测试要么打真实 API 不稳定不可复现，要么 mock 得失真；这是 LLM 应用测试的普遍难点，正确方向是把确定性逻辑和模型调用解耦后分别测

## 模块I：开放性与行为面

#### I1 ⭐ 这个项目你最自豪的一个技术决策是什么？
**考察点**：能否讲出一个有取舍、有深度的决策，STAR 结构
**口播答案**：最自豪的是"按任务确定性选择编排范式"这个原则，而不是把所有东西都做成一个万能 Agent。Situation：市面上很多 AI 面试工具要么每次从零出题，要么盲目上一个 ReAct Agent。Task：我要让系统既有 Agent 的个性化和决策能力，又稳定可控。Action：我把简历面试做成 LangGraph 状态机因为它需要阶段、人在回路和恢复；专项训练做成 Agentic Workflow 因为步骤稳定要可观测和质量门控；只有学习助手做成 Function Calling Agent 因为意图开放。核心是确定性越强的部分越交给程序，只有真正需要语义判断的局部才交给模型。Result：整个系统的成本、延迟、权限、停止条件和失败恢复都可控，而不是把不确定性甩给一个自由 Agent。
**追问链**：
- 追问：这个决策有没有让你放弃一些"更酷"的东西 → 答法要点：放弃了"全自治 Agent"的叙事，但换来了可控和可测；我认为 Agent 工程的重点不是把更多决策交给模型，而是建立清晰的状态、工具、权限和失败边界
- 追问：如果面试官就想看多 Agent 呢 → 答法要点：我会诚实说这是单 Agent 加受控工作流，并解释为什么当前场景强拆多 Agent 是负收益，同时给出真要拆会怎么拆——这比包装成多 Agent 更可信

#### I2 ⭐ 讲一个你在这个项目里发现并修复的最隐蔽的 bug。
**考察点**：深度排查能力，STAR，用真实修复
**口播答案**：Situation：我在做一次深度代码审查时，盯着 SSE 流式的 helper 看。Task：想确认失败路径是不是真的安全。Action：我发现 stream_llm_sse 这个流式辅助函数失败时，只往前端发一个 SSE error 事件，但对调用方没有产生任何"这次失败了"的信号——它返回的还是空字符串。顺着往上追，有三处调用方会把这个空字符串当成正常结果破坏性地持久化，最严重的一处会直接把知识库的 README.md 清空。这是最隐蔽的那种 bug：没有报错、没有异常，数据静默损坏。Result：我给这个 helper 加了显式的 error 信号，让它明确返回失败，再给全部 8 处调用方加了中止守卫，失败就不写、不覆盖。
**追问链**：
- 追问：你怎么会想到去查这个的 → 答法要点：我做审查时对每个外部依赖都问"它失败了会怎样"；流式调用尤其危险因为它可能吐了一半就断，空结果和正常空返回难区分
- 追问：为什么一开始会写成这样 → 答法要点：简化重构时去掉了一些防御层，但流式失败信号这个语义没补上；教训是失败信号必须是显式的返回值而不是靠副作用发事件，调用方才拦得住
- 追问：改完怎么验证 → 答法要点：构造失败场景确认调用方不再写空值、README 不被清空；本质是让"失败"变成一个调用方无法忽略的返回契约

#### I3 ⭐ 再讲一个和状态一致性有关的 bug。
**考察点**：并发/状态清理类问题，STAR
**口播答案**：Situation：会话删除功能。Task：确认删除一个训练会话后系统状态是干净的。Action：我发现删除会话后，live_sessions 这个存瞬时会话状态的地方有残留——数据库里的会话记录删了，但内存里和 live_sessions 表里的对应状态没清。结果是一个已经被删除的会话居然还能被继续对话，因为对话走的是残留的 live 状态，不查已删除的主记录。这是典型的多处状态没同步清理。Result：我把清理改成同一个事务里一起做——删主记录、删 live_sessions、驱逐内存里的 live 状态，保证删除是原子且彻底的。
**追问链**：
- 追问：为什么会漏掉内存那份 → 答法要点：live_store 是内存 TTLDict 存瞬时流式缓冲，容易被当成"反正 2 小时会过期"而忽略；但用户能立刻感知到"删了还能聊"，所以必须显式驱逐不能等 TTL
- 追问：同事务清理保证了什么 → 答法要点：保证要么全删要么全不删，不会出现主记录删了 live 还在的中间态；数据库部分原子，内存驱逐紧跟成功提交后做

#### I4 embedding 相关的问题里，有没有那种"切换配置后静默失效"的坑？
**考察点**：配置变更的级联失效意识，STAR
**口播答案**：有，而且很隐蔽。Situation：系统支持运行时热切换 embedding 模型。Task：确认切换后所有依赖 embedding 的东西都跟着更新。Action：我发现难度锚点的缓存不随 embedding 模型切换失效。难度校准是用已标注难度的锚点做 k-NN，锚点向量是用旧 embedding 算的。切换模型后，锚点缓存还是旧向量，但新题目的 embedding 是新模型算的，两套向量空间不兼容，难度校准就静默失效了——不报错，只是校出来的难度是错的，一直错到进程重启才因为缓存重建而恢复。Result：我把难度锚点的失效挂进了 invalidate_singletons 的级联链，并加了维度守卫，换模型时锚点缓存一起失效重建。
**追问链**：
- 追问：invalidate_singletons 还级联失效什么 → 答法要点：向量记忆后端单例、知识库 Qdrant 的 client 和维度缓存、LlamaIndex 全局 Settings 的 llm 和 embed_model；核心是换 embedding 维度时所有缓存的维度假设必须一起失效，否则混维度 cosine 崩溃
- 追问：为什么静默失效比崩溃更可怕 → 答法要点：崩溃看得见会立刻修；静默失效数据悄悄变错，用户拿到错误难度还以为正常，发现时可能已经污染了一批画像和复习计划

#### I5 ⭐ 你怎么和 LLM 的不确定性共处？举例说明。
**考察点**：LLM 应用工程的核心心法
**口播答案**：核心心法是明确划分边界——让模型做它擅长的语义判断，确定性的东西坚决用程序算。举三个例子。第一，掌握度不交给 LLM，用固定的 EWMA 公式算，因为分数需要稳定、可解释、可回归测试；LLM 只负责从多段评价里抽取共同薄弱点这种语义活。第二，出题时模型负责候选生成，程序负责质量门控——生成完还要过覆盖率、语义重复、难度分布三个 validator，坏题只局部重生成最多一轮。第三，模型自报的难度 1 到 5 我不信，用标注锚点做 k-NN 校准，因为不同模型对"难度 3"的尺度不一样。本质是我不指望模型每次都对，而是给它的每个输出都加确定性的校验和兜底。
**追问链**：
- 追问：那模型输出非法 JSON 这种呢 → 答法要点：安全解析加默认值加计数兜底，比如面试推进不完全靠 LLM 评价，还有最低采样数和每阶段硬上限；解析失败就走确定性路径不让会话终止
- 追问：validator 自己出错了呢 → 答法要点：单个 validator fail-soft，不中断整条生成链路，坏的那个校验跳过而不是整批题作废
- 追问：这套思路的代价是什么 → 答法要点：代码更复杂，要为每个失败路径写兜底；但这正是玩具 demo 和能上线系统的分水岭

#### I6 如果这个项目让你重来一次，你会改哪些设计？
**考察点**：反思能力，识别真实的设计遗憾
**口播答案**：主要三点。第一，测试策略从一开始就该把确定性逻辑和 LLM 调用解耦，让核心算法能脱离外部 API 单测；现在集成测试依赖真实服务，覆盖率上不去，那个 SM-2 契约债也是这么欠下的。第二，状态清理和失败信号应该从设计初期就定成显式契约，而不是后来审查才发现 SSE 空结果和会话残留这类静默问题——如果早定"失败必须是返回值、删除必须原子"，这些 bug 根本不会出现。第三，一些启发式参数比如 EWMA 权重、去重阈值，当初该配套建立标注集和评测流程，而不是先拍经验值再回头补校准。
**追问链**：
- 追问：这些遗憾里哪个影响最大 → 答法要点：测试解耦，因为它是其他问题的放大器——测试不到位，静默 bug 和参数漂移都更难被及时发现
- 追问：为什么当初没这么做 → 答法要点：原型期优先跑通闭环验证产品假设，工程严谨度是逐步补的；这是原型和产品的正常演进，但如果重来我会更早立这些契约

#### I7 ⭐ 这个项目里你觉得最有技术含量的部分，怎么向一个非技术的人解释？
**考察点**：表达能力，抽象到具象的转化
**口播答案**：我会这么说：市面上大部分 AI 面试工具就像一个每次都失忆的陪练，你练完它就忘了，下次还问一样的东西。我做的这个陪练有长期记忆——它记得你哪里老出错、哪些已经练好了、什么时候该复习，下次专挑你的薄弱点出题，难度还跟着你的水平走。技术上最难的不是让 AI 生成题目，那很简单，难的是让它像一个负责任的教练一样：记住的东西不能越记越乱、已经会的要及时放手、AI 偶尔犯浑给出烂题目时系统要能自己发现并纠正。我花最多精力的地方，是让这套东西在 AI 不靠谱的时候依然靠谱。
**追问链**：
- 追问：那"AI 不靠谱时依然靠谱"具体指什么 → 答法要点：切回技术语言——多渠道容灾、熔断降级、质量校验、确定性兜底，用一两个具体例子落地，比如供应商挂了自动切、模型给了重复题目系统自动查出来
- 追问：普通用户能感知到这些吗 → 答法要点：感知不到细节但感知得到结果——练得越久越懂你、很少崩、题目不会明显重复或离谱

#### I8 团队里有人说"直接上一个 GPT 全自动 Agent 就行了，你这套太复杂"，你怎么回应？
**考察点**：技术判断的沟通，能否有理有据地坚持或让步
**口播答案**：我会先认同他的出发点——简单确实有价值，然后用具体场景说明为什么这里不适合。全自动 Agent 的问题是把大量本该稳定的规则也交给了模型：阶段顺序、最大题数、评分持久化、用户隔离，这些一旦让模型自由发挥，就会有无限循环、权限失控、成本不可控、结果不可复现。我的做法是外层程序护栏、局部开放模型决策——需要语义判断的地方交给模型，确定性的地方程序兜死。这不是更复杂，是把复杂放在了对的地方。如果他能指出某个具体环节我过度设计了，我很乐意简化；但整体上，可控性在一个要持续影响用户训练计划的系统里，比"看起来更 AI"重要。
**追问链**：
- 追问：如果他坚持要试全自动版本 → 答法要点：可以在一个低风险模块小范围试点对比，用数据说话——比如比稳定性、成本、坏输出率，而不是靠嘴争
- 追问：有没有你后来发现自己确实过度设计的地方 → 答法要点：诚实举例，比如某些防御层在简化 pass 里被主动删掉了；我也会反向审视自己，不是所有复杂都值得

#### I9 ⭐ 面试官深挖你简历里"三态熔断器"，但当场你有个细节记不清了，你会怎么处理？
**考察点**：诚实边界，压力下的应对
**口播答案**：我会如实说这个具体数值我记不太准，然后讲我确定的部分和背后的原理。比如我会说：熔断器三个状态 CLOSED、OPEN、HALF_OPEN 的转移逻辑我很清楚——连续失败到阈值转 OPEN，冷却后转半开只放少量探测，探测成功才回 CLOSED；但失败阈值到底是 5 还是别的数、恢复时间具体多少秒，我需要看代码确认，因为这些是可调参数不是我硬背的。我绝不会当场编一个数字，因为如果编错了比说"记不清"更糟。工程上这些阈值本来就该是配置项、随压测调整，重要的是我理解为什么需要它、怎么转移、边界在哪。
**追问链**：
- 追问：那你简历上的数字都是真的吗 → 答法要点：结构性数字都是真的且能对到代码——5 阶段、每阶段 10 题硬上限、RRF k=60、去重阈值、14 天半衰期这些；效果类数字比如延迟降低百分比我不写，因为没有可复现的基准报告
- 追问：为什么这么强调不编数字 → 答法要点：项目里我最坚持的原则之一就是所有性能数字必须有真实测试证据，没有就不写；这是技术诚信，编一个当场被追问就穿帮

#### I10 用 90 秒讲清楚这个项目，让我记住它。
**考察点**：电梯陈述，结构和重点
**口播答案**：我做的是一个个性化面试训练 Agent，和普通面试问答产品最大的不同是跨会话闭环，不是一次性问答。每次训练后，系统把逐题表现转成两类信号：能算的——掌握度、SM-2 复习计划——用确定性公式更新；需要语义理解的——薄弱点、思维模式、沟通风格——用类 Mem0 的 ADD、UPDATE、IMPROVE 操作合并进长期画像，下一轮再围绕这些出题。编排上我按任务确定性分三种：简历面试用 LangGraph 状态机，可中断可恢复；专项训练用 Agentic Workflow，多路 RAG 加质量校验；学习助手用 Function Calling。底层做了多渠道 failover、embedding 熔断队列、SSE 心跳和上下文预算保证外部模型波动时的可用性。这个项目让我最深的体会是：Agent 的难点不是 prompt，而是状态、生成质量控制、记忆、评测和失败边界的系统化设计。
**追问链**：
- 追问：一句话说它到底解决什么 → 答法要点：解决普通 AI 面试工具"每次从零开始"的问题，让系统像有记忆的教练一样持续跟踪你的能力变化
- 追问：三个亮点如果只留一个 → 答法要点：留个性化闭环——训练结果不只展示给用户，而是回流去更新画像、记忆、复习调度和下一次出题，这是整个系统的主线价值

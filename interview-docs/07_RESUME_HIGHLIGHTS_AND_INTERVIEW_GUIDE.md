## 一、项目定位与面试口径

### 1. 一句话定位

SparkOffer 是一个面向技术岗位求职者的个性化面试训练 Agent。它不是一次性调用大模型生成题目，而是把简历、目标岗位、知识库、历史薄弱点、掌握度和遗忘曲线组织成跨会话闭环，让系统在每轮训练后更新用户能力模型，并据此调整下一轮的题目、难度与复习计划。

### 2. 技术栈

- 后端：FastAPI、LangGraph、LangChain、LlamaIndex、SQLite、Qdrant/numpy、Redis 可选缓存。
- 前端：React 19、TypeScript、Vite、Tailwind CSS、Recharts、SSE。
- 模型层：OpenAI-compatible LLM、Embedding、可选 Cross-Encoder Reranker。
- 工程能力：JWT 鉴权、用户数据隔离、持久化 Checkpoint、后台任务队列、熔断、渠道切换、离线评测和在线指标。

### 3. 必须讲清楚的 Agent 边界

这个项目包含两种 Agent 形态：

1. 面试训练主链路是“受控工作流 Agent”。LangGraph 和确定性路由掌握流程控制权，LLM 负责提问、分析和评价。
2. 浮窗助手是“单 Agent + Tool Calling”。模型可选择工具，但仍有最大循环次数、工具白名单和用户隔离。

它不是 Multi-Agent 系统。简历中不要写“多智能体协作”，否则面试官询问角色通信协议、任务分解、共享记忆、冲突仲裁时无法用当前代码支撑。

## 二、面向 Agent / AI 应用开发岗位的四条核心创新亮点

结合岗位方向，建议不要把 RAG、记忆和容灾分别都占成一条。它们相互依赖，容易让面试官听成“同一套个性化链路拆成三段”。更有区分度的四条主线应是：

1. **有状态 Agent 编排**：LangGraph 状态机、人在环、持久化恢复和流程护栏；
2. **可控的 10 道题生成 Pipeline**：规划、检索、混合生成、流式解析、质量校验、局部修复和难度校准；
3. **跨会话个性化学习闭环**：长期画像、确定性掌握度、向量记忆和 SM-2；
4. **知识训练场的知识产品化 Pipeline**：把非结构化 Markdown 转成有来源、可去重、可复习的训练卡片。

多渠道 Failover、熔断、上下文预算和 Reasoning-aware SSE 不再单独占一个产品亮点，而作为贯穿四条能力的“生产级工程底座”。如果目标 JD 特别强调高可用、模型网关或平台工程，可以用它替换第四条。

### 推荐亮点一：可恢复、有护栏的有状态面试 Agent

基于 LangGraph 将模拟面试建模为五阶段状态机，通过 `interrupt_before` 实现 Human-in-the-Loop，以 SQLite Checkpoint 持久化会话；结合 LLM 隐式评价、最小采样数、计数兜底和每阶段硬上限，使面试可动态追问、重启续接且不会死循环。

### 推荐亮点二：面向个体能力的 10 道题可控生成 Pipeline

将一次 Prompt 生成 10 道题拆成 `prepare → retrieve → generate → validate → finalize` 五阶段 Pipeline：根据薄弱点掌握度和到期复习项分配题目槽位，融合种子题库与 LLM 生成，边解析 JSON 边推送题目，并通过覆盖率、语义重复和难度分布校验器定位坏题，只局部重生成失败题目，最后用难度锚点校准模型自报难度。

这条对 Agent / AI 应用岗位非常有价值，因为它展示的不是“会调模型”，而是如何把不稳定生成变成可观测、可验证、可修复的工程流程。

关键实现：

- `prepare`：加载画像、薄弱点、SM-2 到期项，识别冷启动，并生成题目槽位计划；
- `retrieve`：按薄弱点执行多路 RAG，超时则空上下文降级，不缓存失败产生的空结果；
- `generate`：最多先从种子池选 6 题，LLM 只补剩余题目，降低成本和首题等待；
- 流式增量解析：每得到一个完整 JSON Object 就推送一道题，而不是等待完整数组；
- ID 修复：不信任模型或种子池原始 ID，服务端强制归一化为连续的 1～10；
- `validate`：校验薄弱点覆盖、题目语义重复和难度分布；
- 局部 Repair：只重生成被标记的坏题，最多修复一轮，避免整批重生成带来的成本和结果漂移；
- `finalize`：使用难度锚点做 k-NN 校准，再持久化题目和 RAG 指标；
- 冷启动：没有画像时使用独立诊断 Prompt，并跳过不适用的薄弱点覆盖校验。

典型边界：

| 问题 | 解决方案 |
| --- | --- |
| LLM 少生成或多生成题目 | 截断到目标数量；数量不足应显式标记，不能伪装成完整 10 题 |
| JSON 被包装成 `{"questions": [...]}` | 兼容 questions/data/items 外层包装 |
| 模型输出 `Q1` 等字符串 ID | 服务端覆盖为连续整数 ID |
| 种子题与 LLM 题重复 | Prompt 告知已覆盖角度，后续再用语义重复 Validator |
| Validator 自身异常 | 单个 Validator fail-soft，不中断整条生成链路 |
| Repair 后仍不合格 | 记录质量问题并有限放行，避免无限自修复循环 |
| 无画像冷启动 | 使用诊断型 Prompt，不强行做弱点覆盖校验 |
| RAG 索引尚未建立 | 后台排队重建，本轮使用空知识上下文继续生成 |

### 推荐亮点三：长期记忆与间隔复习驱动的个性化闭环

将训练结果拆成两类信号：LLM 负责 Extract/ADD/UPDATE/IMPROVE 语义合并，确定性代码负责 EWMA 掌握度、统计和 SM-2；配合向量记忆语义去重、14 天半衰期和连续 3 次高分毕业，使下一轮出题既利用历史弱点，又能让已掌握知识退出高优先级。

### 推荐亮点四：从知识文档到可追溯训练卡片的知识训练场

构建“Markdown 文档 → 语义章节 → 连贯抽样 → LLM 卡片生成 → 质量过滤 → 来源修复 → 持久化 → SM-2 复习”的知识产品化链路，将用户知识库直接转化为三档深度、带原文来源且可到期复习的训练卡片。

这不是普通的“让 LLM 总结文档”，其关键工程设计包括：

- 解析 Markdown 标题层级并保留 `filename + header_path` 来源；
- 忽略代码块内部以 `#` 开头的内容，避免把 shell 注释误识别成标题；
- 过滤冲刺计划、目录、碎片化列表等不适合训练的章节；
- 长纯文本自动切分，相关子章节尽量连续抽样，避免卡片上下文割裂；
- 记录已生成卡片的 Section，下一轮优先覆盖尚未训练的知识区域；
- 支持随机/高频模式、记忆/理解/应用等训练深度；
- LLM 输出经过字段完整性、内容质量和代码块感知过滤；
- `source_index` 优先于模型随意生成的错误 `source_refs`，所有引用必须能在候选章节中校验；
- 卡片 ID 由 topic、标题和来源计算确定性 Hash，重复生成使用 `INSERT OR IGNORE`，且不覆盖已有复习状态；
- 熟悉、模糊、不会分别映射为 9/6/2 分进入 SM-2，到期卡片自动进入复习队列；
- 使用 SSE 逐张推送卡片，模型失败、无可训练章节或解析为空时返回明确错误。

典型边界：

| 问题 | 解决方案 |
| --- | --- |
| Markdown 代码块中的 `#` 被当成标题 | 解析时跟踪 fenced code block 状态 |
| 抽到目录、计划或过短章节 | 章节质量评分与可训练性过滤 |
| 同一知识区反复生成 | 根据已覆盖的 `filename/header_path` 调整抽样 |
| LLM 编造来源 | 仅接受候选 Section 中存在的引用，否则回退到权威来源 |
| 同一张卡重复落库 | 确定性 ID + 主键去重 |
| 重复生成覆盖用户复习进度 | `INSERT OR IGNORE` 保留原有 SRS 状态 |
| 用户知识文档为空 | 返回可操作错误，引导先上传或生成知识库 |
| 卡片只有口号、碎片或缺字段 | Normalize 阶段拒绝低质量卡片 |

## 三、支撑上述亮点的底层能力深挖

## 底层能力 A：LangGraph 驱动的可恢复、有护栏的自适应面试 Agent

### 简历一句话版

基于 LangGraph 构建五阶段有状态面试 Agent，将自我介绍、技术问答、项目深挖和反问环节建模为状态机；结合 SQLite Checkpoint、Human-in-the-Loop 中断点、LLM 隐式评价和确定性硬上限，实现会话重启可恢复、阶段动态推进且避免死循环。

### 更精炼的简历 Bullet

- 设计 LangGraph 五阶段面试状态机，以 SQLite Checkpoint 持久化会话状态，通过 `interrupt_before` 等待用户输入，并采用“LLM 判断是否推进 + 问题数兜底 + 每阶段硬上限”三重护栏，保证长会话可恢复且不会无限追问。

### 为什么它不是普通 Chatbot

普通 Chatbot 通常只有消息历史，没有显式业务状态。当前项目把以下内容放进 `ResumeInterviewState`：

- 当前阶段 `phase`；
- 已提问题 `questions_asked`；
- 当前阶段问题数 `phase_question_count`；
- 是否结束 `is_finished`；
- 最近一次隐藏评价 `last_eval`；
- 全量评价历史 `eval_history`；
- 固定系统前缀、简历上下文和知识库上下文。

这样，流程推进不依赖模型“自己记得现在在哪一步”，服务重启后也能从 Checkpoint 恢复。

### 详细解决方案

#### 1. 状态机建模

面试阶段依次为：

```text
GREETING → SELF_INTRO → TECHNICAL → PROJECT_DEEP_DIVE → REVERSE_QA → END
```

LangGraph 节点包括：

- `init`：加载简历、知识库、长期画像，生成开场；
- `ask`：根据当前阶段和历史消息生成下一问；
- `wait`：在人机交互点暂停；
- `advance`：推进阶段；
- 条件路由：决定继续追问、推进或结束。

关键代码：`backend/graphs/resume_interview.py`、`backend/models.py`。

#### 2. Human-in-the-Loop

图使用 `interrupt_before=["wait"]` 编译。Agent 生成问题后，在 `wait` 节点前中断，等待用户回答，再恢复同一个 `thread_id/session_id` 的图状态。

这样做比在一个 HTTP 请求里用 `while` 等用户输入更合理，因为真实用户响应可能间隔数分钟，HTTP 请求不应该长期占用连接和执行栈。

#### 3. 持久化 Checkpoint

项目使用 `SqliteSaver` 将 LangGraph 状态写入独立的 `data/checkpoints.db`：

- `thread_id` 对应面试 `session_id`；
- SQLite 开启 WAL；
- `busy_timeout=5000`；
- `check_same_thread=False`，适配 `asyncio.to_thread`；
- Checkpoint 与业务库 `interviews.db` 分离，减少锁竞争。

边界：当前设计适合单机、低到中等并发。扩展到多实例时，虽然共享磁盘上的 SQLite 理论上可工作，但不适合高并发写入，应该切换 PostgreSQL/Redis 等共享 Checkpointer。

#### 4. LLM 隐式评价 + 确定性护栏

模型输出正文后附带隐藏标记：

```html
<!--EVAL:{"score":8,"should_advance":true,"observation":"..."}-->
```

服务端会：

- 取最后一个 EVAL 标记，避免模型在正文中误回显示例；
- 从用户可见正文中移除标记；
- 只接受字典；
- 将数值分数限制在 0～10；
- 非数字分数直接丢弃；
- 兼容 `observation → brief` 字段映射。

阶段推进不是完全交给 LLM：

- greeting 至少 1 问；
- self-intro、reverse-qa 有计数规则；
- technical/project 阶段至少问 2 题后才允许 LLM 建议推进；
- 达到配置的阶段问题数后强制推进；
- 每阶段还有 10 题硬上限，防止异常 prompt 或错误评价导致死循环。

#### 5. Prompt 前缀缓存与上下文预算

简历、知识库和长期画像在初始化时组成固定 `system_prompt`，后续每轮仅追加变化的阶段和已问题目。固定前缀保持字节一致，有利于支持 Prompt Caching 的模型命中缓存。

发送给模型的历史不是简单 `[:5000]` 截断，而是根据最小模型上下文窗口、最大输出预留和安全边界计算输入预算，优先保留最近消息。

### 这个亮点解决了什么问题

- 模型忘记业务阶段；
- 服务重启导致面试丢失；
- 模型错误判断导致无限追问或过早结束；
- 长会话超过上下文窗口；
- 每轮重复发送大段稳定上下文造成成本和延迟浪费。

### 常见错误与边界

| 问题 | 当前处理 | 仍需注意 |
| --- | --- | --- |
| EVAL JSON 格式错误 | 忽略评价，走计数兜底 | 不应因评价解析失败终止会话 |
| 用户在回答中伪造 EVAL | 服务端只解析模型响应，且校验类型和范围 | Prompt Injection 仍不能被“彻底消灭” |
| Checkpoint 与业务记录不一致 | 会话状态和业务记录分开保存 | 需要幂等同步和对账机制 |
| 同一 session 并发提交两次回答 | 当前缺少强分布式互斥 | 应增加 session 版本号或乐观锁 |
| 多 worker 共享 SQLite | 低并发可用，WAL 降低竞争 | 高并发应换共享数据库 Checkpointer |
| 模型返回空流或空内容 | 空流可结束，调用侧需提示用户 | 不应把空回答当有效题目沉淀 |

## 底层能力 B：Mem0 风格长期记忆 + 确定性掌握度 + SM-2 的个性化学习闭环

### 简历一句话版

设计跨会话个性化学习闭环：LLM 以 Extract/Update 两阶段合并长期画像，确定性算法计算主题与薄弱点掌握度，向量记忆进行语义去重和时间衰减，并通过改造 SM-2 调度复习，实现“训练—评估—画像更新—定向出题—到期复习”的持续进化。

### 更精炼的简历 Bullet

- 构建 Mem0 风格长期记忆系统，将 LLM 负责的语义合并与可解释的 EWMA 掌握度、SM-2 复习调度解耦；通过向量相似度去重、14 天半衰期和连续高分毕业机制，使历史薄弱点可累积、可衰减、可复习且不会无限膨胀。

### 核心设计思想：让 LLM 做擅长的事，让算法做必须稳定的事

项目没有把整个用户画像交给 LLM 随意改写，而是明确分工：

- LLM：从对话提取抽象洞察；判断新旧事实是新增、更新、无操作还是改善；总结沟通风格和思维模式。
- 确定性代码：掌握度计算、统计更新、复习日期、连续高分次数、容量限制、时间衰减、持久化和并发保护。

这样既保留语义理解能力，又避免数值指标随模型版本和温度漂移。

### 详细解决方案

#### 1. 两阶段画像更新

第一阶段 Extract：

- 输入面试逐字稿、逐题分数和旧画像；
- 提取新的薄弱点、优势、主题掌握度、沟通习惯和思维模式；
- 对大段画像和逐字稿使用 Token Budget，逐字稿优先级高于旧画像。

第二阶段 Update：

- 将已有薄弱点编号；
- 让 LLM 输出 `ADD/UPDATE/NOOP/IMPROVE` 操作；
- 程序只执行结构化操作，而不是用模型返回内容整体覆盖 JSON 文件。

这解决了“同一个问题被换一种说法后反复 append”的记忆膨胀问题。

#### 2. 并发更新保护

画像更新中的 LLM 调用可能持续数十秒。如果全程持有文件锁，会阻塞实时更新；如果不加锁，又会发生旧快照覆盖新数据。

当前采用“两段式并发控制”：

1. 锁外读取快照并调用 LLM；
2. 锁内重新读取最新画像，只执行已经解析好的操作；
3. LLM 输出里的数组索引不直接信任，而是通过快照中的 `point` 文本重新映射到最新列表。

这是典型的长耗时计算与短临界区分离。

#### 3. LLM 失败时的确定性降级

如果 LLM 返回非法 JSON：

- 使用 Embedding 将新薄弱点与已有薄弱点做语义匹配；
- 相似则更新 `times_seen/last_seen`；
- 不相似则新增；
- Embedding 也失败时按新事实处理，不让整次画像更新失败。

注意：降级的目标是保住训练结果，而不是假装语义合并质量完全不受影响。

#### 4. 掌握度公式

单次题目贡献：

```text
contribution = clamp(difficulty, 1, 5) / 5
             × clamp(score, 0, 10) / 10
             × 100
```

薄弱点级掌握度采用 EWMA：

```text
new_mastery = 0.7 × old_mastery + 0.3 × contribution
```

主题级掌握度更新采用较高的新会话权重，默认：

```text
new_topic_score = 0.3 × old_score + 0.7 × session_score
```

设计含义：

- 高难度题答对贡献更高；
- 单题异常不会让薄弱点掌握度剧烈跳变；
- 主题整体水平应更快反映最近状态。

局限：难度和分数本身仍可能来自模型评价，因此不是完全无主观性；“确定性”指合并公式固定、可测试，而不是上游信号绝对客观。

#### 5. SM-2 改造

分数 0～10 映射到 SM-2 quality 0～5：

```text
quality = min(5, int(score / 2))
```

- score ≥ 6 视为通过；
- 第一次通过间隔 1 天；
- 第二次通过间隔 3 天，刻意短于标准 SM-2 的 6 天；
- 后续约为 `round(previous_interval × ease_factor)`；
- 失败则 repetition 清零、间隔回到 1 天；
- ease factor 下限为 1.3。

项目额外引入“连续 3 次分数 ≥7 才毕业”的机制。原因是 SM-2 的 `repetitions` 统计的是 ≥6 分的通过次数，不能代表连续高质量掌握。

#### 6. 向量记忆

长期洞察被写入向量存储，用于下一次训练时按语义检索历史：

- 本地开发：SQLite BLOB + numpy 余弦相似度；
- Docker/部署：Qdrant；
- 薄弱点语义去重阈值 0.75；
- 时间衰减半衰期 14 天；
- 时间因素最多影响最终排序权重的 30%，避免旧但高度相关的记忆完全消失；
- 单用户最多 500 条向量，超限清理旧数据；
- 零向量不允许写入，避免 Embedding 故障污染索引。

### 这个亮点解决了什么问题

- 每次训练都从零开始；
- 同一薄弱点换个说法就重复存储；
- 旧问题永久占据最高优先级；
- LLM 直接维护分数导致不可解释、不可回归测试；
- 已掌握问题仍被无限复习；
- 并发画像更新互相覆盖。

### 常见错误与边界

| 问题 | 正确理解或处理 |
| --- | --- |
| 把 `repetitions` 当成连续高分次数 | 错。它只代表 SM-2 通过次数，当前代码另存 `consecutive_high` |
| 用字符串完全相等去重薄弱点 | 会漏掉同义表达，应使用向量相似度，但要接受阈值误判 |
| LLM 返回操作索引后直接修改列表 | 并发时索引会漂移，应通过快照文本重定位 |
| 画像更新全程加锁 | 会把几十秒模型调用放进临界区，严重阻塞并发请求 |
| Embedding 失败写入零向量 | 会制造无意义高相似/低相似结果，必须跳过 |
| 对所有历史等权平均 | 适应用户近期水平太慢，EWMA 更合适 |
| 只要一次高分就标记已掌握 | 容易误毕业，当前设计要求连续 3 次 ≥7 |
| 个性化越强越好 | 可能造成题目越来越窄，需要保留探索题和通用知识题 |

### 当前已发现的真实测试契约问题

当前执行 `pytest -q` 的结果为 40 通过、1 失败。失败用例 `test_graduation_after_third_pass_with_high_score` 仍假设 legacy `repetitions=2` 后再得一次 8 分即可毕业；当前实现已收紧为独立的 `consecutive_high` 连续高分计数，因此旧状态在没有 `last_score` 证据时只会记为第一次高分。

建议修复方式：

1. 修改测试数据，显式提供 `consecutive_high=2`，验证第三次高分毕业；
2. 增加 legacy 迁移测试：只有 `repetitions`、没有 `consecutive_high` 时不得直接毕业；
3. 增加“8、8、6、8、8、8”的断连重置测试；
4. 更新测试标题和注释，避免继续把 repetitions 与连续高分混为一谈。

面试中可以把它描述为“测试用例未同步最新业务契约的技术债”，不要说成算法已全部通过测试。

## 底层能力 C：面向薄弱点的多路 RAG、增量索引与双层评测

### 简历一句话版

设计面向用户薄弱点的多路 RAG：将多个薄弱点拆成独立查询并发召回，通过 RRF 融合、Embedding 语义去重和可选 Cross-Encoder 重排生成最终上下文；同时支持本地 numpy/Qdrant 双后端、文件哈希增量索引和在线/离线两套指标，提升检索相关性、可观测性与部署灵活性。

### 更精炼的简历 Bullet

- 将“多个薄弱点拼成一个 Query”的低信噪比检索改造为按薄弱点并发召回，使用 RRF（k=60）融合、余弦阈值 0.85 去重和可降级 Reranker 重排；配套文件哈希增量建索引及 Hit@K/MRR 等离线评测，使 RAG 优化从主观调 Prompt 转为可测量迭代。

### 详细解决方案

#### 1. 为什么不能把多个薄弱点拼成一个查询

例如用户同时薄弱于 GIL、asyncio、事务隔离和 Redis 缓存穿透。把四段文本拼成一个向量，会得到一个语义平均方向，可能与任何一个具体主题都不够相似。

当前方案：

- 最多取前 5 个薄弱点；
- 每个薄弱点独立查询；
- 少于 3 个查询时补一个通用探索 Query；
- 使用 Semaphore 控制 Embedding/检索并发，避免供应商限流；
- 子查询异常通过 `gather(return_exceptions=True)` 隔离，其余结果仍可继续。

#### 2. RRF 融合

不同查询甚至不同后端的相似度分数通常不可直接比较，因此项目使用只依赖排名的 RRF：

```text
RRF(chunk) = Σ 1 / (k + rank_i(chunk)), k = 60
```

一个 Chunk 如果在多个薄弱点查询中都排名靠前，会自然获得更高融合分数。

优点：参数少、不需要校准不同查询的原始相似度分布。缺点：丢弃了原始分数强弱信息；如果所有排名质量都差，融合也不会凭空产生正确结果。

#### 3. 语义去重与重排

RRF 后对 Chunk 做 Embedding：

- 与已保留 Chunk 的余弦相似度 ≥0.85 时视为近重复；
- Embedding 缓存优先走 Redis，Redis 不可用时退到内存 LRU；
- 去重后调用可选 Reranker；
- Reranker 不可用时保留 RRF 结果，状态标记为 degraded/off，而不是让主链路失败；
- 最终默认保留前 10 个 Chunk。

0.85 是工程阈值，不是数学真理。知识文档格式、Embedding 模型切换后都应重新评估。

#### 4. 知识索引增量更新

项目为每个主题维护文件哈希 Manifest：

- 新增文件：只加载并嵌入新增文件；
- 修改文件：删除旧文件对应节点，再嵌入新内容；
- 删除文件：删除对应节点；
- Embedding 维度变化、Collection 为空、首次构建或显式 `force=true` 时全量重建。

本地索引和 Qdrant 都走增量语义，但底层删除和持久化方式不同。不要把“双后端”描述为完全相同的物理实现。

#### 5. 双后端策略

- 裸 `uvicorn` 本地开发默认 numpy/本地持久化，降低部署门槛；
- Docker Compose 默认 Qdrant，适合容器化持久化和较大数据量；
- 知识库按 `kb_{user}_{topic}` 分 Collection；
- 长期记忆使用单 Collection + payload 中的 user_id 做多租户过滤。

一个重要边界：Qdrant 模式故障时不应悄悄回退到本地旧索引，否则会出现两个数据源不一致却返回“看起来成功”的结果。当前设计倾向返回空上下文/显式降级，再由后台重建或运维修复。

#### 6. 同步库的异步包装

LlamaIndex 检索本质上是同步调用。项目用：

- `asyncio.to_thread` 将阻塞调用移出事件循环；
- 外层超时控制；
- 超时或异常返回空列表；
- 多主题检索使用共享线程池和单个总截止时间，避免最坏耗时变成 `主题数 × 单主题超时`。

需要注意：`wait_for` 超时只让协程不再等待，不一定能杀死底层线程。所以查询侧还需要 SDK 级快速超时和并发上限，防止“超时线程泄漏式堆积”。

#### 7. 在线指标与离线评测必须分开

在线 `rag_metrics.py` 没有黄金答案，主要衡量：

- 检索结果与薄弱点的相关性；
- 区分度；
- Chunk 多样性。

离线 `rag_eval.py` / `eval/rag_recall.py` 有黄金集合或参考答案，衡量：

- Hit@K；
- MRR；
- Precision/Recall；
- Faithfulness；
- Answer Relevancy；
- Answer Correctness。

两套指标的定义、基线和自然数值范围不同，不能使用同一个全局阈值比较。

### 这个亮点解决了什么问题

- 多意图 Query 语义稀释；
- 多路结果分数不可比；
- 重复 Chunk 浪费上下文；
- Reranker 或 Redis 故障拖垮主链路；
- 每次知识文档变化都全量重新 Embedding；
- RAG 优化只靠“感觉回答变好了”。

### 常见错误与边界

| 问题 | 正确处理 |
| --- | --- |
| 用召回 Query 自己评价召回结果 | 会产生循环指标，结果虚高，应使用独立黄金集合或代理指标 |
| 直接平均不同 Query 的相似度 | 分数分布未校准，优先使用 RRF 等排名融合 |
| 去重只比较前 100 个字符 | 同义改写和不同前缀无法识别，应使用语义相似度 |
| Reranker 挂了就报 500 | Reranker 是增强项，应降级到 RRF 排名 |
| `asyncio.to_thread` 等于可取消线程 | 错。外层超时不会强杀线程，仍需 SDK 超时和并发控制 |
| Qdrant 故障时偷偷读本地旧索引 | 可能返回陈旧数据，应显式失败或空结果 |
| Embedding 换模型后继续使用旧向量 | 维度或向量空间不一致，应触发重建 |
| Chunk 越小越精确 | 太小会失去上下文，太大又降低定位精度，需要通过评测调优 |
| RAG 召回正确就不会幻觉 | 错。还需要 Prompt 约束、引用、生成质量评测和拒答策略 |

## 底层能力 D：模型渠道容灾、后台 Embedding 队列与 Reasoning-aware SSE

### 简历一句话版

构建模型调用可靠性层：支持多 LLM/Embedding 渠道优先级路由、Key 轮转、冷却与半开探测，区分致命 4xx 和可重试故障；通过后台优先级队列、指数退避、三态熔断和 Reasoning-aware SSE 心跳，使长推理、索引重建和外部模型波动不阻塞主请求。

### 更精炼的简历 Bullet

- 封装多渠道 ResilientChatModel，对 429/5xx/网络超时先同渠道重试再 Failover，对确定性 4xx 快速失败；流式调用仅在首 Chunk 前允许切换，并配合 Embedding 后台队列、三态熔断及 SSE idle ping，避免重复输出、级联故障和代理超时。

### 详细解决方案

#### 1. 渠道选择与冷却

每个渠道包含优先级、模型等级、API Key、超时等配置。ChannelManager 维护运行状态：

- 连续错误计数；
- 3 次错误后进入约 60 秒冷却；
- 冷却结束进入 HALF_OPEN；
- HALF_OPEN 只允许一个探测请求，避免恢复瞬间流量洪峰；
- 成功后恢复健康，失败则重新冷却；
- 可按 small/large tier 进行模型分级路由。

#### 2. 错误分类

不能对所有异常都切渠道：

- 429、408、409、5xx、网络错误、连接错误和超时：通常可重试；
- 确定性 4xx，例如请求格式错误、权限或配置错误：换渠道大概率也无法解决，应立即抛出；
- 同一渠道对瞬时错误先做有限重试和短退避，再切下一个渠道；
- 所有渠道耗尽后返回明确错误。

这样避免一个错误 Prompt 或非法参数把所有渠道都打进冷却。

#### 3. 流式 Failover 的提交点

非流式调用可以在失败后重新请求另一个渠道。流式调用必须分两阶段：

1. 首 Chunk 之前失败：客户端还没看到内容，可以安全切渠道；
2. 首 Chunk 已经发出：流已经“提交”，不能换模型重新生成，否则会把另一个完整答案拼到半个旧答案后面。

因此当前实现首 Chunk 后的错误直接向上传播，由客户端展示中断和重试入口。

这是一个非常适合面试展开的工程取舍：一致性优先于“看似无缝”的错误拼接。

#### 4. Reasoning-aware SSE

推理模型可能长时间只输出 reasoning 字段，不输出最终 content。如果服务端只在 content 到达时发送数据，nginx、浏览器或网关会认为连接空闲并关闭。

当前 SSE 层：

- 监听普通 content 和供应商差异化的 reasoning 字段；
- 空闲达到阈值时发送 `ping`；
- reasoning 阶段发送“思考中”进度，但不泄露原始思维链；
- 每累计约 200 字发送进度事件；
- 阻塞同步任务通过 `asyncio.to_thread` 执行，同时定时发心跳；
- 前端按事件类型增量渲染。

#### 5. 增量 JSON 解析

模型生成题目数组时，不等待整个 JSON 完成，而是维护：

- 花括号深度；
- 是否位于字符串内部；
- 反斜杠转义状态；
- 当前对象开始位置。

每形成一个完整 JSON Object 就推送一道题。这样改善的是用户感知延迟，而不是模型总生成时间。

边界：如果模型持续输出非法 JSON，增量解析器可能始终得不到对象，最终仍要依赖整段解析、修复或错误提示。

#### 6. Embedding 后台任务队列

知识库重建、会话记忆入库等非关键写路径不在 HTTP 请求中同步等待：

- 任务有优先级；
- worker 异步消费；
- 失败采用 2s、4s、8s 等指数退避，上限受控；
- 延迟重试通过独立调度任务重新入队，不让 worker `sleep 60s` 占住执行槽；
- 队列满时丢弃低价值重试并记录状态；
- 服务关闭时停止 worker；
- 任务失败不应让主进程崩溃。

#### 7. 查询与后台任务使用不同熔断器

查询路径和后台索引路径对失败的容忍度不同：

- 查询路径强调快速失败，默认 5 次失败打开熔断；
- 后台队列容忍更高，使用独立阈值，避免一次查询侧波动把所有后台重建一并阻断；
- OPEN 后等待恢复窗口，再进入 HALF_OPEN；
- 半开状态只允许探测请求。

共享一个熔断器会导致不同流量类型互相污染状态。

### 这个亮点解决了什么问题

- 单一模型渠道故障导致全站不可用；
- 配置错误触发无意义的全渠道重试；
- 流式中途切模型造成重复或拼接答案；
- Reasoning 模型长时间无正文被代理断连；
- 大规模 Embedding 阻塞 API 请求；
- 外部服务持续故障引发重试风暴和级联失败。

### 常见错误与边界

| 问题 | 正确处理 |
| --- | --- |
| 所有异常都 Failover | 配置/请求类 4xx 应快速失败 |
| 流式失败后换模型续写 | 无法保证语义和 token 边界一致，会拼接重复答案 |
| HALF_OPEN 放开全部流量 | 恢复瞬间可能再次击穿，只允许少量探测 |
| worker 里直接 sleep 60 秒 | 占用 worker，其他任务饥饿，应延迟重新入队 |
| SSE 心跳只看 content | 推理模型 reasoning 阶段仍会被误判空闲 |
| 把原始 reasoning 发给前端 | 可能泄露内部推理、敏感信息和供应商字段 |
| 无限重试 | 放大故障和成本，应限制次数并使用熔断 |
| Redis 不可用就让系统启动失败 | 缓存是增强项，应退到内存 LRU，但要接受多实例不一致 |

## 四、可直接放入简历的四条最终表述

谨慎写的效果数字：首题延迟降低百分比、召回率提升百分比、成本降低百分比、并发量、可用性。仓库当前没有稳定、可复现的基准报告支撑时，不要把经验值写成线上结论。可以说“通过增量推送降低感知等待”，不要虚构“延迟降低 80%”。

## 五、面试高频问题与详细答案

## A. 项目定位与架构

### Q1：请用 1 分钟介绍项目。

建议回答：

SparkOffer 是一个个性化面试训练 Agent，核心区别是跨会话闭环，而不是一次性问答。用户上传简历或选择专项后，系统通过 LangGraph 或受控 Pipeline 组织出题、作答和评价；训练结束后，一部分结果用确定性公式更新掌握度和 SM-2 复习计划，另一部分由 LLM 以 Mem0 风格合并到长期画像，同时写入向量记忆。下一轮出题会融合简历、知识库 RAG、历史薄弱点和到期复习项。为了让它能稳定运行，还做了模型多渠道容灾、Embedding 后台队列、SSE 心跳、上下文预算和离线评测。

### Q2：项目最核心的数据流是什么？

```text
用户输入/简历/JD
  → Agent 状态或训练 Pipeline
  → 个性化 RAG 召回
  → LLM 出题/追问
  → 用户作答
  → 逐题评价与总结
  → 掌握度、画像、向量记忆、SM-2 更新
  → 下一轮定向出题
```

### Q3：为什么说这是 Agent，而不只是 RAG 应用？

因为系统不仅“检索后回答”，还维护业务状态、基于状态选择下一动作、暂停等待人类输入、调用工具、产生长期记忆并跨会话影响未来决策。RAG 是 Agent 获取外部知识的一部分，不是全部。

### Q4：为什么不是 Multi-Agent？如果要改成 Multi-Agent 怎么做？

当前没有多个自治角色间的消息通信、任务协商和仲裁，主链路是单个受控工作流。若改造，可拆成面试官、知识检索、评分员、画像更新员和质量审查员，但必须解决：共享状态 Schema、并行与依赖关系、冲突裁决、调用成本、超时传播和可观测 Trace。并不是 Agent 越多越先进，当前场景中确定性编排更稳定、成本更低。

### Q5：为什么 LangGraph，而不是普通 if/else？

if/else 能实现简单流程，但 LangGraph 提供显式状态、条件边、Checkpoint、Interrupt 和状态恢复。项目的价值不在“用了框架”，而在把阶段推进和人机交互建模为可持久化状态机。若流程只有一次调用，LangGraph 反而是过度设计。

### Q6：项目中哪些地方是确定性的，哪些依赖 LLM？

- 确定性：图路由硬限制、掌握度公式、SM-2、文件哈希 diff、缓存、权限、容量、超时和熔断。
- LLM：出题、回答评价、画像事实提取、语义合并、总结。
- Embedding：语义召回、去重和相似匹配。

好的回答重点是“边界清晰”，而不是说所有智能都来自大模型。

## B. LangGraph 与会话状态

### Q7：一次简历面试如何启动、暂停和恢复？

启动时创建图并以 session_id 作为 thread_id；`init` 加载稳定上下文并生成开场；图在 `wait` 前 Interrupt。用户回答后，API 把 HumanMessage 写回同一线程状态，再 invoke 图，条件路由决定 ask、advance 或 END。状态由 SqliteSaver 保存，因此服务重启后仍可按 thread_id 恢复。

### Q8：为什么 Checkpoint 单独放一个数据库？

Checkpoint 写入频率和业务表不同，单独数据库能减少与会话、评分等业务写入的锁竞争；也便于独立清理和迁移。代价是产生跨库一致性问题，需要通过幂等同步和最终一致性处理。

### Q9：隐藏 EVAL 有什么风险？

- 模型不输出或输出非法 JSON；
- 模型回显示例；
- 字段缺失；
- 分数越界；
- Prompt Injection 诱导模型生成错误评价。

当前通过取最后标记、JSON 类型校验、分数裁剪和计数兜底降低风险。更强方案是结构化输出/Tool Calling、独立评分模型和基于 Schema 的严格校验。

### Q10：为什么技术阶段至少问两题才允许推进？

单题方差太大，可能题目太简单、用户误答或模型误判。最低采样数能避免阶段被一次偶然结果过早结束；同时仍有最大问题数，防止为了统计稳定无限追问。

### Q11：如何防止重复问题？

状态中保存 `questions_asked`，每轮将已问题目作为动态上下文传入 Prompt。专项出题链路还可配合语义去重 Validator。仅靠字符串去重不够，因为模型可能换一种说法重复追问；更强方案是对问题做 Embedding 并设相似度阈值。

### Q12：两个并发回答请求会发生什么？

当前同一 session 缺少严格的分布式顺序锁，可能出现重复推进或消息顺序异常。生产方案应增加：

1. 请求幂等键；
2. session version；
3. `UPDATE ... WHERE version=?` 乐观锁；
4. 单 session 队列或 Redis 锁；
5. 前端提交期间禁用重复按钮只是体验层，不能代替服务端保护。

## C. 记忆、个性化与学习算法

### Q13：为什么不直接把全部历史对话塞给模型？

成本和上下文长度会线性增长，噪声越来越大，旧事实可能与新事实冲突。项目将原始会话压缩成结构化画像和向量洞察，按需检索相关历史。原始记录负责审计，压缩记忆负责决策。

### Q14：Mem0 风格体现在哪里？

不是简单 append，而是先 Extract 新事实，再对照旧事实生成 ADD/UPDATE/NOOP/IMPROVE 操作。程序执行操作，保留已有结构和元数据。项目是“Mem0 风格”，不是直接集成 Mem0 SDK，表述时应准确。

### Q15：为什么画像合并用 LLM，掌握度不用 LLM？

“GIL 不理解”和“对 CPython 锁机制认识模糊”是否同一问题需要语义判断，适合 LLM/Embedding；分数如何合并必须稳定、可解释、可测试，适合确定性公式。

### Q16：EWMA 的权重为什么是 0.7/0.3？

这是经验参数，薄弱点级 0.7 旧值 + 0.3 新贡献用于抑制单题波动；主题级对新会话权重更高，用于快速反映近期状态。正确回答应承认需要通过离线数据或 A/B 实验校准，而不是声称这是理论最优。

### Q17：高难度答错时贡献也可能低，这合理吗？

当前贡献是难度与得分相乘，高难度低分仍然低，符合“尚未掌握”。但难度越高，满分贡献越高。边界是不同难度题的评分标尺未必线性，未来可用 IRT 或基于题目校准参数的能力估计替代简单乘法。

### Q18：薄弱点语义去重阈值怎么确定？

当前是 0.75。应构造正负样本对，观察同义点与不同点的相似度分布，在 Precision/Recall 间选阈值。模型更换、中文领域变化后要重新标定。低阈值会错误合并，高阈值会重复堆积。

### Q19：时间衰减为什么不能权重过大？

如果完全按时间衰减，用户几个月前反复暴露的核心弱点会被新但无关的记忆挤掉。因此项目让时间只提供有限加权，语义相关性仍是主体。衰减用于打破相近相关度的排序，而不是删除历史事实。

### Q20：SM-2 为什么把第二次复习改成 3 天？

面试备战周期通常短于长期语言学习，标准 6 天可能错过短期强化窗口。改为 3 天是场景化调整，但要承认缺乏真实用户留存数据时仍是启发式参数。

### Q21：如何避免个性化造成信息茧房？

- 只有少量薄弱点时补通用探索 Query；
- 题目分配应保留弱点利用、基础覆盖和新主题探索；
- 对最近题目做去重；
- 监控主题覆盖率和多样性；
- 设置薄弱点毕业机制，让已掌握内容退出高优先级。

### Q22：画像文件并发写如何保证不损坏？

使用 per-user Lock，将 read-modify-write 放在同一临界区，并采用临时文件写完后原子替换。跨进程时 threading.Lock 不够，需要文件锁或迁移到数据库事务。

## D. RAG 与索引

### Q23：完整讲一下个性化 RAG 链路。

先从画像选出高优先级薄弱点，每个薄弱点独立检索，必要时加入探索 Query；并发召回后用 RRF 融合；对融合结果做语义去重；可选 Reranker 重排；截取最终 Chunk；计算在线指标并记录来源，最后放入 Token Budget 与简历、画像、历史消息共同装配。

### Q24：为什么 RRF 的 k 是 60？

60 是经典常用平滑常数，使排名前几位有差异但不会过度尖锐。当前值是经验选择；面试时应说明可通过离线 Hit@K/MRR 网格搜索校准，而不是把 60 当成固定真理。

### Q25：为什么先融合再去重？

先融合能让重复出现的高价值 Chunk积累多路支持信号，再统一去重；如果每路先激进去重，可能丢失“多个查询都召回它”的证据。不过实现时需要保留元数据映射，避免文本去重后丢失来源。

### Q26：Dense、Sparse 和 Hybrid 怎么选？

当前核心是 Dense Embedding，适合同义表达。对错误码、类名、函数名等精确词，BM25/Sparse 更有优势。生产版可做 Dense + Sparse 双路召回，再用 RRF 融合。知识库以中文概念文档为主时 Dense 是合理起点，但不是终点。

### Q27：增量索引如何识别修改和删除？

对源文件计算哈希并与 Manifest 比较，得到 added/modified/deleted。修改和删除先删除旧文件对应节点，新增和修改再加载、切块、Embedding、写入索引，成功后更新 Manifest。必须考虑中途失败，Manifest 只能在索引更新成功后提交。

### Q28：Embedding 模型切换为什么必须重建？

不同模型即使维度相同，向量空间也不兼容；维度不同则数据库直接无法计算。仅检查维度只能发现一部分问题，更稳妥的 Manifest 还应记录模型名称、版本和归一化方式。

### Q29：Qdrant 和 numpy 如何保持接口一致？

通过抽象 VectorStore 接口统一 upsert/search/delete/cleanup 等行为，上层不依赖具体实现。但一致的是逻辑契约，不是性能、事务和故障语义。numpy 适合单机小规模；Qdrant 支持服务化检索和过滤，但增加网络与运维成本。

### Q30：检索超时后线程还在运行怎么办？

Python 无法安全强杀普通线程。应从源头控制：SDK 连接/读取超时、较小线程池、Semaphore、快速失败 Embedding 客户端、熔断和监控活动任务数。真正需要硬取消时，应使用可终止的子进程或原生异步 SDK。

### Q31：如何证明 RAG 改造有效？

固定同一知识库和 Query 集，对改造前后比较 Hit@K、MRR、关键词覆盖、Precision；再使用固定生成模型比较 Faithfulness 和 Answer Correctness。应报告均值、分主题结果、失败样本和置信区间，不能只展示几个成功案例。

### Q32：在线 RAG 指标为什么不能当真实准确率？

在线没有 ground truth，只能用 Embedding 相似性、多样性等代理指标监控趋势。代理指标高不代表答案一定正确，只适合异常检测和相对比较。

## E. 容灾、流式与异步

### Q33：一次 LLM 调用如何选择渠道？

先按 enabled、priority、tier 和健康状态筛选渠道；请求失败后判断错误类型，瞬时错误可在同渠道有限重试，仍失败则记录错误并切下一个；累计错误达到阈值进入冷却；冷却结束只放一个半开探测。

### Q34：哪些错误不应该 Failover？

参数非法、Prompt 超长、认证/权限错误等确定性 4xx。因为这些错误通常由调用本身或共享配置引起，换渠道只会重复失败并污染所有渠道健康状态。429 和多数 5xx 属于可重试故障。

### Q35：流式中途失败为什么不能切模型？

客户端已经收到一部分不可回滚内容。另一个模型无法从完全相同的隐藏状态和采样位置继续，重新调用通常从头生成，拼接会重复、矛盾或破坏 JSON。安全提交点只能在首 Chunk 之前。

### Q36：SSE 为什么不用 WebSocket？

当前主要是服务端单向推送，客户端请求仍走普通 HTTP，SSE 更简单、可自动重连且易穿过代理。若需要实时语音、双向 token 交互或复杂房间广播，WebSocket 更合适。

### Q37：SSE 心跳间隔如何设置？

必须小于 nginx、负载均衡器和客户端最短空闲超时，并留安全余量。项目内部 idle heartbeat 与代理配置需要协同；过密会增加事件和日志噪声，过疏仍可能断连。

### Q38：客户端断开后服务端如何清理？

理想处理是检测生成器取消，取消尚未提交的上游任务、停止积累缓冲并释放资源。对于已经进入第三方 SDK 的线程调用，可能无法立即停止，因此还需要任务超时、容量上限和后台清理。临时会话设置 2 小时 TTL 防止永久泄漏。

### Q39：为什么后台重试不能直接在 worker 中 sleep？

worker 数有限，长时间 sleep 会占住处理槽，使后续正常任务饥饿。项目使用延迟任务，时间到后重新入队，让 worker 立即继续处理其他任务。

### Q40：熔断和限流有什么区别？

- 限流：保护系统不被过多请求压垮，与下游是否健康无关。
- 熔断：下游持续失败时暂时停止调用，避免无效请求和级联故障。
- 重试：处理少量瞬时故障。
- 超时：限定单次等待时间。

四者需要组合，单独使用任何一个都不完整。

## F. 安全、存储与扩展性

### Q41：多用户隔离如何实现？

API 通过 JWT 取得 user_id；业务查询都带 user_id；文件路径统一从 `data/users/{user_id}` 派生；Qdrant 记忆检索使用 user_id payload 过滤；管理接口有 owner-only 限制。需要警惕任何手写路径和漏加 user_id 的 SQL。

### Q42：如何防路径穿越？

上传文件名必须取 basename、限制扩展名和大小，并在 resolve 后验证目标仍位于用户根目录。不能直接拼接用户提供的 `../../` 路径。知识库路由已经包含文件名校验，新增写文件功能必须复用同样原则。

### Q43：Prompt Injection 怎么处理？

无法仅靠一句 Prompt 根治。应分层：把外部文档标记为不可信数据；限制工具集合和参数；写操作二次确认；结构化输出校验；敏感工具做权限检查；日志审计；对引用内容做来源展示。当前主面试 Agent 工具权限有限，因此风险低于能执行任意命令的 Agent。

### Q44：为什么用 SQLite？什么时候必须换？

单机个人项目、写并发有限时 SQLite 部署简单、事务可靠，WAL 可支持读写并行。多实例、高写并发、复杂迁移和强运营查询时应迁移 PostgreSQL；迁移前需要 Repository 抽象、Schema 版本管理和数据回填脚本。

### Q45：扩展到 10 万用户，优先改什么？

建议顺序：

1. PostgreSQL 替换业务 SQLite 和 Checkpoint SQLite；
2. Redis 做共享 session/cache/rate limit；
3. Celery/RQ/Kafka 等替换进程内 Embedding 队列；
4. 对象存储保存简历和知识文件；
5. Qdrant 集群或其他向量库分片；
6. API 无状态化、水平扩容；
7. 全链路 Trace、成本、延迟和队列积压监控；
8. 多租户配额、计费和数据生命周期治理。

### Q46：当前最大的技术债是什么？

可以诚实回答三点：

- SQLite、文件锁和进程内队列限制了多实例扩展；
- LLM/Embedding 集成测试依赖外部服务，现有单元测试主要覆盖纯函数和局部逻辑；
- SM-2 的最新“连续高分毕业”契约与一个旧测试尚未同步。

同时给出改进顺序，比只说“没有技术债”更可信。

### Q47：如何控制 LLM 成本？

- 固定系统前缀利用 Prompt Cache；
- Token Budget 丢弃低优先级上下文；
- 小模型批改、大模型总结的分级路由；
- RAG 只取有限 Chunk；
- Embedding 和 Reranker 缓存；
- 不把全部历史原文重复发送；
- 后台任务合并和去重；
- 记录每场会话 token 与成本，按用户设置配额。

### Q48：如何设计可观测性？

至少记录：session_id、user_id 脱敏标识、graph node、渠道、模型、重试次数、首 token 延迟、总延迟、token、RAG Query 数、召回数、去重数、Reranker 状态、上下文各 Section token、队列长度、熔断状态和错误类型。日志不应记录 API Key、完整简历或敏感对话正文。

## G. 10 道题生成 Pipeline 与知识训练场

### Q49：为什么 10 道题不能让 LLM 一次生成完就直接使用？

一次生成虽然代码简单，但存在数量不稳定、JSON 格式错误、难度失衡、重复题、薄弱点漏覆盖和全批返工成本高等问题。当前将流程拆成准备、检索、生成、校验、持久化五阶段，每阶段都能记录耗时和产物，坏题只局部重生成。

### Q50：题目槽位规划解决了什么问题？

只在 Prompt 中写“多出一些薄弱点题”无法保证分布。槽位计划把 10 个位置提前分配给到期复习、低掌握薄弱点、巩固项和探索项，并给出目标难度分布。LLM 的任务从自由创作变成按约束填槽，Validator 再检查实际结果。

### Q51：种子题库和 LLM 混合生成有什么优势？

种子题可立即推送、质量稳定、成本低；LLM 负责补足个性化角度和动态内容。当前最多使用 6 道种子题，至少让 LLM 生成 2 道，避免完全退化成固定题库。需要用近期题目和语义 Validator 防止种子题重复。

### Q52：为什么只局部 Repair，不重新生成全部 10 题？

整批重生成会丢掉已经合格的题目，成本更高，而且新批次可能产生新的问题。局部 Repair 把原题、题号和失败原因交给模型，只替换坏题并保持 ID 和顺序。Repair 最多一轮，避免 Validator 与模型形成无限循环。

### Q53：难度校准为什么不能相信 LLM 自报的 1～5？

不同模型和不同批次对“难度 3”的尺度不一致。项目用已标注难度锚点的 Embedding 邻居校准，保留 `difficulty_llm` 便于对比。边界是锚点质量决定校准上限，跨主题不能盲目共用同一套锚点。

### Q54：知识训练场如何保证卡片有事实来源？

每张卡都关联候选 Section 的 `filename/header_path`。模型给出的引用必须能在本轮候选章节中找到；如果模型给了错误来源但提供了有效 `source_index`，以 source_index 指向的权威 Section 修复；都无效时回退到位置对应的原始章节。

### Q55：为什么知识卡片用确定性 Hash ID？

同一主题、标题和来源生成稳定 ID，可以使用主键做精确幂等。重复生成时 `INSERT OR IGNORE` 不会覆盖用户已有的熟悉度和 SM-2 状态。缺点是标题轻微变化仍会形成新卡，因此还可增加语义级卡片去重。

### Q56：知识训练场和普通 RAG 问答的区别是什么？

RAG 问答是用户提问后即时检索并生成答案；知识训练场是主动内容生产，把文档提前转成可复用训练单元，并维护来源、熟悉度、复习时间和覆盖范围。前者解决“现在回答什么”，后者解决“未来应该练什么”。

## 七、面试时容易踩的“红线”

1. 不要说这是 Multi-Agent。准确说法是 LangGraph 受控工作流 + 单 Agent Tool Calling。
2. 不要说掌握度完全不依赖 LLM。公式是确定性的，但题目难度和评分信号仍可能来自模型。
3. 不要说流式可以无缝切模型。只允许首 Chunk 前切换。
4. 不要说 Redis/Qdrant 挂了“完全无影响”。正确说法是核心链路按设计降级，但检索质量、缓存一致性或功能可用性会下降。
5. 不要说 `asyncio.to_thread + wait_for` 能杀死阻塞线程。
6. 不要把在线代理指标当真实准确率，也不要把在线和离线 RAG 分数横向比较。
7. 不要说阈值 0.75、0.85、EWMA 0.7/0.3 是理论最优。它们是可通过评测继续校准的工程参数。
8. 不要虚构线上 DAU、QPS、准确率或成本收益。没有可靠实验报告时只写结构性成果。
9. 不要说全部测试通过。当前状态是后端 40/41 通过，前端生产构建通过。
10. 不要回避 SQLite 和进程内队列的规模边界，主动给出演进路线更专业。

## 八、建议的 90 秒项目陈述

我做的是一个个性化面试训练 Agent。和普通面试问答产品不同，它的重点是跨会话闭环：每次训练后，系统会把逐题表现转换成稳定的掌握度和 SM-2 复习计划，同时用 Mem0 风格的 Extract/Update 流程合并长期薄弱点、沟通习惯和思维模式，下一轮再围绕这些信息出题。

在 Agent 编排上，我用 LangGraph 把简历面试建模为五阶段状态机，通过 Interrupt 等用户回答，SQLite Checkpoint 保证重启后能续接；阶段推进由 LLM 评价和确定性计数共同决定，并设置硬上限防止死循环。

专项训练不是让模型一次性吐出 10 道题，而是拆成准备、RAG、混合生成、校验和持久化五阶段：先按薄弱点与到期复习项规划题目槽位，再融合种子题和 LLM 生成，生成过程中逐题推送，最后用覆盖率、语义重复和难度分布 Validator 找出坏题并局部修复。

我还做了知识训练场，把 Markdown 知识文档按语义章节切分，生成带来源引用的三档训练卡片，通过确定性 ID 去重，并用 SM-2 安排到期复习。底层则用多渠道 Failover、Embedding 熔断、Token Budget 和 Reasoning-aware SSE 保证外部模型波动时的可用性。这个项目让我最深的体会是：Agent 的难点不只是 Prompt，而是状态、生成质量控制、记忆、知识落地、评测和失败语义的系统化设计。

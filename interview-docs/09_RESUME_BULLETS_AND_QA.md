## 一、总体诊断

**结论：内容底子很好，不用推翻重写；要做的是「压密度、填数字、亮决策」三件事。**

这段简历的稀缺优点：每句都有可验证的具体数字（RRF k=60、0.85 余弦、18 个工具、五阶段、SM-2）。大部分候选人写"使用了 RAG 技术优化检索效果"，你写的是"RRF(k=60) 融合、0.85 余弦语义去重"——前者面试官没法问，后者面试官会眼睛一亮开始深挖。**深挖正是你想要的**，因为每个数字背后你都有真实的设计故事。

三个问题，按优先级：

| # | 问题 | 严重度 | 说明 |
|---|------|--------|------|
| 1 | **`__%` 空白占位** | 🔴 上简历前必须解决 | 空白 = 没做完或者数据造假前的草稿，二选一都致命。解决路径见 §四 |
| 2 | **句长与信息密度** | 🟡 强烈建议改 | 每条 3~4 行不换气。HR 初筛平均一条只看 5~8 秒，技术面试官也是先扫再挑。要"先结论、后弹药"：第一个分句就是这条的价值主张 |
| 3 | **决策感被细节淹没** | 🟡 建议改 | 你简历里最值钱的不是"用了什么"而是"为什么这里用这个"——"三种编排按场景选型""数值全由确定性算法维护"这两个决策点目前埋在句子中间，要提到句首 |

## 二、改写原则（先看这个再看逐条）

1. **每条第一分句 = 价值主张**。面试官只读第一分句也能明白这条在讲什么能力。
2. **每句话都能被代码支撑**。写上去的每个数字都要能当场指认出处；反之，代码撑不住的效果数字（"延迟降低 80%"）一律不写——参考 `07_RESUME_HIGHLIGHTS_AND_INTERVIEW_GUIDE.md` §四的数字红线。
3. **动词选"设计/构建/将 X 解耦为 Y"，不选"使用/基于/借助"**。前者是决策者视角，后者是使用者视角。
4. **细节留 30%，别写满**。简历写七分，面试讲十分——每条 bullet 留一两个"钩子"让面试官来问（比如写"三项校验"不展开是哪三项），你答的时候才有增量。
5. **一条 bullet 一个主题**。现在"项目概述"一条里挤了场景清单+差异化+闭环三层意思，拆开各自才有力量。

## 三、逐条深度改写

### 3.1 项目概述

**原文**：
> 面向技术求职者的 AI 面试训练平台，覆盖简历模拟面试、专项训练、JD定向备面、知识卡片、算法题、多轮问答六类场景。区别于一次性问答工具：每轮训练经 LLM 逐题评估，沉淀为长期画像与向量记忆，驱动掌握度更新与 SM-2 复习调度，问答总结与高频错点自动回写知识库，形成「训练→评估→记忆→复习→再出题」的自进化闭环。

**逐句诊断**：
- 场景罗列放在最前面，是这条里信息价值最低的部分（六类场景 HR 看不出差别，技术面试官更关心闭环）
- "区别于一次性问答工具"是个好的对比框架，但被动句式弱化了它
- 闭环描述是整条的灵魂，却排在最后

**改后（信息密度版）**：
> **项目概述**：AI 面试训练系统，核心差异化是「训练→评估→记忆→复习→再出题」的跨会话自进化闭环——每轮训练经 LLM 逐题评估，沉淀为长期画像与向量记忆，驱动 SM-2 复习调度与下一轮个性化出题；问答总结与高频错点自动回写知识库。覆盖简历模拟面试、专项训练、JD 定向备面、知识卡片、算法题、多轮问答六类场景。

**改后（可读性版，适合 HR 初筛为主的投递）**：
> **项目概述**：把"一次性 AI 问答"升级为"越练越懂你的训练系统"：每轮训练的评估结果沉淀为长期画像，驱动复习调度和下一轮出题，形成跨会话自进化闭环。覆盖模拟面试、专项训练、JD 备面等六类场景。

**面试展开路线**（被问到这条时）：
1. 30 秒版：闭环五环节各一句话（训→评→记→复→再）
2. 60 秒版：+ "区别于 ChatGPT 的三个词：记忆、调度、可控"
3. 深挖入口：面试官挑哪个环节，就进对应模块（评估→模块A；记忆→模块B；复习→模块B的SM-2；再出题→模块E）
4. 高频追问 Top3：「进化发生在哪」「和 ChatGPT 模拟面试有什么区别」「闭环里哪个环节最难」→ 题库 A 组

### 3.2 技术栈

**原文**：
> 后端 FastAPI + LangGraph/LangChain/LlamaIndex；存储 SQLite(WAL) + Qdrant(向量检索) + Redis(缓存)；前端 React 19 + TypeScript + Tailwind CSS；全链路 SSE 流式

**诊断**：结构好，不用大动。两个微调建议：
- "LangGraph/LangChain/LlamaIndex" 三件套并列会 100% 引来"为什么三个都用，不冗余吗"——这其实是你的送分题（三者不同层：状态机/模型接入/索引检索），但简历上可以主动把边界写出来，显得更清醒
- SQLite(WAL) 是亮点保留；可补 "numpy/Qdrant 双后端"一词，这是真实的架构决策点

**改后**：
> **技术栈**：后端 FastAPI + LangGraph(状态机) + LangChain(模型接入) + LlamaIndex(索引检索)；存储 SQLite(WAL) + Qdrant/numpy 双后端向量库 + Redis 缓存；前端 React 19 + TypeScript + Tailwind CSS；全链路 SSE 流式。

**面试展开路线**：
- 必问「三件套为什么都用」→ 一句话："三者不在同一层——LangGraph 只管简历面试的状态机，LlamaIndex 只管知识库检索，LangChain 只提供统一模型抽象配合自研渠道池"
- 必问「为什么 SQLite 不用 PG」→ "规模决定的理性选择 + repository 模式留了迁移口子"（题库 G 组）
- 必问「双后端是什么」→ "裸开发 numpy、Docker 部署 Qdrant，500 向量/用户的规模刻意不上重型基建"

### 3.3 长期记忆与用户画像

**原文**：
> 实现 Mem0 风格画像更新，LLM 从面试记录抽取薄弱点/优势/思维模式，以 ADD/UPDATE/IMPROVE/NOOP 操作式合并进长期画像；掌握度、SM-2 复习间隔等数值全由确定性算法维护；向量记忆按 0.75 相似度去重、14 天半衰期时间衰减，连续 3 次高分的薄弱点自动更新降级为低优先级。

**逐句诊断**：
- 内容全部准确（已核对 memory.py / spaced_repetition.py / vector_memory.py）
- 最大问题："数值全由确定性算法维护"是这条最能体现架构判断力的设计红线，被埋在句子中间一笔带过
- "自动更新降级为低优先级" 表述拗口，代码里的概念是"毕业"（graduation），口语也更好记

**改后**：
> **长期记忆与用户画像**：设计「语义归 LLM、数值归算法」的两阶段画像更新——LLM 仅负责从面试记录抽取发现并以 ADD/UPDATE/IMPROVE/NOOP 决策合并（Mem0 风格）；掌握度、SM-2 复习间隔等数值一律由确定性算法维护，可解释、可回放。向量记忆按 0.75 相似度语义去重、14 天半衰期衰减（权重封顶 30%），连续 3 次 ≥7 分的薄弱点自动"毕业"退出复习队列。

**为什么这么改**：
- 「语义归 LLM、数值归算法」放句首——这是你所有画像相关追问的总纲，先立论点
- 补了两个防御性细节：衰减"权重封顶 30%"（防追问"老记忆会不会清零"）、毕业条件写全"连续 3 次 ≥7 分"（数字具体化）
- "毕业"比"降级为低优先级"短且形象，面试口播也顺

**面试展开路线**：
1. 先讲总纲（为什么 LLM 不碰数字：稳定性 + 可解释性 + 跨版本可比）
2. 再讲两阶段流程（抽取→合并四操作）
3. 深挖备弹：合并冲突怎么办 / LLM 合并错了怎么恢复（操作日志）/ 0.75 怎么定的 / 为什么是 14 天
4. 高频追问 → 题库 B 组

### 3.4 三种 Agent 编排按场景选型

**原文**：
> 简历面试用 LangGraph 五阶段状态机，interrupt 回路 + SQLite Checkpoint 断点续接，LLM评估与阶段题数上限共同控制推进；专项训练用画像加载→RAG检索→混合生成→质量校验→难度校准流水线；浮动助手为单 Agent + 18 个工具的 Function Calling，用户以自然语言操作全平台，工具结果结构化回填，支持同轮并发与多轮工具链推理。

**诊断**：
- 标题「按场景选型」极好，直接展示的是决策力而非工具使用，保留
- 内容准确（五阶段枚举/interrupt_before/SqliteSaver/18 个 TOOLS/三种编排均已核对）
- 缺一个"选型标准"的总起句——三个场景并列罗列，读者要自己归纳出"为什么不同"，应该替读者说出来
- "interrupt 回路" → "interrupt 断点等待作答" 更直白

**改后**：
> **三种 Agent 编排按场景选型**（流程形状决定编排形式）：简历面试是有环状态流程→LangGraph 五阶段状态机，interrupt 断点等待作答 + SQLite Checkpoint 持久化，服务重启可续接，LLM 评估信号与阶段题数硬上限双保险控制推进；专项训练是单向流水线→画像加载→RAG 检索→混合生成→质量校验→难度校准，零状态机开销；浮动助手是开放指令→单 Agent + 18 工具 Function Calling，结构化回填 + 同轮并发 + 多轮工具链推理，刻意不引入多 Agent 复杂度。

**为什么这么改**：
- 括号里六个字「流程形状决定编排形式」就是这条的选型标准，也是面试答题的第一句
- 每个场景前加了"流程形状"标签（有环状态流程/单向流水线/开放指令），三分法一目了然
- "双保险"点出 LLM 决策 + 确定性兜底的设计模式（这个模式在你项目里反复出现，面试要串起来讲）
- "刻意不引入多 Agent 复杂度"——把"没做多 Agent"从缺陷变成决策

**面试展开路线**：
1. 总纲：流程形状决定编排形式（有环→状态机；单向→流水线；开放→工具箱）
2. 每种展开一层：interrupt+checkpoint 断线续接全流程 / 流水线五阶段 / 18 工具怎么防选错
3. 深挖备弹：MemorySaver→SqliteSaver 演进故事 / 为什么不用一个万能 ReAct Agent / 状态机怎么防死循环
4. 高频追问 → 题库 C 组

### 3.5 个性化 RAG 与可控出题

**原文**：
> 检索按薄弱点拆成多路并发查询，经 RRF(k=60) 融合、0.85 余弦语义去重、可选 Cross-Encoder 重排，索引按文件哈希比对增量重建；出题按掌握度规划难度分布，种子题库与 LLM 混合生成并流式逐题推送，语义重复/薄弱点覆盖/难度分布三项校验不合格的题仅局部重生成；自建 RAGAS 离线评测集，Hit@8 达 __%、MRR __、忠实度 __，评测历史入库支持跨 run 对比。

**诊断**：
- 这条是全简历技术密度最高的一条，数字全部核实无误
- 结构其实是三层：检索链路 / 生成控制 / 评测验证——但一逗到底读不出层次
- `__` 空白必须处理（见 §四）
- 缺"难度校准"这个真实存在的亮点（离线锚点 k-NN 修正 LLM 自报难度）——你写了"难度校准流水线"在 3.4，这里的"按掌握度规划难度分布"可以补上校准闭环

**改后**：
> **个性化 RAG 与可控出题**：检索层——按薄弱点拆多路并发查询，RRF(k=60) 融合、0.85 余弦语义去重、可选 Cross-Encoder 重排，索引按文件哈希 diff 增量重建；生成层——按掌握度规划难度分布，种子题库与 LLM 混合生成、流式逐题推送，语义重复/薄弱点覆盖/难度分布三项校验，不合格仅局部重生成，另以离线难度锚点 k-NN 校准 LLM 自报难度；评测层——自建 RAGAS 风格离线评测集，Hit@8 __%、MRR __、忠实度 __，评测历史入库支持跨 run 对比。

**为什么这么改**：
- 「检索层/生成层/评测层」三个标签把一逗到底切成三段，10 秒能扫完结构
- 补"难度锚点 k-NN 校准"：这是个好故事（不信 LLM 自报难度，用确定性方法校准），且你已经写了校准却没说怎么校
- "文件哈希比对" → "文件哈希 diff"，更准确（manifest diff 出增/改/删）

**面试展开路线**：
1. 按三层讲：检索（拆融去排）→ 生成（规划-混合-校验-校准）→ 评测（在线三无、离线八有）
2. 最好的故事在评测层：discrimination→coverage 指标重构（题库 F 组有完整展开）
3. 深挖备弹：RRF 为什么不用分数加权 / 0.85 vs 0.75 两个阈值为什么不同 / 局部重生成怎么回填失败原因
4. 高频追问 → 题库 E、F 组

## 四、`__` 空白数字的处理路径

**路径一（首选）：填真实值。**
```bash
# 跑离线基准（k=8 对应简历里的 Hit@8）：
python -m backend.eval.rag_benchmark --top_k 8
# 或走前端 RAG Dashboard 触发评测，结果在评测历史 / rag_eval_runs 表
```
填数三原则：① 记住口径（哪个 topic、k 多少、strict 与否），面试必被追问；② 数字别取整到可疑（"85%"比"84.7%"更像编的）；③ 同一指标简历、口述、Dashboard 三处一致。

**路径二：数字不理想 → 换定性表述**（§3.6 的降级版）。"评测框架真实存在且历史入库"本身就是超过大多数候选人的亮点，宁可定性也不虚构。

**路径三（禁止）：编一个。** 面试官现场让你解释 MRR 是怎么从 0.x 提升的，编的数字撑不过第二个追问。

> - **「语义归 LLM、数值归算法」的长期记忆设计**：LLM 仅做发现抽取与 ADD/UPDATE/IMPROVE/NOOP 合并决策，掌握度与 SM-2 复习间隔由确定性算法维护；向量记忆 0.75 语义去重 + 14 天半衰期 + 连续高分自动毕业。

### 5.4 90 秒口述版（自我介绍讲到项目时）

> 我做了一个 AI 面试训练系统，解决的问题是：市面上的 AI 模拟面试都是一次性的，练完就忘，下次还从零开始。我的系统把每轮训练闭环起来——LLM 逐题评估后，薄弱点经 Mem0 风格的两阶段更新沉淀进长期画像，SM-2 算法安排复习，下一轮出题时装配画像、掌握度、知识库三层上下文，所以系统是越练越懂你。
> 工程上有三个我比较得意的决策：一是「语义归 LLM、数值归算法」——画像合并让 LLM 决策，但掌握度和复习间隔全是确定性公式，可解释可回放；二是三种场景用了三种编排，流程形状决定编排形式——有环的简历面试用 LangGraph 状态机加 checkpoint 断点续接，单向的专项训练就是普通流水线，开放的助手是单 Agent 加 18 个工具；三是出题质量不靠祈祷靠校验——语义重复、薄弱点覆盖、难度分布三个校验器，不合格的题局部重生成，另外自建了在线加离线两层 RAG 评测，上线后还靠它发现并重构过一个方向反了的指标。
> 技术栈是 FastAPI、LangGraph、LlamaIndex、React 19，存储 SQLite 加 Qdrant，全链路 SSE 流式。

## 七、数字速查卡（面试前 10 分钟过一遍）

- 六类场景 · 五阶段 · 三种编排 · **18** 个助手工具 · 三项校验 · 三层上下文
- RRF k=**60** · chunk 去重 **0.85** · 记忆去重 **0.75** · 半衰期 **14 天**（权重封顶 **30%**）
- 每用户向量上限 **500** · 索引缓存 **50** 个 / TTL **1h** · live 会话 TTL **2h**
- SM-2 ease_factor 下限 **1.3** · 毕业 = 连续 **3** 次 ≥ **7** 分 · 掌握度 = 难度/5 × 得分/10
- 渠道冷却 **60s** / 三振 · 熔断 **5** 败跳闸 / **60s** 半开 · SSE 心跳 **30s** / 进度 **200** 字符
- JWT HS256 **7 天** · SQLite WAL + busy_timeout **5s** · **16** 张表 · **15** 个 router
- ⚠️ 待填：Hit@8 / MRR / 忠实度 / 薄弱点覆盖率 → `python -m backend.eval.rag_benchmark --top_k 8`

## 八、表达红线（面试绝不能说的）

1. **不要说浮动助手是"多 Agent"** —— 它是单 Agent + 18 工具，说成 multi-agent 会被一路追杀到自相矛盾。
2. **不要把两套评测指标放在一起比** —— 在线 relevance ~0.45-0.65 是健康区间，别拿去和 RAGAS 的 0.8+ 比"为什么这么低"。
3. **不要说掌握度是 LLM 打的分** —— 确定性公式是你的设计红线，说反了全条崩塌。
4. **不要虚构效果数字** —— 没有基准报告支撑的百分比一个都别说；被问到就讲评测框架和定性结论。
5. **不要把"没上 PG/Milvus/多 Agent"说成"没来得及"** —— 全部是主动决策：规模不配重型基建，但留了迁移接口。

## 1. 最终结论

本轮针对后端、前端、数据存储、向量索引、Docker 配置和测试体系进行了全量审查与修复。审查过程中确认的 P0/P1/P2 问题均已落实代码修复和回归测试；当前没有已知的、可复现的高风险阻断问题。

这不是“绝对不存在任何潜在缺陷”的保证。真实外部模型、Qdrant、Nginx、Docker 多副本和浏览器级长连接仍需要部署环境验收；这些边界在第 7～8 节单独列出。

## 3. 关键一致性不变量

后续维护代码时，应继续遵守以下不变量；它们比单个函数的实现细节更重要：

1. **权威写入必须带所有权证明。** 长任务、评测、同步、Resume turn 和 HALF_OPEN probe 的完成/失败回报必须携带当前 claim token 或 permit；无 token 的迟到回报不能改变当前 generation。
2. **重试必须幂等。** 同一用户、会话和业务步骤的重复请求只能重放结果或更新同一条记录，不能重复推进画像、SR、知识演进或指标。
3. **文件先完整、后替换。** 上传和 manifest 更新先写临时文件并验证，再使用原子替换；失效、索引重建和 Topic 元数据更新失败时必须能回滚或进入可诊断的重试状态。
4. **缓存不是事实来源。** live store、进程 LRU、队列状态和前端 state 只用于加速；SQLite、用户文件和 Qdrant 中的 token/fingerprint/版本才是恢复依据。
5. **客户端状态必须有请求代次。** 任何会随 Topic、session、job 或用户变化的异步响应，落地前都要验证当前 generation/身份；组件卸载必须释放流和对象 URL。
6. **生产配置默认 fail closed。** 认证 secret、owner 初始口令、Qdrant key、CORS 和代理信任边界缺失时，生产启动应失败，而不是仅记录 warning。

## 4. 持久化与迁移变更

### 4.1 Sessions 与任务 claim

`sessions.meta` 现在承载 evaluation、sync、Resume turn 的 claim token、claim 时间、同步目标快照、步骤结果和完成 marker。所有 claim 都以用户 ID、会话 ID 和 token 作为更新条件，过期 worker 的提交会返回失败而不会覆盖新 generation。

Resume transcript 使用 token-fenced 的原子提交；`chat` 和 `end` 共用用户/会话生命周期锁。长图调用期间 heartbeat 会续租，SQLite 短暂繁忙时按 TTL 保护窗口重试。

### 4.2 RAG metrics

`rag_metrics` 的逻辑唯一键为：

```text
(user_id, session_id, stage)
```

启动迁移会按 `created_at`、`id` 删除旧重复行，保留最新记录，并创建 `idx_rag_metrics_user_session_stage` 唯一索引。`save_rag_metrics()` 改为 SQLite 原子 `ON CONFLICT DO UPDATE`；带 evaluation token 的写入同时约束 insert 和 update，旧 worker 不能覆盖新评测结果。

### 4.3 RAG 评测与 QA 幂等记录

- `rag_eval_runs` 增加 claim token 和用户/job 唯一约束，旧重复 job 会在启动时迁移为可追溯的 legacy ID。
- `rag_eval_start_requests` 持久化请求指纹、job 映射、租约和终态响应，支持断线/重启后的重放。
- `qa_ingest_requests` 持久化知识录入的 idempotency key、内容 hash、写入计划和终态响应，防止浏览器重试重复写卡片。

数据库初始化是幂等的，但生产升级前仍应先备份 SQLite 文件及 WAL，并执行 Qdrant snapshot/备份。

### 4.4 用户 ID 与向量迁移

默认用户迁移按 stage/verify/rollback/finalize 分段执行，覆盖 SQLite、用户目录、memory vectors、Qdrant memory payload 和知识库 collection。迁移不会把内部 Resume namespace 或转义后的 Topic namespace 暴露给普通知识列表；校验失败时保留原数据并留下可重试状态。

## 7. 部署验收清单

1. 复制 `.env.example` 为部署环境配置，设置随机的 `JWT_SECRET`、`DEFAULT_PASSWORD`、`QDRANT_API_KEY`，并明确 `APP_ENV=production`、CORS 和 `TRUSTED_PROXY_CIDRS`。
2. 确认旧实例中的 owner 已经改掉公开 bootstrap 密码；生产启动校验不会自动改写存量账号密码。
3. 备份 SQLite 数据库（含 WAL/checkpoint）、用户知识文件和 Qdrant snapshot，再启动自动迁移。
4. 启动 Docker Desktop/daemon 后执行 `docker compose config --quiet`、`docker compose up -d --build`、`docker compose ps`，确认 backend、Redis、Qdrant health 状态。
5. 通过 frontend/nginx 验证登录、知识上传/回滚、Topic 重建、Resume chat/end、QA stream、RAG eval start/status 和断线重试。
6. 对真实 LLM、embedding、reranker 和 Qdrant 做一次成功/超时/401/5xx failover smoke；检查日志中不出现 API key。
7. 上线后保留审计日志、任务终态和迁移 marker，定期演练 SQLite + Qdrant 恢复。

## 8. 当前架构边界

这些是已知设计边界，不是本轮遗漏的已确认 Bug：

- 任务队列、live store、部分索引锁和 channel health 仍有进程内部分；横向扩容到多 worker/replica 前应迁移到 Redis/持久队列/分布式锁。
- SQLite、文件和 Qdrant 的补偿链已经 token-fenced 和可重试，但不是跨存储的分布式 exactly-once；长期可进一步引入 outbox/event table。
- 前端已通过静态门禁，尚无完整 Playwright/component suite；多标签页、断网和浏览器代理行为仍应在 CI 补测。
- 外部 provider 协议、延迟和 Qdrant 实际网络/权限只能通过持续集成探测验证。
- 本次环境没有 Docker daemon 和 Nginx，因此真实镜像启动、Nginx 配置语法和跨服务 SSE 尚未在本机执行。

## 0. 这个项目是什么

AI 面试训练系统。核心不是「一次性问答」，而是一个跨会话闭环：

```
训练 → LLM 逐题评估 → 画像更新（Mem0 风格）→ 向量化入库
  ↑                                                    ↓
  └──── 下轮出题融合三层上下文 ←──── SM-2 复习调度 ←────┘
```

后端 FastAPI + LangGraph + LangChain + LlamaIndex；前端 React 19 + Vite + Tailwind v4。

## 1. 三条训练链路（各自编排不同）

`InterviewMode` 枚举（`models.py`）有 4 个成员，但 **`RECORDING` 已随 ASR 全链路下线**（commit `688c0e2`），
后端不存在创建路径，仅在历史查询与前端筛选项里保留读取存量数据的兼容代码。**当前活跃的是三条**：

| 链路 | 入口 | 编排方式 |
|---|---|---|
| 模拟面试 | `graphs/resume_interview.py` | **唯一的 LangGraph `StateGraph`**，五阶段状态机 + `interrupt_before=["wait"]` + SQLite Checkpoint |
| 专项训练 | `graphs/topic_drill.py` → `graphs/drill_pipeline.py` | 普通 async 流水线：画像加载 → RAG → 混合生成 → 三项校验 → 难度校准 |
| JD 备面 | `graphs/job_prep.py` | 普通 async 流水线：JD 分析 → 出题 → 评估 |

复习（SM-2 到期项）**不是独立场景** —— `graphs/review.py` 是复盘生成器，到期复习内容并入专项训练出题。

### 五阶段状态机

`InterviewPhase`：`greeting → self_intro → technical → project_deep_dive → reverse_qa → end`。
推进由 LLM 评估 + 阶段题数上限共同控制。Checkpoint 落 `data/checkpoints.db`，重启后可续接。

### 浮动助手

`assistant.py` —— **单 Agent + Function Calling，18 个工具**（`TOOLS` 常量，实测 `len(TOOLS) == 18`）。
支持同轮并发调用与多轮工具链推理。**不是 multi-agent**，描述时不要说成多智能体。

## 2. RAG 检索管线（本轮重构，两条业务线已统一）

### 2.1 统一入口

`graphs/rag_retrieval.py` 提供两个公开入口，共享同一实现 `_retrieve_fused`：

```python
retrieve_for_drill(topic, ...)       # 单 topic × 多薄弱点
retrieve_for_job_prep(topics, ...)   # 多 topic × query（笛卡尔积扇出）
```

**变更前**：JD 备面没有融合/去重/重排，只是把各 topic 的原始检索结果拼接，且用固定字符串
`"核心知识点 面试常见问题"` 作 query —— JD 只决定查哪个库，不决定查什么。现已全部接入。

### 2.2 管线阶段

```
扇出（topic × query，并发，信号量限流）
  → RRF 融合（k=60）
  → 语义去重（余弦 ≥ 0.85）
  → Rerank 重排（可选，未配置则 status="off"）
  → 检索质量指标（embedding-only，零 LLM 成本）
```

### 2.3 三条并发正确性约束（改动时务必保持）

1. **`asyncio.gather` 按提交顺序返回**，chunk 与其 metadata 靠这个对齐。换成 `as_completed` 会错位。
2. **`return_exceptions=True` + 逐槽位判断**：单个 topic 索引缺失只让那一槽降级为 `[]` 并记入
   `failure_details`（带 topic 标签），其余结果照常融合。
3. **queries 与 topics 在扇出前去重**。RRF 是按路加和的，同一 ranking 进入两次会让该 chunk 分数翻倍
   —— 等于自己给自己投票。（这正是本轮修掉的一个缺陷：JD 把同一段文本同时作 query 和 fallback 传入，
   而 `<3 queries → 追加 fallback` 的补齐逻辑又加了一遍。）

### 2.4 语义去重的顺序依赖（重要）

`_semantic_dedup` 是**贪心**的：先到的 chunk 被保留，后来的只要与已保留项余弦 ≥ 阈值就丢弃。
因此**保留哪一条取决于输入顺序**。当前顺序由 RRF 分数决定（确定性），所以结果可复现。
若将来把 dedup 挪进并发段、或让输入顺序随完成顺序变化，同样的检索会在不同请求返回不同 chunk。

### 2.5 两个 0.75 / 0.85 阈值不要混淆

| 阈值 | 位置 | 用途 |
|---|---|---|
| **0.85** | `rag_retrieval.py` `SIMILARITY_THRESHOLD` | RAG 检索结果的**块级**去重 |
| **0.75** | `vector_memory.py` `SIMILARITY_THRESHOLD` | 长期记忆的**薄弱点**语义去重 |

## 3. 画像更新机制（Mem0 风格两阶段）

真相源是 `data/users/{uid}/profile/profile.json`。向量库只是语义召回索引，**不是真相源**。

### 3.1 两阶段

入口 `memory.py` `update_profile_after_interview` → `llm_update_profile`：

- **阶段 1 Extract**：LLM 从 transcript + 评分提取本次新发现。
- **阶段 2 Update**：把**带索引的存量画像 + 新发现**再喂 LLM，逐条决策操作。

### 3.2 四种操作分布在两个字段（写 prompt schema 时注意）

```python
ops["weak_point_ops"]  → ADD / UPDATE / NOOP
ops["improvements"]    → IMPROVE（独立数组，不是 action 的第四个取值）
```

| 操作 | 效果 |
|---|---|
| ADD | 追加，`mastery=20`、`times_seen=1` |
| UPDATE | 改写描述、`times_seen+1`、刷新 `last_seen` |
| NOOP | 语义重复，不动 |
| IMPROVE | 标 `improved=True`，移出活跃薄弱点 |

**降级**：LLM 返回 JSON 解析失败 → `_resolve_new_weak_points` 用向量余弦 0.75 做确定性合并。
智能优先、确定性兜底。

### 3.3 三个工程细节（面试价值高于算法本身）

**索引重映射**：LLM 那次调用可能耗时几十秒，期间实时更新会往 `weak_points` 追加，**LLM 返回的下标就失效了**。
代码不信任下标位置，而是拿快照的 point 文本回查真实位置（`_apply_memory_ops` 内的 `_resolve`）。

**读写分离**：慢的 LLM 调用在锁**外**；应用变更时在 `profile_transaction` 内**重新加载**画像，纯同步无 await。
不会用几十秒前的快照覆盖并发写入。

**幂等**：`operation_id` + `_applied_operations` 表，重试不重复计数。

## 4. 掌握度与 SM-2（注意两个「掌握度」的区别）

这是最容易讲错的地方。项目里有**两个**掌握度，确定性程度不同：

### A. 领域掌握度 `topic_mastery` —— 公式确定，但输入来自 LLM

```python
# memory.py  _update_mastery
merged = old_score * (1 - session_weight) + new_score * session_weight
#                                            ^^^^^^^^^ 评估阶段 LLM 产出
```

### B. 薄弱点掌握度 `wp["mastery"]` —— 真正零 LLM

```python
# spaced_repetition.py  update_weak_point_sr
contribution = (difficulty / 5) * (score / 10) * 100     # 纯算术
wp["mastery"] = round(0.7 * prev_mastery + 0.3 * contribution)
```

**说「掌握度零 LLM 参与」时必须限定到 B**，否则被问「那个 score 谁给的」会自相矛盾。

### 毕业判定：连续，不是累计

```python
new_sr["consecutive_high"] = (prev_high + 1) if score >= 7 else 0   # 未达标即归零
if wp["sr"]["consecutive_high"] >= 3:
    wp["improved"] = True
```

**为什么用独立的 `consecutive_high` 而不复用 `repetitions`**：后者计的是 SM-2 **通过**次数（≥6 分），
不是高分次数。复用会让一长串 6 分的及格在第一次真高分时误毕业。代码注释里专门写了这点。

毕业后：`drill_pipeline` 出题与 `get_due_reviews` 都跳过该点，同时往 `strong_points` 写一条
「已掌握: X」（带去重，防止重复毕业堆积）。

## 5. 关键常量表（改动前先读 CLAUDE.md 的权衡说明）

| 常量 | 值 | 位置 |
|---|---|---|
| RRF 平滑常数 | 60 | `rag_retrieval.py` `RRF_K` |
| RAG 块去重阈值 | 0.85 | `rag_retrieval.py` `SIMILARITY_THRESHOLD` |
| 记忆语义去重阈值 | 0.75 | `vector_memory.py` `SIMILARITY_THRESHOLD` |
| 时间衰减半衰期 | 14 天 | `vector_memory.py` `TIME_DECAY_HALF_LIFE` |
| 衰减权重上限 | 0.3（最旧仍保 ~70%） | `vector_memory.py` `TIME_DECAY_WEIGHT` |
| 每用户向量上限 | 500 | `vector_store/base.py` `MAX_VECTORS_PER_USER` |
| 索引缓存 TTL / 上限 | 1 小时 / 50 | `indexer.py` `_INDEX_CACHE_TTL` / `_INDEX_CACHE_MAX_SIZE` |
| 检索超时 | 60s | `indexer.py` `_RETRIEVAL_TIMEOUT` |
| Embedding 并发 | 2 | `rag_retrieval.py` `_EMBED_CONCURRENCY` |
| 熔断恢复窗口 | 60s | `embedding_tasks.py` `recovery_timeout` |
| SM-2 ease factor 下限 | 1.3 | `spaced_repetition.py` `sm2_update` |

> **Embedding 并发为什么是 2**：检索扇出与 dedup 阶段命中**同一个** embedding key，5 路并发曾触发
> DashScope 单 key 限流，导致每个请求拖到超时、dedup 静默失效。这个信号量在扇出上仍然生效 ——
> 扇出变大只会排队（延迟增加），不会突破并发上限。

## 6. JD 备面链路（本轮重点修复，与旧文档差异最大）

旧文档对这条链路的描述基本已失效。当前实现：

### 6.1 会话不带 topic

JD 天然跨多个知识领域，`sessions.topic` 列为 NULL。匹配到的 topic 集合在创建会话时冻结进
`meta.topics`；参考答案/提示接口的 `topic` 参数**可选**，为空时从会话元数据解析检索范围，
老会话回退到重新匹配。

### 6.2 JD → topic 匹配是 token 级的

`job_prep.py` `_match_topics_in_text`：ASCII 整词匹配、CJK 子串匹配。
朴素的 `in` 会让 `"java"` 命中 `"javascript"`，且哈希键名/中文名的自建知识库永远匹配不上。

**检索侧与写回侧共用同一匹配函数，但语义不同**：
- 检索侧（`_match_jd_topics`）无命中时回退到前几个 topic —— 只读，安全。
- 写回侧（`routers/interview.py` `_match_jd_to_topics`）**无命中即为空**，绝不回退 ——
  写回是往知识库里写内容，回退会污染无关领域。

### 6.3 知识缓存键按共享前缀取摘要

preview 与出题看到完整 JD，评估步骤只有 `preview["jd_excerpt"]`（截断 1500 字）。
按原文取 sha256 会让评估步骤**必然** miss 缓存并重跑整套多 topic 检索。
现按前 1500 字（`_JD_QUERY_CHARS`，与 `jd_excerpt` 截断长度绑定）取摘要，三步共享一次检索。

### 6.4 简历上下文用 retriever，不用 query engine

`indexer.py` `retrieve_resume_chunks` 取原始 chunk。
旧的 `query_resume` 走 query engine，多一次 LLM 调用，且可能返回字面量 `"Empty Response"` / `"None"`
—— 这两个字符串会被当作简历**内容**塞进 prompt。检索为空时 `resume_used` 如实返回 `False`，
不再一边显示「简历联动已启用」一边让模型凭空编经历。

## 7. 评测体系：两套，不可比

这是最容易被追问穿的地方，务必分清。

| | 在线（`rag_metrics.py`） | 离线冻结集（`data/eval/rag_queries.json`） |
|---|---|---|
| 指标 | relevance / coverage / diversity | Hit@K / MRR / nDCG |
| 金标 | 无 | 人工标注，55 例 |
| 成本 | embedding-only，零 LLM | 无生成，只评检索 |
| 量纲 | 天然 0.45–0.65（短 query 比长文档块） | Hit@3 92.7% |

**两者放一起比会得出「检索质量只有 50 分」的错误结论**，所以前端每个指标按自己的分档区间上色
（`frontend/src/lib/metrics.ts` `METRIC_SPEC`），不用统一阈值。

另有第三套 `rag_eval.py`（RAGAS，LLM 合成金标），与上面两套都不同。**讲冻结集时不要说 RAGAS**。

冻结集分布（实测）：共 55 条，`semantic_gap` 16 / `long_tail` 12 / `term_ambiguity` 11 /
`cross_chapter` 6 / `direct` 10。

> ⚠️ `backend/eval/reports/` 当前为空。评测数字（Hit@1 76.4% / Hit@3 92.7% / Hit@5 100% /
> MRR 0.86 / p50 230ms）的实跑记录保存在 18 号文档。**投递前建议重跑一次留存报告**
> （`scripts/eval_rag.py`），否则被要求现场复现时会很被动。

## 9. 部署视角差异（分析代码前先确认目标环境）

compose 给 backend 注入了 `VECTOR_BACKEND=${VECTOR_BACKEND:-qdrant}` + `QDRANT_URL=http://qdrant:6333`：

- **Docker / 服务器部署默认走 Qdrant**：知识库按 `kb_{user}_{topic}` 分 collection，
  记忆库单 collection 多租户，qdrant-only **不降级**。
- **裸 `uvicorn` 本地开发**默认 numpy / 本地 persist。

两条路径的构建、增量、失败语义**并不相同**。讨论索引与检索行为时必须先说清是哪种环境。

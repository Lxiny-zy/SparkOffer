# Part 2 · 06 — 流式与上下文工程

> LLM 应用的体验，一半在"流式推送够不够顺"，一半在"塞进上下文窗口的内容选得对不对"。本章讲透 **SSE 流式 + 心跳保活 + reasoning 模型处理 + 增量 JSON 解析**（体验层），以及 **token 预算装配 + prompt 前缀缓存 + 上下文压缩**（上下文工程层）。

---

## 1. SSE：服务器推送的流式骨架

### 1.1 是什么

**SSE（Server-Sent Events）** 是基于 HTTP 的**服务器→客户端单向流式**协议。响应头 `Content-Type: text/event-stream`，body 是一串 `data: {...}\n\n` 的帧，客户端边收边处理。

### 1.2 为什么用 SSE 而不是 WebSocket

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器→客户端） | 双向 |
| 协议 | 纯 HTTP，天然过 nginx/CDN | 需要 Upgrade 握手 |
| 实现 | 极简（`StreamingResponse`） | 要管连接生命周期 |
| 适用 | **LLM token 流式推送** | 实时双向（聊天室、协作） |

LLM 场景是"服务器把生成的 token 不断推给前端"——**典型单向**，SSE 完美契合，且实现/部署都更简单。本项目所有流式端点（出题、答题、助手、解题）都用 SSE。

### 1.3 本项目的 SSE 封装（`utils/sse_helpers.py`）

```python
def sse_event(data: dict) -> str:
    return f"data: {json.dumps(data, ensure_ascii=False)}\n\n"   # 一帧

def streaming_response(generator):
    return StreamingResponse(generator, media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

- `X-Accel-Buffering: no`：**关键**——告诉 nginx **别缓冲**这个响应，否则 nginx 会攒一批再发，流式就失效了（前端要等很久才一次性收到）。
- `ensure_ascii=False`：中文直接输出，不转 `\uXXXX`。

事件类型约定：`progress`（进度）/`token`（可见 token）/`pipeline_stage`（阶段计时）/`question`（出题）/`question_update`（修复/校准后替换）/`reasoning`/`action`（前端动作）/`ping`（心跳）/`done`/`error`。

## 2. 心跳保活：根治"流式被代理掐断"

### 2.1 问题

流式连接如果**一段时间没有任何字节**，nginx（`proxy_read_timeout`）和 httpx（read timeout）会认为连接死了，直接掐断 → 前端白屏。什么时候会"字节静默"？
1. LLM 还在排队/首 token 未出；
2. **推理模型在"思考"**——这是最坑的（下一节专讲）；
3. 工具调用/检索在跑（几十秒无输出）。

### 2.2 解法：idle ping + 进度心跳

`iter_llm_stream`（`sse_helpers.py:110-164`）和各端点的做法：

- **idle ping**：`asyncio.wait_for(下一个chunk, timeout=30s)`，30s 没等到任何 chunk 就 yield 一个 `ping` 事件——给连接"打个字节"，刷新 nginx 计时器。`IDLE_HEARTBEAT_SECONDS=30`。
- **进度心跳**：流式生成时每累积 `PROGRESS_CHAR_INTERVAL=200` 字符推一个进度事件（"已生成 N 字"）。
- 工具执行/同步阻塞任务：每 5-15s 推 ping（`stream_blocking_sse`、assistant 工具循环）。

## 3. Reasoning 模型流式处理（一个真实的坑）

### 3.1 问题本质

推理模型（gpt-5.x / o-系 / DeepSeek-R1）在"思考阶段"会**持续吐 chunk，但这些 chunk 的 `content` 是空的**——真正的思考内容被网关塞在 `additional_kwargs` 的 `reasoning_content`/`reasoning` 字段里。

后果：裸 `async for chunk in llm.astream(...)`——
- chunk 在稳定到达，所以 **idle ping 不触发**（不是真 idle）；
- 但 `chunk.content` 是空的，所以 **token 也不推**；
- 结果流"看起来活着但一个字节没发"，直到 httpx/nginx read timeout → 白屏。

### 3.2 解法（`sse_helpers.py` 的 `chunk_reasoning` + `iter_llm_stream`）

1. `chunk_reasoning` 从 `additional_kwargs` 里把思考增量抠出来（多种 key 容错：`reasoning_content`/`reasoning`/任何含 reason/think 的 key）。
2. `iter_llm_stream` 把流统一成 `(kind, text)` 三类：
   - `"token"`：可见答案增量；
   - `"reasoning"`：思考增量，**按 ~3s 批量转发**（`REASONING_KEEPALIVE_SECONDS`）——既让流不静默、又不把每个微小思考 delta 都刷出去；
   - `"idle"`：30s 真没动静 → 调用方推 ping。

```python
chunk = await asyncio.wait_for(aiter.__anext__(), timeout=idle_timeout)
r = chunk_reasoning(chunk)            # 思考增量
if r: rbuf += r; (每3s) yield ("reasoning", rbuf)
t = chunk_text(chunk)                 # 可见 token
if t: yield ("token", t)
```

3. `chunk_text` 还兼容 content 是 **list of blocks**（`[{"type":"text","text":...}]`）的网关——裸 `accumulated += chunk.content` 遇到 list 会 `TypeError`，这里统一抽成字符串。

> **面试金句**：「我踩过一个推理模型的坑——思考阶段 chunk 一直来但 content 是空的，裸 astream 既不触发 token 也不触发 idle，流会字节静默到超时白屏。我写了个统一的流式循环 `iter_llm_stream`，把思考增量从 `additional_kwargs` 抠出来按 3 秒批量转发当心跳，read timeout 还故意设得比 nginx 高，让超时只由一层兜。」**这是非常能体现实战经验的细节。**

## 4. 增量 JSON 解析：边流边渲染（"30 秒→3 秒"的关键）

### 4.1 问题

出题让 LLM 返回一个 JSON 数组（10 道题）。如果等整个数组生成完再 `json.loads`，用户要盯着空白屏等 LLM 把 10 道题全吐完（几十秒）。能不能**生成一道、渲染一道**？

### 4.2 解法：括号深度状态机（`utils/stream_parser.py`）

`extract_complete_objects(partial_json)` 从**不完整**的流式文本里抠出**已经完整的 JSON 对象**：

```python
depth = 0; in_string = False; escape = False; obj_start = -1
for i, ch in enumerate(cleaned):
    # 处理转义和字符串内的字符（字符串里的 { } 不算结构）
    if ch == '"' and not escape: in_string = not in_string
    if in_string: continue
    if ch == "{":
        if depth == 0: obj_start = i
        depth += 1
    elif ch == "}":
        depth -= 1
        if depth == 0:                       # 一个完整对象闭合了
            obj = json.loads(cleaned[obj_start:i+1])
            objects.append(obj)
```

核心是一个**状态机**：用 `depth` 追踪花括号嵌套层数，`depth` 归零时就拿到一个完整对象。还正确处理了：
- **字符串内的 `{}`**（`in_string` 标志）——题面里的花括号不能误判为结构；
- **转义符** `\`；
- 开头的 ```json 围栏剥离。

### 4.3 在出题管道里怎么用（`drill_pipeline._stage_generate`）

```python
async for kind, delta in iter_llm_stream(llm, messages):
    if kind in ("idle", "reasoning"): yield ping; continue
    accumulated += delta
    objects, _ = extract_complete_objects(accumulated)   # 增量解析
    while emitted_count < len(objects):                  # 有新的完整题就推
        q = objects[emitted_count]; q["id"] = ...
        yield sse_event({"type": "question", "data": q})
        emitted_count += 1
```

效果：LLM 每吐完一道题的 JSON，前端就立刻渲染一张题卡——**首屏从"等全部生成"降到"等第一道题"**。配合**种子题池**（先秒出 6 道命中薄弱点的题），首屏几乎瞬时。

### 4.4 兜底

万一增量解析一道都没抠出来（模型没按数组格式吐），最后做一次完整 `_parse_json_response` 兜底；再不行抛错。还强制把题目 `id` 重写成连续整数（种子题占 1..N、LLM 题接续）——**绝不信任 LLM 给的 id**（它可能给 "Q2"、"py-gil-01" 这种字符串，破坏前端和持久化的数字假设）。

## 5. Token 预算上下文装配（`context_assembler.py`）

### 5.1 问题：告别 `[:5000]` 魔法数

各处历史代码用硬编码字符截断（`knowledge_ctx[:5000]`、`history[:30]`）。问题：
- 不同模型上下文窗口不同（8k/32k/128k），固定字符数要么浪费要么溢出；
- 字符数 ≠ token 数（中文 ~1 token/字，英文 ~3.5 字/token）；
- 多块内容（知识/最近题/洞察）该谁多谁少？硬编码没法表达优先级。

### 5.2 token 计数：tiktoken + CJK 启发式

```python
def count_tokens(text):
    enc = tiktoken.get_encoding("cl100k_base")  # 优先用真 tokenizer
    if enc: return len(enc.encode(text))
    return _heuristic_tokens(text)              # 缺失时回退
```

- **tiktoken** 是 OpenAI 的分词器，`cl100k_base` 是 GPT-3.5/4 系编码。它本来就是 langchain-openai 的传递依赖，项目显式 pin 住，避免静默回退。
- **CJK 感知启发式兜底**（`_heuristic_tokens`）：中日韩字符按 ~1.05 token/字、其他按 1/3.5。**故意略微高估**——tokenizer 缺失时宁可"早点截"，绝不溢出真实窗口。

### 5.3 预算解析：取最小窗口

```python
input_budget = window − output_reserve − safety_margin(2000)
```

- `window`：取**所有启用 LLM 渠道里最小的** `context_window`——因为 failover 可能落到最紧的渠道，必须按最紧的预算。
- `output_reserve`：取最大的 `max_tokens`（给输出留够空间）。
- `safety_margin=2000`：吸收模板开销和 tokenizer 漂移。
- 下限 `_MIN_INPUT_BUDGET=4000`：再紧也别给个没法用的预算。

### 5.4 贪心装配（`ContextBudget.pack`）

每个待装配的内容是一个 `Section`，带 `priority`（小=重要）、`required`（永不丢）、`min_tokens`（放不下这么多就整段丢，不留没用的碎片）：

```python
ctx_budget = resolve_input_budget() − count_tokens(固定模板)
packed = ContextBudget(ctx_budget).pack([
    Section("recent",    最近题, priority=2),                  # 防重复，便宜
    Section("knowledge", 知识库, priority=3, min_tokens=200),  # 价值最高
    Section("insights",  历史洞察, priority=4, min_tokens=100),
])
```

算法：required 先全量计入 → 其余按 priority 升序装，装得下就全要、装不下就**按行边界截断**（`_truncate_on_boundary`，不切断 Markdown 表格行/代码行）、连 `min_tokens` 都放不下就整段丢。返回一份 **token 报告**（用了多少/截了哪些/丢了哪些）供 SSE 观测——前端时间线能显示 `ctx 3200/4000 tok（截断 knowledge）`。

`pack_messages` 是它的对话版：保留最近 `keep_last` 条，其余从**旧到新**丢弃直到放得下。

> **面试金句**：「我把所有上下文拼装统一到一个 token 预算装配器：用 tiktoken 量、按优先级贪心装、放不下按行边界截，还产出 token 报告供观测。窗口取所有启用渠道里最小的——因为 failover 可能落到最紧那个。这比到处写 `[:5000]` 魔法数靠谱得多。」

## 6. Prompt 前缀缓存（呼应 02 章）

为了吃到 LLM 网关的 **prompt prefix caching**，简历面试把"跨轮不变的内容"（简历/知识/画像）冻成稳定系统前缀，"每轮才变的"（阶段/已问题）放尾部消息——**前缀逐字节稳定 → 缓存命中 → 多轮更快更省**。详见 02 章 §5。

## 7. 上下文压缩：QA Arena 的滚动摘要（`qa_arena.py`）

### 7.1 问题

QA Arena 是自由多轮问答，对话会越来越长，迟早撑爆上下文窗口。直接截断老消息会丢上下文，全塞进去又超窗。

### 7.2 解法：增量滚动摘要 + map-reduce

- **触发**：历史超过 `COMPRESSION_THRESHOLD=20` 条时启动压缩。
- **增量摘要**：只对**新增的轮次**生成摘要（`INCREMENTAL_COMPRESS_PROMPT`），缓存在 `qa_sessions.context_summary`；新增不足 `SUMMARY_REGEN_INTERVAL=10` 轮就复用旧摘要——避免每轮都重算整段摘要。
- **保留近期**：最近 `KEEP_RECENT=10` 条原文逐字保留（近期上下文最重要）。
- **最终结构**：`系统前缀 + 滚动摘要 + 向量记忆 + 最近10条原文`，再用 `pack_messages` 按 token 预算裁尾。

### 7.3 知识卡导出的 map-reduce

把长对话导出成 Markdown 知识卡时，用**两段式 map-reduce**：对话超 `SINGLE_PASS_BUDGET=40000` 字符就切成 `CHUNK_SIZE=12000` 的块，每块 LLM 提炼笔记（**map**），再合并所有笔记 + 全局摘要（**reduce**）。这是处理超长文本的经典模式——单次塞不下就分而治之。

## 本章小结

- **SSE** 是 LLM 流式的最佳骨架（单向、过代理友好、实现简单）；`X-Accel-Buffering:no` 是 nginx 下流式生效的关键。
- **心跳保活** + **reasoning-aware 流式**根治"思考阶段字节静默→超时白屏"——把思考增量当心跳转发。
- **增量 JSON 解析**（括号深度状态机）实现"生成一道渲染一道"，配种子题池把首屏压到近乎瞬时。
- **Token 预算装配器**用 tiktoken 量、按优先级贪心装、产出可观测报告，取代 `[:5000]` 魔法数。
- **上下文压缩**（增量滚动摘要 + map-reduce）让无限长对话不撑爆窗口。

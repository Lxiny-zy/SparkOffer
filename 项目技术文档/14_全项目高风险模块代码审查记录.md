## 历史问题清单

### P0（历史，已修复）：Docker 默认暴露 Qdrant 和 Backend，Qdrant 默认无鉴权

> 当前状态：backend/Qdrant 均不发布宿主端口，Qdrant 服务端和 backend client 使用同一强 API key，数据服务仅加入 internal 网络。下列位置和影响保留为初审证据，不描述当前 Compose。

初审位置：

- `docker-compose.yml:16-18`：Qdrant REST/gRPC 直接发布到宿主机 `6333/6334`
- `docker-compose.yml:30-31`：backend 直接发布到宿主机 `9001`
- `docker-compose.yml:39-40`：`QDRANT_API_KEY` 默认空
- `backend/config.py:66-68`：`qdrant_api_key` 默认为空

问题：Docker 部署版默认把 Qdrant REST/gRPC 端口和 backend 端口暴露到宿主机网络。Qdrant 中保存 RAG chunks、payload、向量集合；如果宿主机端口对外可达，攻击者可以绕过应用层 JWT，直接读写/删除向量库数据。

影响：训练知识库、简历向量、用户记忆等敏感内容可能被直接读取；collection 可被删除或污染，导致 RAG 检索不可用或被投毒。

已落实：不发布 Qdrant/backend 宿主端口，仅通过 frontend/nginx 暴露 `/api/`；生产环境强制配置 Qdrant API key，并在 Qdrant service 与 backend client 侧同时启用。

### P0/P1（历史代码路径已修复，存量账号需核验）：默认 owner 账号、默认密码、默认 JWT secret 仅告警不阻断

> 当前状态：生产启动会拒绝公开/过短的 bootstrap 密码、JWT secret、Qdrant key 和不安全 CORS。该校验不会改写数据库中已存在的 owner 密码；升级旧实例仍必须在应用内改密并确认旧口令失效。

初审位置：

- `backend/config.py:41-43`：`jwt_secret = "change-me-in-production"`，`default_password = "legend"`
- `backend/main.py:33-48`：启动时只输出 warning
- `backend/main.py:57-58`：启动时自动 `ensure_default_user()`
- `backend/auth.py:67-92`：默认 owner 账号按 `DEFAULT_EMAIL` 稳定创建

问题：服务启动会自动创建默认 owner 用户；如果 `.env` 没改 `DEFAULT_PASSWORD`，默认账号可直接登录。若 `JWT_SECRET` 也保持默认，攻击者还可伪造 JWT。

影响：在非本机部署中，默认 owner 可直接取得全局设置、AI 渠道、审计日志等管理能力。默认 JWT secret 会使认证令牌可被离线伪造。

已落实：生产/Docker 部署在弱安全配置下直接启动失败；仅显式 `APP_ENV=development` 的隔离本机环境允许带告警运行。存量 owner 的密码核验仍属于升级运维步骤。

### P1（历史，已修复）：backend 直连时可伪造 `X-Real-IP` 绕过登录限流

> 当前状态：backend 不发布宿主端口；客户端 IP 从右向左剥离可信代理链，默认仅信任宿主入口网关与固定 frontend 地址。

初审位置：

- `backend/routers/auth.py:29-39`：`client_ip()` 无条件优先信任 `x-real-ip`
- `frontend/nginx.conf:20-24`：nginx 会设置 `X-Real-IP`
- `docker-compose.yml:30-31`：backend 同时直接发布 `9001`

问题：代码注释假设请求一定经过 nginx，因为 nginx 会覆盖 `X-Real-IP`。但 Docker compose 同时暴露 backend 端口，攻击者可直接访问 `:9001` 并自定义 `X-Real-IP`，从而让登录/注册限流按伪造 IP 分桶。

已落实：backend 不直接对公网暴露；仅在直接对端属于 `TRUSTED_PROXY_CIDRS` 时消费 `X-Real-IP` / `X-Forwarded-For`，否则使用 `request.client.host`。

### P1：面试结束与手动同步的副作用幂等不是原子操作，可能重复推进画像/SR/知识写回

位置：

- `backend/routers/interview.py:297-301`：结束评估前读取已有 scores 判断 `already_scored`
- `backend/routers/interview.py:432-462`：topic drill 保存 review 后执行 SR/profile/knowledge，最后才 `mark_session_synced`
- `backend/routers/interview.py:517-538`：JD prep 同样逻辑
- `backend/routers/interview.py:674-722`：`sync_session_side_effects()` 先读 `meta.synced_at`，执行副作用后再标记
- `backend/storage/sessions.py:111-132`：`mark_session_synced()` 是普通 read-modify-write，不是原子 claim

问题：幂等判断是“先读后写”。并发调用 `/interview/end/{session_id}`，或 `/interview/end/{session_id}` 与 `/interview/sync/{session_id}` 并发时，多个请求都可能在 `synced_at` 写入前通过检查，然后重复执行 SR 更新、画像推进、知识库自动沉淀和高频题收集。

影响：同一次训练被计入多次，画像、复习计划、知识库计数失真。这类错误难以通过 UI 发现，后续学习路径会被错误数据长期影响。

建议：增加原子 claim，例如 SQLite `UPDATE ... WHERE synced_at IS NULL` 并检查 `rowcount`；或增加单 session async lock / DB 表 `session_side_effects(session_id,user_id,status)`。`/sync` 和 `/end` 必须共用同一个幂等入口。

### P1：Knowledge 强制重建会先删索引再入队，入队失败仍返回成功

位置：

- `backend/routers/knowledge.py:301-305`：`force=True` 时先 `invalidate_topic_index()`，再 `schedule_index_rebuild()`
- `backend/embedding_tasks.py:250-262`：任务重复或队列满时 `submit()` 返回 `False`
- `backend/embedding_tasks.py:526-548`：`schedule_index_rebuild()` 忽略 `submit()` 返回值，始终返回 task id

问题：全量重建会先删除 Qdrant collection / 本地 cache，然后尝试入队。但如果同 topic 已有任务 active/pending，或队列满，`submit()` 会失败；调用方仍返回“已提交”。

影响：Docker/Qdrant 部署中，collection 可能已被删除，但没有新任务恢复。RAG 检索会退化为空知识库，且 UI 可能误以为重建任务已正常提交。

建议：把 `force` 作为任务参数传给 worker，只有任务真正进入 worker 并拿到 topic build lock 后再执行 invalidation。`submit()` 的 `False` 必须反馈给接口：已有任务返回 409，队列满返回 429/503。

### P1：索引重建期间再次编辑知识文件，可能造成 manifest 与实际向量永久不一致

位置：

- `backend/routers/knowledge.py:130-132`、`147-149`、`170-172`、`215-217`：写文件后调度 rebuild
- `backend/embedding_tasks.py:255-257`：同 task id active/pending 时去重
- `backend/indexer.py:452-500`：Qdrant 增量 diff、嵌入、最后保存 manifest
- `backend/indexer.py:560-575`：全量构建后重新计算并保存 manifest
- `backend/indexer.py:146-151`：manifest 直接写 `_file_hashes.json`

问题：重建任务 ID 固定为 `rebuild:{user}:{topic}`。如果用户在重建 active 期间继续保存/上传/删除文件，新的 rebuild 请求会被 dedupe，不会排队第二轮。与此同时，当前任务可能已经读过旧文件内容，但最后保存的是后来文件状态的 hash，或反过来。

影响：manifest 认为文件已是最新，但 Qdrant 中仍是旧 chunk。后续增量重建会误判“无变化”，RAG 长期使用过期内容。

建议：为每个 topic 引入 dirty generation/version；active rebuild 期间发生写入时标记 dirty，当前任务完成后自动再跑一轮。或对源文件做构建快照，manifest 必须对应同一份快照。manifest 写入也应使用 `atomic_write_text()`。

### P1：`topics.json` 读改写无锁且非原子，可能丢更新或损坏

位置：

- `backend/indexer.py:199-214`：`load_topics()` / `save_topics()` 直接 read/write
- `backend/routers/profile.py:41-47`：创建 topic 是 read-modify-write
- `backend/routers/profile.py:60-64`：删除 topic 是 read-modify-write
- `backend/utils/files.py:15-31`：项目已有原子写工具，但 topics 未使用

问题：topic 配置文件采用 JSON 文件保存，但没有 per-user lock，也没有 temp file + `os.replace()` 原子写。并发创建/删除 topic 时可能互相覆盖；容器重启或进程崩溃打断写入时，`topics.json` 可能变成半文件。

影响：topic 映射丢失或损坏后，Knowledge、训练、历史、画像展示都会受影响。JSON 损坏时 `load_topics()` 会直接抛异常，相关接口 500。

建议：使用 per-user lock + `atomic_write_text()`。`load_topics()` 对 JSONDecodeError 做备份恢复或返回可诊断错误。更稳妥方案是迁移到 SQLite 表并用事务处理 create/delete。

### P1/P2：多渠道配置保存会携带其他 section 的旧快照，可能回滚刚保存的渠道

位置：

- `frontend/src/pages/Settings.tsx:294-346`：页面同时渲染三个独立 `ChannelManager`
- `frontend/src/components/ChannelManager.tsx:73-89`：每个 manager 独立加载一次 `allData`
- `frontend/src/components/ChannelManager.tsx:166-184`：保存当前 section 时，把 `allData` 中其他 section 一起放入 payload
- `backend/routers/settings_router.py:98-115`：后端接收完整 `llm/embedding/reranker`
- `backend/ai_config.py:183-199`：`save_channels()` 对传入 section 直接覆盖 `_cache[section]["channels"]`

问题：三个 ChannelManager 分别持有自己的 `allData` 快照。假设用户先保存 embedding，随后保存 llm；llm manager 的 `allData.embedding` 仍可能是旧值。llm 保存请求会把旧 embedding 一起 POST，后端整段覆盖，导致刚保存的 embedding 配置被回滚。

影响：AI 渠道配置在同一页面内被互相覆盖，表现为“保存成功但配置丢失/回退”。Docker 部署中 LLM/Embedding/Reranker 配置是运行时关键配置，该问题会直接影响 RAG 和评估链路。

建议：前端每个 section 只提交当前 section；后端提供 PATCH `/settings/ai/channels/{section}`。或保存前重新拉取最新全量配置并做三方 merge。增加配置版本号/ETag；后端发现版本过旧时返回 409，提示用户刷新。

### P2：保存 review 与副作用写回非事务，崩溃会留下半完成状态

位置：

- `backend/routers/interview.py:435`：先 `save_review()`
- `backend/routers/interview.py:440-461`：再更新 SR/profile/knowledge，最后 `mark_session_synced()`
- `backend/routers/interview.py:520-538`：JD prep 同样逻辑
- `backend/storage/sessions.py:64-75`：`save_review()` 独立 commit

问题：`save_review()`、画像/SR/知识写回、`mark_session_synced()` 分散在多个独立操作中。进程在中间崩溃时，可能出现 review/scores 已保存但副作用未完成，或副作用部分完成但未写 `synced_at`。

影响：后续 re-eval 会因 `already_scored` 跳过副作用，导致漏同步；手动 sync 又可能重复部分已完成副作用。

建议：拆分状态：`side_effect_status = pending/running/done/failed`。先原子 claim，再逐项记录已完成步骤。对 SR/profile 这类统计更新引入可幂等事件表，按 `(session_id, step)` 去重。

### P2：Resume 面试结束写回没有 `synced_at`/幂等锁

位置：

- `backend/routers/interview.py:602-634`：`_persist_resume()` 执行画像抽取、`save_review()`、知识写回
- `backend/routers/interview.py:640`：直接 shield persist
- `backend/routers/interview.py:660-679`：手动 sync 只支持 `topic_drill` / `jd_prep`

问题：Resume 路径没有使用 `already_scored`、`synced_at` 或 per-session lock。多标签页/重复点击/网络重试可能让同一 resume session 多次写回画像和知识。

建议：Resume 结束路径也使用统一的 session side-effect idempotency 机制。手动 sync 支持 resume，或明确 resume 不产生可重复副作用。

### P2：简历上传先删旧文件再写新文件，失败会丢旧简历且旧索引可能残留

位置：

- `backend/routers/resume.py:36-38`：先删除 resume 目录中旧文件
- `backend/routers/resume.py:45-54`：再流式写入新文件
- `backend/routers/resume.py:55-57`：新文件超限时删除新文件并抛 413
- `backend/routers/resume.py:64`：只有成功后才 invalidate resume 索引

问题：上传新简历时，旧简历会先被删除。如果新上传文件超限、连接中断或写入失败，旧简历已经不可恢复。由于索引失效只在成功后执行，失败场景下还可能出现“旧文件已删，但旧 Qdrant resume 向量仍在”的不一致。

建议：先写临时文件并完成大小校验，成功后用原子 replace/rename 替换旧文件。旧文件至少保留到新文件写入完成且索引失效成功之后。失败时清理临时文件，不影响旧简历。

### P2：Knowledge 删除 topic 只删除映射和索引，不删除源知识文件

位置：`backend/routers/profile.py:58-69`

问题：`delete_topic()` 删除 `topics[key]` 后调用 `invalidate_topic_index()`，但没有删除 `settings.user_knowledge_path(user_id) / topics[key]["dir"]` 下的源知识文件。

影响：用户以为领域已删除，但 Docker volume 中原文仍保留。如果后续用同 key 重建 topic，旧文件会重新出现并被索引。

建议：删除接口明确支持 hard delete 或 archive。hard delete 前必须校验目标目录解析后仍位于当前用户 knowledge 根目录下。UI 文案明确“删除领域是否删除源文件”。

### P2：Knowledge 允许 200MB 上传，但读取接口会一次性返回全量文件正文

位置：

- `backend/routers/knowledge.py:17`：上传上限 200MB
- `backend/routers/knowledge.py:98-114`：`get_core_knowledge()` 读取 topic 下所有文件完整正文并 JSON 返回
- `frontend/src/pages/Knowledge.tsx:231-232`：上传成功后立即 `loadCore()`

问题：单个 `.md` 可上传 200MB，但核心知识读取接口会把 topic 下所有文件全文一次性返回给前端。

影响：backend JSON 序列化、nginx、浏览器、React state 全链路内存压力过高。Docker 容器内存较小时可能卡死或 OOM。

建议：列表接口只返回文件名、大小、mtime、摘要。正文按文件懒加载。上传上限与在线编辑上限分离；大文件可索引但不可在线全文编辑。

### P2：Knowledge 前端切 topic 无请求代际/取消，旧响应可能覆盖新 topic 状态

位置：`frontend/src/pages/Knowledge.tsx:103-143`

问题：`selected` 变化后并发调用 `loadCore()`、`loadHighFreq()`、`loadStats()`，响应回来后直接写 `setCoreFiles/setEditContent/setHighFreq/setStats`，没有 request id 或 AbortController。

影响：快速切换 topic 或网络慢时，旧 topic 内容可能显示在新 topic 下。如果用户此时保存，可能把旧内容写入当前选中的 topic。

建议：每次 topic 切换生成 request generation，响应落地前校验仍是当前 generation。或使用 AbortController 取消旧请求。

### P2：设置页修改密码前后端字段不一致，导致改密失败

位置：

- `backend/models.py:102-104`：后端模型要求 `current_password`
- `backend/routers/auth.py:106-115`：路由读取 `req.current_password`
- `frontend/src/api/settings.ts:53-58`：前端 API 类型为 `{ old_password, new_password }`
- `frontend/src/pages/Settings.tsx:157-169`：提交 `{ old_password: currentPassword, new_password: newPassword }`

问题：前端发送 `old_password`，后端要求 `current_password`。Pydantic 会认为缺少必填字段，返回 422。

影响：用户无法从设置页修改密码；对默认密码风险的缓解路径被破坏。

建议：前端改为发送 `current_password`。或后端兼容 alias：`current_password: str = Field(alias="old_password")`，同时保留新字段。加一条前后端契约测试覆盖改密接口。

### P2：Assistant 工具查询知识库时会阻塞事件循环最多 60 秒

位置：

- `backend/assistant.py:685-695`：`query_knowledge_base` 中创建 `ThreadPoolExecutor` 后直接 `future.result(timeout=60.0)`
- `backend/assistant.py:824-833`：工具执行本身在 async 流中 gather，但内部阻塞仍会卡住当前 event loop

问题：`_execute_tool()` 是 async 函数，但 `query_knowledge_base` 分支里直接调用阻塞式 `future.result(timeout=60.0)`。这会阻塞 FastAPI 当前 worker 的事件循环，而不是只等待该工具任务。

影响：一个 Assistant 知识库查询最多可让同 worker 上其他 SSE/API 请求卡住 60 秒。Docker 单 worker/少 worker 部署中影响更明显。

建议：改为 `await asyncio.wait_for(asyncio.to_thread(retrieve_topic_context, ...), timeout=60)`。或维护共享线程池，避免每次请求创建 executor。工具执行期间继续周期性发送 ping，避免代理超时。

### P2：QA Arena 同一 session 无服务端串行化，多标签并发会污染对话顺序

位置：

- `backend/routers/qa_arena.py:60-74`：chat 路由直接启动 SSE
- `backend/qa_arena.py:593-607`：读取历史、保存 user message、随后基于旧 history 生成回答
- `backend/qa_arena.py:561-568`：assistant 回复按完成顺序保存
- `backend/storage/qa_sessions.py:77-88`：消息插入是单条 append，无 session turn lock

问题：单页面前端用 `isStreaming` 阻止并发发送，但服务端没有 per-session lock。多标签页或重复请求可同时进入同一 session：两个请求都读取近似相同的旧 history，各自保存 user message，并发生成 assistant 回复；最终 assistant 消息按完成顺序落库，可能不对应正确 user turn。

建议：对每个 `(user_id, session_id)` 加 async lock。或引入 turn id，服务端只允许上一轮完成后进入下一轮。前端 `isStreaming` 只能作为体验优化，不能作为一致性保证。

### P2/P3：Algorithm live chat 也缺少 per-session lock，并发追问可能交错

位置：

- `backend/routers/algorithm.py:56-83`
- `backend/live_store.py:98-126`

问题：`algorithm_chat()` 直接从 live store 取 session，先 append 用户消息，再异步流式调用 LLM，完成后 append AI 回复并保存。多标签并发追问时，两个请求会共享并修改同一个 `session["messages"]`，容易产生上下文交错。

建议：复用 QA 的 per-session turn lock 方案，或把算法追问持久化到 DB，以 turn id 约束顺序。

### P3：旧版 `/settings/ai` 保存接口会过滤合法的 0 值

位置：

- `backend/models.py:130-135`：`LLMConfig.temperature` 支持 `float`
- `backend/routers/settings_router.py:28-30`：`config = {k: v for k, v in config.items() if v}`

问题：旧 AI 配置接口会把 falsy 值过滤掉。`temperature=0` 是合法配置，但会被丢弃。当前设置页主要使用多渠道接口，此问题优先级低于渠道保存覆盖。

建议：只过滤 `None`，不要过滤 `0`/`False`。对空字符串“删除覆盖”的语义放到 `save_ai_config()` 内部处理。

## 仍保留的架构边界

1. 真实 Docker build/start、Nginx SSE、Qdrant 鉴权与跨存储恢复仍需在具备 daemon 和外部服务的环境中验收。
2. 当前队列、live store、任务状态及部分锁仍是单进程设计；横向扩容前需要共享协调和持久任务系统。
3. 文件锁与 SQLite claim 解决当前单实例并发，不等价于跨主机分布式事务；画像、知识和向量库的跨存储 exactly-once 仍需事件表/outbox。
4. 前端已通过静态检查，但尚无完整 component/Playwright 套件；快速切换、断网恢复和多标签页仍应补浏览器级回归。
5. 上游模型、embedding、reranker 和真实 Qdrant 的协议漂移/延迟只能通过集成与持续探测覆盖。

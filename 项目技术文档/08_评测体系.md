# Part 2 · 08 — 评测体系

> Agent / RAG 岗位最看重的能力之一是：**你怎么证明你的系统"更好"？** 本章讲 SparkOffer 的评测哲学——"**先修尺子，再谈优化**"——以及离线评测矩阵（persona × strategy × judge）、LLM-as-Judge 多模型投票、确定性 judge（含 KL 散度），和"用基线证明相对结论"的方法论。

---

## 0. 核心哲学：没有可信的尺子，一切调参都是盲调

这是项目 `OPTIMIZATION_PLAN` 的第一原则，也是最该在面试讲的方法论：

> **优先修「衡量手段」，再谈「优化手段」。** 上 hybrid 检索、上 rerank、调 prompt 之前，先得有一把能测出"好坏"的尺子。否则你改完根本不知道是变好还是变坏。

这个意识把"我加了个很大的知识库 / 我调了很多 prompt"这种**没有 before/after 数据**的叙事，升级成"我先建评测、发现真实瓶颈、用数据决定每一刀"——**含金量差一个量级**。

---

## 1. 离线评测框架：persona × strategy × judge 矩阵（`backend/eval/`）

目标（`eval/README.md`）：**证明（或证伪）个性化出题管道在客观指标上优于朴素基线**。这是后续所有优化（rerank、slot 策略、难度校准）的"对照基线"。

整体是一个三维矩阵：

```
        judge1  judge2  judge3  judge4
persona × strategy 每个组合(cell)跑出题 → 4 个 judge 打分 → CSV
```

### 1.1 Persona（5 个虚拟用户画像）

| persona_id | topic | mastery | weak_points | 测什么 |
|---|---|---|---|---|
| `junior_python` | python | 25 | 5 | 新手段（应出简单/中等） |
| `mid_python` | python | 50 | 4 | 中段（难度均衡） |
| `senior_distributed` | java | 75 | 4 | 高段（应偏难） |
| `cold_start` | (任意) | 0 | 0 | **冷启动边界**（管道不能崩） |
| `agent_focused` | agent | 60 | 5 | agent 标签薄弱点匹配 |

为什么是 5 个？覆盖三个掌握度段 + 冷启动边界，足够区分策略差异；再多只会让 LLM-judge 成本翻倍而不改变定性结论。**这种"够用就好、克制扩张"的取舍本身是亮点。**

### 1.2 Strategy（3 个出题策略，含 2 个基线）

| strategy | 做什么 | 成本 |
|---|---|---|
| `personalized` | **把 persona 物化成真实用户目录、跑真正的 `DrillPipeline`** SSE 全流程，收集出的题 | LLM 重（全管道） |
| `topic_only`（基线） | 只给 topic 名、不给画像/薄弱点，问同一个 LLM | 1 次 LLM/persona |
| `random_baseline`（基线） | 从知识库 .md 里采样问题样式的行 | 免费、确定性 |

`personalized` 会在 `data/users/eval_<id>_<hex>/` 建临时用户、跑完 rmtree 清理——**用真管道而非 mock，保证评测的是真实行为**。

### 1.3 Judge（4 个评判器：3 确定性 + 1 LLM）

| judge | 类型 | 测什么 | 方向 |
|---|---|---|---|
| `coverage` | 确定性 | persona 薄弱点被 ≥1 道题命中的比例（关键词 + embedding ≥0.55 余弦兜底） | 越高越好 |
| `difficulty_kl` | 确定性 | 产出难度分布与目标分布的 **KL 散度**（目标按掌握度分 3 段） | 越高越好 |
| `diversity` | 确定性 | `1 − 题目两两 embedding 余弦均值`（题目多样性） | 越高越好 |
| `llm_judge` | LLM | 最多 3 个不同渠道各 1-10 打分，除以 10 取**中位** | 越高越好 |

**所有 judge fail-soft**：embedding 服务挂了，给低分 + 诊断字符串，**绝不抛异常中断整个评测**。

## 2. LLM-as-Judge：用 LLM 当裁判

### 2.1 是什么 / 为什么

有些质量维度（题目"好不好"、"相关不相关"）没有确定性公式可算，只能靠"判断"。**LLM-as-Judge** 就是让另一个 LLM 来打分。它是当前 LLM 评测的主流手段——快、能覆盖主观维度。

### 2.2 本项目怎么降低 LLM-judge 的偏差

LLM 当裁判有个公认问题：**单个裁判会漂移、有偏好**。本项目（`eval/judges/llm_judge.py`）用**多模型投票**降偏差：

- 从**最多 3 个不同的 LLM 渠道**（不同模型）各要一个 1-10 打分；
- 取**中位数**（median）而非均值——抗单个离群值；
- 评分维度明确写进 prompt：weak_point 相关性、难度匹配、覆盖多样性、可作答性；
- 全渠道都失败时返回 0 + `all_channels_failed` 诊断。

> **面试金句**：「LLM 当裁判会漂移，我用多模型投票降偏差——拉最多 3 个不同模型各打 1-10 取中位数，而不是信任单个裁判。」这正好能回答面试官常问的"怎么避免 evaluator 漂移"。

## 3. 确定性 Judge 详解

### 3.1 coverage（覆盖率）

测"出的题有没有命中 persona 的薄弱点"。先关键词匹配，匹配不上用 **embedding 余弦 ≥0.55** 兜底（语义命中也算）。

> **同源性陷阱（必须懂的认知偏差）**：persona 的 weak_points 既喂给 `personalized` 策略出题，又用**同一批** weak_points 判覆盖——所以 `personalized` 的 coverage 绝对值天然偏高。**结论**：coverage 的绝对数值**不能**解读成"检索/出题质量好"；但因为 random/topic_only 基线吃**同样**的 judge，"personalized 是否**优于**基线"这个**相对结论**有效。这个区分是 RAG 评测成熟度的试金石。

### 3.2 difficulty_kl（KL 散度）

测"产出题目的难度分布"和"该 persona 应有的目标分布"有多接近。

**KL 散度（Kullback-Leibler Divergence）** 是信息论里衡量两个概率分布差异的指标：

```
KL(P ‖ Q) = Σ P(i) · log( P(i) / Q(i) )    ≥ 0，越小越接近
```

- 这里 `P` = 实际产出难度分布，`Q` = 目标分布（按 persona 掌握度选 easy/medium/hard 三段之一）。
- 本项目把它转成"越高越好"的分数（KL 越小 → 分越高）。
- 直觉：新手该多出简单题，专家该多出难题——KL 散度量化"难度梯度对不对"。

### 3.3 diversity（多样性）

`1 − 题目两两 embedding 余弦的均值`。题目互相越不像，多样性越高。注意 README 诚实标注：`random_baseline` 可能在 diversity 上**反超** personalized（随机采样跨子主题更广）——**这没关系，diversity 是"别退化"的守门指标，不是要冲高的目标**。

## 4. 基线对比方法论：为什么需要基线

只看 `personalized` 的绝对分没意义（多少分算好？）。**必须有基线对照**：

```
personalized  vs  topic_only  vs  random_baseline
（完整个性化）   （只给主题）      （随机采样）
```

`eval/README.md` 给的"假设区间"：

| judge | personalized | topic_only | random_baseline |
|---|---|---|---|
| coverage | 0.70–0.95 | 0.10–0.30 | 0.05–0.20 |
| difficulty_kl | 0.75–0.95 | 0.50–0.75 | 0.30–0.55 |
| llm_judge | 0.65–0.85 | 0.45–0.65 | 0.20–0.40 |

只要 `personalized` 在 coverage/difficulty_kl/llm_judge 上**显著高于两个基线**，就证明了"个性化管道确实在干活"——这是个**相对结论**，不受 coverage 同源性陷阱影响。

CLI（`python -m backend.eval.run`）支持 `--smoke`（1×1×1，不烧 token）、`--no-llm-judge`（快速迭代省钱）、`--persona/--strategy/--judges` 自由组合，输出 CSV 到 `eval/reports/`。

## 5. 在线 RAG 指标：出题时实时测检索质量

离线评测是"实验室",在线指标是"生产监控"。出题主链路里 `rag_metrics.compute_retrieval_metrics`（`rag_retrieval.py` 调用）**纯 embedding、零 LLM 成本**地实时算：

- **relevance**：检索 chunk 与 query 的相关度；
- **coverage**：多少 query 被覆盖；
- **diversity**：chunk 间多样性。

随出题落进 `rag_metrics` 表，前端 **RAG Dashboard** 可视化。算不出来时返回 `None`（不存假的全零记录，避免误判"检索崩了"）。

另有离线的 `eval/rag_recall.py`（检索召回评测）算 **Recall@k / Hit-rate / MRR**（见 03 章 §7）——这把尺子跑出来的结论（HitRate=1.0、MRR≥0.9）**直接修正了优化方向**：检索不是瓶颈，延迟才是，于是 hybrid/rerank 被搁置。

## 6. 诚实的边界（面试时主动说，比被戳穿强）

- **没有完整的自动评测 CI**：离线 harness 有了，但没接 pytest/GitHub Actions，目前是人工跑 CSV。
- **评测集触顶**：rag_recall 评测集只有 10 条且 HitRate 全 1.0——"尺子测不出短板"，扩充更难的区分性评测集（术语歧义/近义混淆/长尾/负样本）是当务之急。
- **coverage 同源性**：见 §3.1，绝对值不可解读为质量。

> **面试金句**：「我的评测体系能证明'个性化优于基线'这个相对结论，确定性指标 + 多模型 LLM 投票都有。但我也清楚边界——还没接 CI、评测集偏小且触顶，这些是已知 TODO。」诚实标注短板，反而显得可信。

---

## 本章小结

- 核心哲学：**先修尺子再优化**，每一刀都要有 before/after 数据。
- 离线评测是 **5 persona × 3 strategy（含 2 基线）× 4 judge** 矩阵；personalized 跑**真管道**。
- **LLM-as-Judge 多模型投票取中位**降裁判漂移；确定性 judge 含 coverage / **KL 散度** / diversity。
- 懂 **coverage 同源性陷阱**（绝对值≠质量，相对结论才有效）和**基线对照**的必要性。
- 在线 RAG 指标实时落库可视化；离线 rag_recall 的数据**直接修正了优化方向**（瓶颈是延迟不是召回）。

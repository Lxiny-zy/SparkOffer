# Part 2 · 05 — 工程鲁棒性

> LLM 应用最大的敌人是**不确定性**：API 会超时、会限流、会 5xx，embedding 服务会抖动。本章讲 SparkOffer 怎么用一整套生产级机制把这些兜住——**多渠道 failover、三态熔断器、后台任务队列、两阶段流式 failover**。这一章是区分"玩具 demo"和"能上线的系统"的分水岭。

---

## 0. 鲁棒性设计的总原则

贯穿全项目的几条原则，先记住：

1. **降级优于崩溃**：任何外部依赖挂了，给个合理兜底（空上下文/零向量/原顺序），绝不让整个请求 500。
2. **快速失败优于慢慢挂**：embedding `max_retries=1`、`timeout=20s`，宁可早点失败兜底，也不拖垮外层预算。
3. **区分"瞬时错误"和"确定性错误"**：5xx/429/超时值得重试或切换；4xx 配置错误重试也没用，直接抛。
4. **隔离爆炸半径**：单个工具/单路检索/单个任务失败，不能炸掉整轮/整批。
5. **不阻塞事件循环**：所有同步阻塞调用（embedding、SQLite、LlamaIndex）都 `asyncio.to_thread` 移走。

## 1. 多渠道 Failover（`channel_manager.py`）

### 1.1 是什么 / 为什么

"渠道（channel）"= 一个 LLM/embedding/reranker/ASR 的接入点（一组 `api_base + keys + model`）。配多个渠道，一个挂了自动切下一个——这就是 **failover（故障转移）**。为什么需要：单一 API key 会限流、单一供应商会宕机，多渠道是生产可用性的基本保障。

本项目对 4 类服务都支持多渠道：`llm` / `embedding` / `reranker` / `asr`（按 `section` 区分）。

### 1.2 渠道状态机（`ChannelState`）

每个渠道维护一个状态（用 `__slots__` 省内存）：

```python
healthy: bool          # 是否健康
error_count: int       # 连续错误数
cooldown_until: float  # 冷却截止时间戳
current_key_index: int # Key 轮询游标
```

三个关键行为：

| 行为 | 逻辑 | 参数 |
|---|---|---|
| **Key 轮询** | `next_key` 每次取下一个 key，`(idx+1) % len(keys)` 循环 | 一个渠道挂多个 key 分摊限流 |
| **错误冷却** | `mark_error`：error_count++，达 3 次 → 标记不健康 + 冷却 60s | `MAX_ERRORS_BEFORE_COOLDOWN=3`、`COOLDOWN_SECONDS=60` |
| **成功恢复** | `mark_success`：error_count 清零、恢复健康 | — |

### 1.3 HALF_OPEN 探活（精妙处）

渠道冷却 60s 后，不是直接"完全信任"它，而是 `is_available`（`channel_manager.py:46-57`）：

```python
if time.time() >= self.cooldown_until:
    self.healthy = True
    self.error_count = MAX_ERRORS_BEFORE_COOLDOWN - 1   # 故意设成"差一次就再次熔断"
    return True
```

含义：**冷却结束后渠道变得"可被选中"，但只要再错一次就立刻重新冷却**——直到真正成功一次（`mark_success` 清零）才完全恢复。这就是断路器里的 **HALF_OPEN（半开）探活**思想：给一次机会试探，但保持警惕。

### 1.4 渠道选择：优先级 + 两遍 tier 过滤

`_select`（`channel_manager.py:100-140`）：
- 渠道按 `priority` 升序排（数字小优先）。
- 支持 **tier（档位）**：`small`/`large`——可以把便宜小模型和贵大模型分开，按任务路由。
- **两遍扫描**：第一遍尊重 tier 过滤；如果该 tier 没有可用渠道，第二遍**降级到任意 tier**（并去重日志，避免每次出题都刷一行警告）。
- 跳过：被 exclude 的（本轮已试过的）、disabled 的、不可用（冷却中）的。

### 1.5 一个细节：`get_health` 是纯读

健康查询接口**不调** `is_available()`——因为后者有"复活冷却渠道"的副作用。`get_health` 内联计算可用性，保证查询不改状态。这种"读不改状态"的洁癖是高质量代码的标志。

## 2. 三态熔断器（`embedding_tasks.py:31-128`）

### 2.1 是什么 / 为什么

**熔断器（Circuit Breaker）** 是分布式系统经典模式：当下游服务持续失败时，**主动"断路"快速拒绝请求**，而不是让每个请求都去撞墙、白白等超时、还可能压垮正在恢复的下游。

本项目给 **embedding 服务**专门配了一个熔断器（embedding 被画像更新、向量检索、去重等多处高频调用，挂了影响面大）。

### 2.2 三个状态

```
        5 次连续失败
CLOSED ───────────────→ OPEN
  ↑                       │ 60s 后
  │ 2 次成功               ↓
  └──────── HALF_OPEN ←────┘
              │ 任何一次失败
              └──→ OPEN（重新计时）
```

| 状态 | 含义 | 行为 |
|---|---|---|
| **CLOSED**（闭合） | 正常 | 放行所有请求；成功则 failure_count 递减（渐进愈合） |
| **OPEN**（断开） | 故障中 | **直接拒绝**（`can_execute()` 返回 False），调用方拿零向量兜底 |
| **HALF_OPEN**（半开） | 试探恢复 | 只放行 `half_open_max_calls=2` 个探测请求；2 个都成功→CLOSED，任一失败→OPEN |

参数：`failure_threshold=5`、`recovery_timeout=60s`、`half_open_max_calls=2`。

### 2.3 线程安全（容易忽略的点）

熔断器的计数器被**两个地方并发改**：任务队列的 worker loop + embedding 实际跑在 `asyncio.to_thread` 的工作线程。所以每个状态转移都用 `threading.Lock` 守护，否则更新会丢失、熔断不确定性触发。

### 2.4 熔断器怎么和检索协作

`vector_memory._embed`（`vector_memory.py:56-101`）调 embedding 前先问 `cb.can_execute()`：
- OPEN → 直接返回零向量（不发请求），写库时这些零向量会被过滤掉。
- 成功 → `record_success()`；失败/超时 → `record_failure()` + 指数退避重试（2 次，base 1.5）。

> **面试金句**：「embedding 是高频依赖，我给它配了三态熔断器——服务挂的时候快速失败返回零向量降级，而不是让几百个请求一起去撞超时、把正在恢复的服务再压垮。60s 后放 2 个探测请求试水，确认好了才完全恢复。」

## 3. 后台任务队列（`embedding_tasks.py:173-489`）

### 3.1 为什么需要

大知识库建索引、画像向量重建，可能耗时几十秒。这些**不能**卡在 HTTP 请求里（会超时）。解法：**fire-and-forget 后台任务队列**——提交后立即返回，慢活在后台慢慢干，前端轮询进度。

### 3.2 核心特性

| 特性 | 实现 | 价值 |
|---|---|---|
| **优先级队列** | `asyncio.PriorityQueue`，HIGH=1（增量插入）/ NORMAL=2（画像重建）/ LOW=3（全量重建） | 小而急的活先做 |
| **任务去重** | `task_id` + `_pending_ids`/`_active_tasks` 集合 | 同一 `(user,topic)` 的重建在飞，重复提交是 no-op |
| **指数退避重试** | 失败重试，backoff `min(2^(n-1)*2, 30)` = 2s/4s/8s…封顶 30s | 瞬时失败自愈 |
| **熔断集成** | 执行前查熔断器，OPEN 则延迟重排（不占 worker） | 下游挂时不空转 |
| **状态追踪** | `TaskStatus`（pending/running/completed/failed），保留 1h，定期 GC | 前端能轮询"建索引到哪了" |
| **并发限制** | `max_workers=2`、`max_queue_size=100` | 控资源；队满丢弃并计数 |

### 3.3 一个精妙设计：非阻塞重试

重试不能让 worker `await asyncio.sleep(backoff)` 干等——那会**钉住这个 worker**，饿死其他排队任务。`_spawn_retry` 把"延迟后重新入队"**分离成一个独立的后台任务**（`_track`），worker 立即返回去处理别的活：

```python
def _spawn_retry(self, task, delay):
    self._pending_ids.add(task.task_id)          # 占住去重 id
    self._track(self._schedule_retry(task, delay))  # 分离协程：sleep 后 put_nowait
```

而且重新入队用 `put_nowait`（队满就丢弃），**绝不**用阻塞 put——否则 worker 在队满时 await put 会和"队列消费需要 worker"形成死锁。

> 这种"别让等待钉住工作者"的考量，是写过真实异步系统才会有的直觉。

## 4. ResilientChatModel：LLM 的透明 failover 包装（`llm_provider.py:162-287`）

### 4.1 是什么

`ResilientChatModel` 是 `ChatOpenAI` 的 **drop-in 替换**——接口一样（`invoke`/`ainvoke`/`astream`/`bind_tools`），但内部对接 `channel_manager` 做多渠道自动 failover。上层代码（LangGraph 节点、各路由）**完全无感**。

### 4.2 错误分类：哪些切渠道、哪些不切

这是 failover 的灵魂——**不是所有错误都该切渠道**：

| 错误类型 | 状态码 | 处理 | 为什么 |
|---|---|---|---|
| **致命配置错误** | 400/401/403/404/422 | **直接抛**，不切 | 换渠道也救不了（key 错、模型名错），切了还白白冷却所有渠道 |
| **瞬时错误** | 408/409/429/500/502/503/504、网络/超时 | **先同渠道重试**（2 次，1.5s 退避），再切 | 抖一下，重试常常就好；单渠道部署尤其重要 |

`_extract_status_code` 会**顺着异常链**（`__cause__`/`__context__`）找状态码——因为 LangChain 把 openai/httpx 的异常包了好几层。

> **为什么 429 不算致命**：429 是限流，换个渠道/key 就能继续，**值得 failover**；这是和其他 4xx 的关键区别。

### 4.3 两阶段流式 Failover（最精妙处）

流式（`astream`）的 failover 比非流式难——**因为内容已经吐给用户了**。`astream`（`llm_provider.py:255-286`）分两阶段：

```
Phase 1：拉第一个 chunk 之前
   → 出错可以安全切渠道（用户还没看到任何字）
Phase 2：第一个 chunk 已 yield 出去之后
   → 绝不能切渠道！否则会把"另一个渠道的完整新答案"拼接到"已经吐出的半截答案"后面
   → 让 mid-stream 错误直接抛给调用方，由调用方决定怎么呈现已流出的部分
```

```python
try:
    aiter = llm.astream(messages).__aiter__()
    first_chunk = await aiter.__anext__()   # Phase 1：可失败转移
except Exception as e:
    _reraise_if_fatal(e, channel)
    report_error("llm", channel["id"]); tried.add(channel["id"])
    channel = get_next_channel(...); continue
report_success("llm", channel["id"])
yield first_chunk                            # 一旦 yield，进入 Phase 2
async for chunk in aiter:                    # 不再切渠道
    yield chunk
```

> **面试金句**：「流式 failover 有个坑——首 chunk 已经发给用户后就不能再切渠道了，否则会把新渠道的完整答案拼到半截答案后面，用户看到两段重复。所以我做了两阶段：首 chunk 前可切，首 chunk 后committed，错误直接上抛。」这个细节非常能体现工程深度。

### 4.4 其他生产细节

- **HTTP 客户端缓存复用**：`_build_http_clients` 按 `(proxy, timeout)` 缓存 httpx client。httpx 客户端设计为长生命周期连接池，**每次调用新建且不关会泄漏 socket/fd**——这是修过的真实问题。
- **超时分层**：LLM `read=360s`，**故意高于** nginx 的 `proxy_read_timeout=300s`——让长推理的超时**只由 nginx 一层兜**，而不是 httpx 和 nginx 互相竞争。
- **tier + reasoning_effort**：支持按档位路由、按调用覆盖推理强度（如摘要生成用 `low` effort 而不动全局）。

## 5. 配置热重载与单例失效（`llm_provider.py` + `ai_config.py`）

### 5.1 机制

LLM/embedding/向量后端都是**单例**，但配置可以运行时改（`ai_config.json` 热重载）。怎么让改配置后单例自动重建？用**配置版本号**：

```python
ver = get_config_version()      # 每次保存配置 +1
if instance is None or cached_version != ver:
    instance = _create(...)     # 版本变了就重建
    cached_version = ver
```

### 5.2 换 embedding 渠道的级联失效

`invalidate_singletons()` 不只重建 LLM/embedding，还**级联失效**：
- 向量记忆后端单例（embedding 维度/通道变了要重连）；
- 知识库 Qdrant 状态（client/健康标志/维度缓存）；
- LlamaIndex 全局 `Settings.llm` / `Settings.embed_model`。

> 这解决了一个隐蔽问题：**换了 embedding 模型（如 1536 维换 1024 维），所有缓存的维度假设都要一起失效**，否则会触发"混维度 cosine"崩溃。`_zero_vec` 也改成动态探测当前维度而非硬编码 1536——同一个维度治理思路。

## 6. 超时 / 降级 / 隔离：一张速查表

| 场景 | 兜底策略 | 位置 |
|---|---|---|
| 知识库检索超时（60s） | `to_thread + wait_for`，超时返回空 chunk | `indexer.safe_retrieve_*` |
| 出题 RAG 总预算（100s） | 超时降级到空知识上下文，照常出题 | `drill_pipeline._stage_retrieve` |
| embedding 失败/熔断 | 返回零向量，写库时过滤零向量 | `vector_memory._embed` |
| 重排失败 | 返回原顺序（degraded） | `reranker.rerank` |
| 单路检索失败 | `gather(return_exceptions=True)`，该路置空 | `rag_retrieval.retrieve_for_drill` |
| 单工具失败 | 转错误结果继续，整轮不中断 | `assistant._execute_tool` |
| LLM 全渠道挂 | 抛 `RuntimeError`，前端兜底提示 | `ResilientChatModel` |
| Redis 不可用 | 退化到内存 LRU（5000 条） | `redis_cache` |
| 画像 LLM 合并失败 | 降级到向量去重 | `memory._deterministic_update` |

> **共同模式**：每个外部依赖都有"挂了怎么办"的明确答案。这种"**对每个失败路径都有交代**"的习惯，是鲁棒性的本质。

## 本章小结

- **多渠道 failover**：优先级 + Key 轮询 + 3 错 60s 冷却 + **HALF_OPEN 探活**，区分致命 4xx 与瞬时错误。
- **三态熔断器**：embedding 专用，CLOSED/OPEN/HALF_OPEN，线程安全，挂了快速降级零向量。
- **后台任务队列**：优先级 + 去重 + 指数退避 + **非阻塞重试**（别钉住 worker）。
- **ResilientChatModel**：透明 failover，同渠道重试，**两阶段流式 failover**（首 chunk 后禁切）。
- **配置热重载 + 级联单例失效**：换 embedding 维度不崩。
- 一句话：**降级优于崩溃，快速失败优于慢慢挂，对每个失败路径都有交代。**

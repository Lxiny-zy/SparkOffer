## 1. Docker Compose 编排（`docker-compose.yml`）

### 1.1 四个服务

```
浏览器 https://你的域名
  └── 宿主 TLS 入口（Nginx/Caddy/负载均衡器）
        └── http://127.0.0.1:9000
              └── frontend (nginx, 容器 80)
                    └── /api → backend (uvicorn, expose 8000)
                                  ├── redis  (data 内部网络)
                                  └── qdrant (data 内部网络)
```

| 服务 | 镜像/构建 | 端口可见性 | 角色 |
|---|---|---|---|
| `frontend` | nginx（构建 React 产物） | 宿主回环 `127.0.0.1:9000` → 容器 `80` | 静态资源 + 反代 `/api` 到后端；只作为宿主 HTTPS 入口的上游 |
| `backend` | uvicorn（FastAPI） | 仅 `expose 8000`，不映射宿主端口 | 业务逻辑；仅由 frontend 通过 `proxy` 网络访问 |
| `redis` | `redis:7-alpine` | 不映射宿主端口 | 缓存（256mb，LRU 淘汰）；仅在 `internal: true` 的 `data` 网络可达 |
| `qdrant` | `qdrant/qdrant:v1.12.0`（默认固定版本） | 仅向 Docker 网络 `expose 6333/6334` | Docker 默认向量后端；仅在 `data` 内部网络可达，必须配置 API key |

生产用户只访问 `https://你的域名`。`127.0.0.1:9000` 是宿主 TLS 反向代理使用的明文回环上游，不是浏览器入口；9000、8000、6333、6334、6379 均不得直接暴露到公网。

### 1.2 编排里的工程考量

- **健康检查 + 启动依赖**：`backend` 等 `redis` healthy 才起；`frontend` 等 `backend` healthy 才起（`depends_on` + `condition`）。后端健康检查是访问 `/docs`。
- **Qdrant 不等待 healthy、但仍是默认后端**：backend 对 qdrant 使用 `condition: service_started`——Qdrant 镜像没有可供当前 exec 健康检查使用的 shell/curl。compose 给 backend 注入 `VECTOR_BACKEND=qdrant`，**Docker 部署默认走 Qdrant 且 qdrant-only 不降级 numpy**：连不上时知识库检索降级为空上下文并委派后台重建（IndexNotReady 语义），服务本身不崩。numpy 是裸 uvicorn 本地开发的默认。
- **固定版本 + 服务鉴权**：Qdrant 默认镜像固定为 `qdrant/qdrant:v1.12.0`，避免无意漂移；`QDRANT_API_KEY` 是 Compose 必填项，并以同一值注入 Qdrant 服务与 backend 客户端。
- **内部网络隔离**：backend 只用 `expose` 发布 8000，Redis/Qdrant 也没有宿主端口映射；后两者只加入 `internal: true` 的 `data` 网络。frontend 的 9000 映射固定在宿主回环地址。
- **数据卷职责分离**：backend 使用 `./data:/app/data` 保存 SQLite、用户目录等应用数据；Redis 独占 `./data/redis:/data`，Qdrant 独占 `./data/qdrant:/qdrant/storage`。由于这两个宿主子目录也落在 backend 的父级挂载下，backend 再用只读 `tmpfs` 覆盖 `/app/data/redis` 和 `/app/data/qdrant`，避免绕过服务 API 读取其持久化文件；该遮罩不影响 Redis/Qdrant 自己的直接挂载与持久化。
- **资源限制**：backend 限 2G 内存；redis `maxmemory 256mb` + `allkeys-lru`（满了淘汰最久未用）。
- **`restart: unless-stopped`**：崩了自动拉起。

## 2. nginx 反向代理 + 流式调优（`frontend/nginx.conf`）

nginx 既服务前端静态资源，又反代 `/api` 到后端。**关键是对 SSE 流式的调优**：

```nginx
location /api/ {
    proxy_pass http://backend:8000;
    proxy_read_timeout 300s;       # 长推理/出题留够时间（后端 read 设 360s 比它高一层）
    proxy_send_timeout 300s;
    proxy_buffering off;           # 关键！关缓冲，SSE 才能逐帧实时下发
    proxy_cache off;
    proxy_http_version 1.1;        # SSE 需要 HTTP/1.1 长连接
    proxy_set_header Connection '';# 清空 Connection 头，保持长连接（不被 close）
}
```

| 配置 | 为什么 |
|---|---|
| `proxy_buffering off` | **流式的命门**——开着的话 nginx 会攒一批响应再发，前端收不到实时 token。配合后端 `X-Accel-Buffering: no` 双保险 |
| `proxy_read_timeout 300s` | 长出题/推理不被中途掐断；后端 httpx read=360s **故意比它高**，让超时只由 nginx 一层兜（呼应 05 章） |
| `proxy_http_version 1.1` + `Connection ''` | SSE 依赖 HTTP/1.1 持久连接 |

静态资源的缓存策略也分两类：
- `/assets/`（文件名带哈希）→ `expires 1y, immutable`（激进缓存，内容变了文件名就变）；
- `index.html` → `no-cache`（永远拉最新，保证发版立即生效）。

## 3. 可选依赖优雅降级（部署哲学）

SparkOffer 的一个设计主线：**核心功能零外部依赖，增强能力可选且优雅降级**。

| 依赖 | 不配会怎样 | 降级到 |
|---|---|---|
| **Redis** | 自动检测不可用 | 内存 LRU（5000 条）——缓存仍工作，只是不跨进程 |
| **Qdrant** | 裸 uvicorn 不配 = numpy 后端。**Docker 部署默认启用且 qdrant-only**：连不上不降级，检索返回空上下文 + 后台重试 | 空上下文（服务不崩）；显式设 `VECTOR_BACKEND=numpy` 才退本地 |
| **本地 embedding** | 不装 torch 依赖 | API embedding（OpenAI 兼容端点） |
| **Reranker** | 不配 | 检索退回原顺序（degraded/off） |
| **多渠道** | 只配单渠道 | 单渠道 + 同渠道重试（无 failover 但能跑） |

> **面试金句**：「我的部署哲学是核心零外部依赖——一个 FastAPI + 一个 SQLite 文件就能跑起来；Redis/本地 embedding/reranker 是可选增强，连不上自动降级。向量后端按环境定默认：本地开发 numpy 零依赖，Docker 部署默认 Qdrant 且 qdrant-only——配置说了走 Qdrant 就不静默换后端，坏了宁可返回空上下文 + 后台自愈，也不让两个后端的数据悄悄分叉。」

**最小启动要按环境区分**：裸 `uvicorn` + `npm run dev` 的本地开发仍以 LLM + Embedding 配置为核心；Docker Compose 默认按生产模式启动，除模型配置外还必须提供强 `JWT_SECRET`、强 `DEFAULT_PASSWORD`、HTTPS `CORS_ALLOW_ORIGINS` 和独立 `QDRANT_API_KEY`，然后运行 `docker compose up -d --build`。生产访问还必须先配置宿主 TLS 入口，完整步骤见 [`DEPLOYMENT.md`](../DEPLOYMENT.md)。

## 4. 配置体系（呼应各章）

两层配置，运行时优先：
- **`.env`**（`pydantic-settings` 读）：打底的静态配置。
- **`data/ai_config.json`**（运行时热重载）：优先级更高，可在 Settings 页面热改渠道、换模型，配 `_config_version` 触发单例失效（05 章 §5）。**换渠道不用重启。**

关键环境变量：

- **模型与增强能力**：`API_BASE/API_KEY/MODEL`（LLM）、`EMBEDDING_*`、`RERANKER_*`、`REDIS_URL`、`VECTOR_BACKEND`、`QDRANT_URL`。
- **Docker / 生产边界**：`APP_ENV=production`、`FRONTEND_BIND_ADDRESS=127.0.0.1`、强 `JWT_SECRET`、强 `DEFAULT_PASSWORD`、HTTPS `CORS_ALLOW_ORIGINS`、`ALLOW_REGISTRATION=false`。
- **Qdrant**：`QDRANT_IMAGE` 默认固定 `qdrant/qdrant:v1.12.0`；`QDRANT_API_KEY` 在 Compose 中必填，backend 与 Qdrant 必须使用同一个值，并应与 `JWT_SECRET` 分别独立生成。
- **代理信任**：`TRUSTED_PROXY_CIDRS` 只信任实际的宿主入口网关与 frontend 地址；不要扩大为任意来源。

可分别运行两次 `openssl rand -hex 32` 生成 `JWT_SECRET` 与 `QDRANT_API_KEY`，不要复用同一密钥。

## 本章小结

- **Docker Compose** 四服务编排：浏览器经宿主 HTTPS 入口访问回环 `127.0.0.1:9000` 上的 nginx 前端；backend 只 `expose 8000`，Redis/Qdrant 只在 `internal` 数据网络可达，不暴露宿主端口。
- **持久化与鉴权**：backend、Redis、Qdrant 各按职责挂载数据；backend 用只读 `tmpfs` 遮罩服务自有目录。Qdrant 默认固定 `v1.12.0`，并要求与 backend 共享独立的 `QDRANT_API_KEY`。
- **nginx 流式调优**：`proxy_buffering off` 是 SSE 命门，超时分层（nginx 300s < 后端 360s），HTTP/1.1 长连接；静态资源按哈希激进缓存、index.html 不缓存。
- **启动与降级边界**：Compose 会等待 Redis healthy，并只等待 Qdrant started；运行期 Redis/本地 embedding/reranker/多渠道仍有降级路径。向量后端按环境定默认（本地 numpy / Docker Qdrant），qdrant-only 时坏了返回空上下文 + 后台自愈而非静默换后端。

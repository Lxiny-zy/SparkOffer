# 大模型推理与部署

## 1. 推理过程

### 自回归生成
LLM 生成文本是逐 token 进行的，分为两个阶段：

#### Prefill 阶段（预填充）
- 一次性处理整个输入 prompt
- 计算所有输入 token 的 KV Cache
- **计算密集型（Compute-bound）**：大量矩阵乘法
- 可以充分利用 GPU 并行能力
- 耗时与输入长度成正比

#### Decode 阶段（解码）
- 逐个生成输出 token
- 每步只有 1 个新 token 的 Q 与整个 KV Cache 做 attention
- **访存密集型（Memory-bound）**：大量读取 KV Cache，但计算量小
- GPU 利用率低（batch_size 为 1 时尤其明显）
- 每步耗时与上下文长度成正比

```
Prefill vs Decode 对比：

Prefill:
  输入: [token1, token2, ..., tokenN]   (N 个 token 并行)
  计算: Q[N, d] * K[N, d]^T → Attention[N, N]
  特点: 计算量大，GPU 利用率高

Decode (生成第 t 个 token):
  输入: [token_t]                        (1 个 token)
  计算: Q[1, d] * K_cache[t, d]^T → Attention[1, t]
  特点: 计算量小，频繁访问 KV Cache
```

#### TTFT 和 TPS
- **TTFT（Time To First Token）**：从请求到第一个 token 输出的时间，主要由 Prefill 决定
- **TPS（Tokens Per Second）**：生成速度，主要由 Decode 决定
- **Throughput（吞吐量）**：单位时间内处理的总 token 数

## 2. 生成采样策略

### 贪心解码（Greedy Decoding）
- 每步选概率最高的 token
- 确定性输出，但容易重复、缺乏多样性
- 适合需要确定性输出的场景（如代码生成、JSON 输出）

### Temperature（温度）
```
P(token_i) = exp(logit_i / T) / sum(exp(logit_j / T))
```
- T < 1：分布更尖锐，倾向高概率 token（更确定、更保守）
- T = 1：原始分布
- T > 1：分布更平坦，增加多样性（更随机、更有创意）
- T → 0：等同于贪心解码
- T → inf：等同于均匀随机采样

### Top-K Sampling
- 只从概率最高的 K 个 token 中采样
- 将 K 以外的 token 概率设为 0，重新归一化后采样
- K 太大：可能选到低质量 token
- K 太小：缺乏多样性
- 常用值：K=50

### Top-P（Nucleus）Sampling
- 从累积概率达到 P 的最小 token 集合中采样
- 动态调整候选集大小
- 比 Top-K 更灵活：概率集中时选少量 token，分散时选更多
- 常用值：P=0.9 或 0.95

### Beam Search（束搜索）
- 同时维护 B 条最优候选序列
- 每步对每条候选扩展所有可能的 token，保留总分最高的 B 条
- 适合翻译等对质量要求高的任务
- 缺点：生成内容缺乏多样性，计算量大

### Min-P Sampling
- 设置一个动态阈值 = max_prob * min_p
- 只保留概率大于该阈值的 token
- 比 Top-K/Top-P 更简单但效果好
- 自适应：高置信时选择少，低置信时选择多

### Repetition Penalty（重复惩罚）
```
对已出现过的 token，降低其 logit:
  logit_adjusted = logit / penalty  (if logit > 0)
  logit_adjusted = logit * penalty  (if logit < 0)
```
- penalty > 1 时抑制重复
- 常用值：1.0-1.3

### 采样参数组合建议

| 场景 | Temperature | Top-P | 其他 |
|------|-----------|-------|------|
| 代码生成 | 0-0.2 | 0.95 | 确定性优先 |
| 技术写作 | 0.3-0.5 | 0.9 | 准确性优先 |
| 创意写作 | 0.7-1.0 | 0.95 | 多样性优先 |
| 聊天对话 | 0.5-0.8 | 0.9 | 平衡 |
| JSON 输出 | 0 | 1.0 | 贪心解码 |

## 3. 推理加速技术

### KV Cache
- 缓存已计算的 Key 和 Value 矩阵
- 避免每生成一个 token 都重新计算整个序列的 attention
- 显存占用随序列长度线性增长

### PagedAttention（vLLM 核心技术）
- 类似操作系统的虚拟内存分页机制
- KV Cache 不再需要连续显存，按"页"（Block）分配
- 解决了 KV Cache 的显存碎片和浪费问题

```
传统方式：
  请求 A: [KV Cache ][  预留空间（可能浪费）  ]
  请求 B: [KV Cache      ][  预留空间     ]
  → 需要预分配最大长度的连续显存，利用率低

PagedAttention：
  Block Pool: [B1][B2][B3][B4][B5][B6][B7][B8]
  请求 A: B1 → B3 → B5（按需分配，不连续）
  请求 B: B2 → B4 → B6
  → 按需分配，无碎片，利用率接近 100%
```
- 显存利用率提升 2-4 倍
- 支持 Copy-on-Write：相同前缀的请求共享 KV Cache

### Continuous Batching（连续批处理）
```
Static Batching（传统）：
  时间 → ─────────────────────────
  请求A: [████████████████████]     ← 短请求也要等最长的
  请求B: [██████████████████████████████████████]
  请求C: [████████████]             ← 等待...

  → 请求 A、C 完成后仍在等 B，GPU 空闲

Continuous Batching：
  时间 → ─────────────────────────
  请求A: [████████████████████]
  请求B: [██████████████████████████████████████]
  请求C: [████████████]
  请求D:              [████████████████████]     ← A/C 完成后立即加入
  请求E:                   [████████████████]

  → 请求完成即返回，空位立刻放入新请求
```
- 吞吐量提升数倍
- 所有现代推理框架的标配

### Speculative Decoding（投机解码）

```
1. Draft Model（小模型，如 1B）快速生成 K 个候选 token:
   draft_tokens = [t1, t2, t3, t4, t5]

2. Target Model（大模型，如 70B）一次性并行验证这 K 个 token:
   verify_results = target_model([input + t1, t2, t3, t4, t5])

3. 从左到右检查：
   t1 ✓ (接受)  t2 ✓ (接受)  t3 ✓ (接受)  t4 ✗ (拒绝，用大模型的 token 替换)

4. 一次 forward pass 生成了 3+1=4 个 token！
```

**关键要求**：
- 小模型与大模型的 token 分布要尽量一致
- 验证过程保证输出分布与直接用大模型生成完全相同（无损）
- 加速比取决于小模型的"猜中率"
- 通常加速 2-3 倍

### Prefix Caching（前缀缓存）
- 多个请求共享相同的 System Prompt
- 缓存 System Prompt 的 KV Cache，新请求直接复用
- vLLM 的 Automatic Prefix Caching：自动检测共享前缀
- SGLang 的 RadixAttention：基于基数树的 KV Cache 共享和复用

### Chunked Prefill
- 将长 Prefill 分块处理，与 Decode 交错执行
- 避免长 Prefill 独占 GPU，影响正在 Decode 的请求
- 降低 TTFT 的方差

### Disaggregated Inference（分离式推理）
- 将 Prefill 和 Decode 分离到不同的 GPU/实例
- Prefill 节点：计算密集，高 GPU 利用率
- Decode 节点：访存密集，优化 KV Cache 访问
- 各自独立扩缩容，资源利用更高效

## 4. 模型蒸馏与剪枝

### 知识蒸馏（Knowledge Distillation）

用大模型（Teacher）指导小模型（Student）学习：

```
蒸馏 Loss = alpha * KL(softmax(z_t/T), softmax(z_s/T))
          + (1-alpha) * CE(y, softmax(z_s))

z_t: Teacher 模型的 logits
z_s: Student 模型的 logits
T: 温度（通常 2-10，使分布更软）
y: 真实标签
```

**LLM 蒸馏方式**：
- **黑盒蒸馏**：用 Teacher 生成的文本作为 Student 的训练数据
  - 如 Alpaca 用 GPT-4 生成指令数据训练 LLaMA
  - 简单高效，但只能学到输出，学不到中间表示
- **白盒蒸馏**：同时利用 Teacher 的 logits 和中间层表示
  - 效果更好，但需要访问 Teacher 模型的参数
  - 可以逐层对齐（Layer-by-Layer）或注意力对齐

### 结构化剪枝
- 移除整个注意力头、FFN 中间维度、甚至整层
- 减少模型参数和计算量
- 需要少量数据重新校准/微调
- LLM-Pruner、SliceGPT 等方法

### 非结构化剪枝
- 将小权重置零（Magnitude Pruning）
- 产生稀疏矩阵，需要硬件/框架支持才能真正加速
- SparseGPT：一次性将 LLM 剪枝到 50% 稀疏度，精度损失小

## 5. 推理框架

### vLLM
- **最流行的生产级 LLM 推理框架**
- 核心技术：PagedAttention + Continuous Batching
- 兼容 OpenAI API 格式
- 支持多种量化格式（GPTQ, AWQ, FP8, INT8）
- 支持 TP（Tensor Parallelism）多卡并行
- 支持 LoRA 动态加载（多个 LoRA 适配器共享基础模型）

```bash
# 启动 vLLM 服务
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --tensor-parallel-size 2 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.9 \
    --enable-prefix-caching
```

### Ollama
- 一键本地运行大模型，开箱即用
- 自动管理模型下载和运行
- 基于 llama.cpp，支持 GGUF 量化
- 适合个人开发和测试

```bash
# 运行模型
ollama run qwen2.5:7b
ollama run deepseek-r1:14b
ollama run llama3:8b

# API 调用（兼容 OpenAI 格式）
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen2.5:7b", "messages": [{"role": "user", "content": "Hello"}]}'
```

### TGI（Text Generation Inference）
- HuggingFace 出品的推理框架
- 支持 FlashAttention、量化、流式输出
- Docker 部署，适合 HuggingFace 生态

### TensorRT-LLM
- NVIDIA 出品，深度优化 NVIDIA GPU
- 编译时将模型转为 TensorRT 引擎，极致优化
- 支持 INT4/INT8/FP8 量化
- 吞吐量通常最高，但部署复杂度也最高
- 适合追求极致性能的生产环境

### SGLang
- 面向复杂 LLM 程序的推理框架
- **RadixAttention**：基于基数树的 KV Cache 共享和复用
- 适合多轮对话、Agent、批量推理等场景
- 支持结构化输出（JSON Schema、正则约束）

### llama.cpp
- 纯 C/C++ 实现的 LLM 推理
- 支持 CPU 推理，内存占用极低
- GGUF 量化格式，支持 Q2 到 Q8 多种精度
- 适合边缘设备、消费级硬件

### 推理框架对比

| 框架 | 优势 | 适用场景 |
|------|------|---------|
| vLLM | 综合性能好，生态好 | 生产环境首选 |
| Ollama | 简单易用 | 本地开发测试 |
| TGI | HF 生态集成好 | HuggingFace 用户 |
| TensorRT-LLM | 极致性能 | 高吞吐生产环境 |
| SGLang | 复杂应用优化好 | Agent、多轮对话 |
| llama.cpp | CPU 友好，资源占用低 | 边缘设备、消费级 |

## 6. API 调用

### OpenAI 兼容 API（最通用的格式）
```python
from openai import OpenAI

client = OpenAI(
    api_key="your-key",
    base_url="https://api.openai.com/v1"  # 或其他兼容服务的地址
)

# Chat Completion
response = client.chat.completions.create(
    model="gpt-4",
    messages=[
        {"role": "system", "content": "你是一个有帮助的助手"},
        {"role": "user", "content": "什么是 RAG？"}
    ],
    temperature=0.7,
    max_tokens=2048,
    stream=True  # 流式输出
)

for chunk in response:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")
```

### 流式输出（SSE - Server-Sent Events）
- 模型每生成一个 token 就发送一次
- 用户体验好，不需要等全部生成完
- 前端用 EventSource 或 fetch + ReadableStream 处理
- 数据格式：`data: {"choices":[{"delta":{"content":"hello"}}]}\n\n`

### Function Calling / Tool Use
```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"}
                },
                "required": ["city"]
            }
        }
    }
]

response = client.chat.completions.create(
    model="gpt-4",
    messages=messages,
    tools=tools,
    tool_choice="auto"
)

# 模型返回 tool_calls → 应用层执行函数 → 把结果回传给模型
```

## 7. 部署架构

### 单机部署
- 适合小模型或低并发场景
- Ollama / vLLM 单实例
- 模型需要能放入单卡显存

### 多卡并行
- **Tensor Parallelism**：模型切分到多张 GPU（同一节点）
- vLLM: `--tensor-parallel-size 4`
- 适合单个大模型推理

### 分布式部署
- 多台机器协作
- 负载均衡（Nginx/Envoy）+ 多 vLLM 实例
- 水平扩展，处理高并发

### 推理成本优化策略
1. **选择合适的量化精度**：4-bit 通常性价比最高（精度损失小，速度快）
2. **Prefix Caching**：相同 System Prompt 复用 KV Cache
3. **Batch 大小调优**：增大 batch 提高 GPU 利用率
4. **Prompt 精简**：减少不必要的 System Prompt 内容
5. **模型选择**：根据任务难度选择合适大小的模型
6. **模型路由**：简单请求用小模型，复杂请求用大模型
7. **缓存层**：对相同/相似请求缓存结果（语义缓存）

### 高可用部署架构
```
用户请求
    ↓
负载均衡（Nginx/API Gateway）
    ↓
┌───────────────────┐
│   API 服务层      │  ← 限流、认证、参数校验
│  (FastAPI/Go)     │
└───────────────────┘
    ↓
┌───────────────────┐
│  模型路由/调度器   │  ← 根据请求类型分配到不同模型
└───────────────────┘
    ↓
┌──────┐ ┌──────┐ ┌──────┐
│vLLM-1│ │vLLM-2│ │vLLM-3│  ← 多实例水平扩展
│(7B)  │ │(7B)  │ │(70B) │
└──────┘ └──────┘ └──────┘
    ↓
监控系统（Prometheus + Grafana）
  - QPS、延迟、GPU 利用率、显存使用
  - 异常告警、自动扩缩容
```

## 面试高频问题

### Q1: LLM 推理的 Prefill 和 Decode 阶段有什么区别？
**答**：Prefill 一次处理整个输入 prompt，计算密集型，GPU 利用率高。Decode 逐 token 生成，每步只有 1 个 Q 与 KV Cache 做 attention，访存密集型，GPU 利用率低。TTFT 主要由 Prefill 决定，TPS 由 Decode 决定。

### Q2: Temperature、Top-K、Top-P 分别是什么？怎么调？
**答**：Temperature 控制概率分布的平滑度（越低越确定）；Top-K 只从最高概率的 K 个 token 中采样；Top-P 从累积概率达到 P 的最小集合中采样（动态候选集大小）。代码生成用低温度（0-0.2），创意写作用高温度（0.7-1.0）。

### Q3: vLLM 的 PagedAttention 原理？
**答**：类似 OS 虚拟内存分页，将 KV Cache 按固定大小的 Block 分配，不需要连续显存。请求按需申请 Block，完成后释放。消除了预分配导致的显存浪费和碎片，利用率提升 2-4 倍。还支持 Copy-on-Write，相同前缀的请求共享 KV Cache。

### Q4: Speculative Decoding 的原理？为什么能加速？
**答**：用小模型（Draft）快速生成 K 个候选 token，大模型（Target）一次 forward pass 并行验证。验证过程保证输出分布与直接用大模型完全相同（无损）。加速原理是将 K 次大模型的串行 Decode 变成 1 次并行验证。加速比取决于小模型的猜中率，通常 2-3 倍。

### Q5: Continuous Batching 为什么能提升吞吐？
**答**：传统 Static Batching 要等一个 batch 中最慢的请求完成才处理下一批，导致短请求等待浪费。Continuous Batching 在请求完成时立即返回，空出的 slot 立即放入新请求，GPU 始终保持忙碌，吞吐量可提升数倍。

### Q6: 如何在消费级显卡（24GB）上部署大模型？
**答**：7B 模型用 INT4 量化（约 4GB）可以跑在 RTX 3090/4090 上；13B 模型用 4-bit 量化（约 7GB）也可以。使用 Ollama（最简单）或 vLLM（生产级）。GGUF 格式支持 CPU + GPU 混合推理，可以将部分层放 CPU 运行。

### Q7: 知识蒸馏有哪些方式？
**答**：黑盒蒸馏用 Teacher 生成的文本作为 Student 的训练数据，简单高效但只学到输出分布。白盒蒸馏利用 Teacher 的 logits（soft targets）和中间层表示，效果更好但需要 Teacher 参数访问。LLM 领域黑盒蒸馏更常见（如用 GPT-4 生成训练数据）。

### Q8: 推理框架 vLLM、Ollama、TensorRT-LLM 怎么选？
**答**：vLLM 综合性能好，OpenAI 兼容 API，生产环境首选。Ollama 一键部署，适合本地开发测试。TensorRT-LLM 性能最高但部署复杂，适合追求极致吞吐的场景。如果是复杂 Agent 应用，SGLang 的 RadixAttention 对多轮对话更优。

### Q9: Prefill 和 Decode 分离部署的优势？
**答**：Prefill 计算密集适合高算力 GPU，Decode 访存密集适合大显存/高带宽配置。分离部署让各阶段独立扩缩容，避免长 Prefill 阻塞 Decode。可以根据流量模式灵活调整 Prefill/Decode 节点比例，整体资源利用率更高。

### Q10: 如何监控和优化 LLM 推理服务？
**答**：关键指标包括 TTFT、TPS、P99 延迟、QPS、GPU 利用率、显存使用率。优化手段：Prefix Caching 复用 KV Cache、调整 batch 大小、量化降低计算和显存开销、模型路由（简单任务用小模型）、语义缓存（相似问题直接返回缓存结果）、自动扩缩容。

# 操作系统

## 一、进程、线程与协程

### 1.1 进程（Process）

进程是**资源分配**的基本单位，拥有独立的内存空间。

**进程的内存布局**：
```
高地址 ┌──────────────┐
       │    内核空间    │  用户不可访问
       ├──────────────┤
       │     栈(Stack) │  局部变量、函数调用帧，向下增长
       │      ↓       │
       │              │
       │      ↑       │
       │   堆(Heap)   │  动态分配的内存（malloc/new），向上增长
       ├──────────────┤
       │  BSS 段      │  未初始化的全局/静态变量
       ├──────────────┤
       │  数据段(Data) │  已初始化的全局/静态变量
       ├──────────────┤
       │  代码段(Text) │  程序指令，只读
低地址 └──────────────┘
```

**进程状态转换**：
```
          创建
           |
           v
  ┌──→ 就绪(Ready) ←──────────┐
  │        |                    │
  │    调度(被CPU选中)           │
  │        |                    │
  │        v                    │
  │    运行(Running)             │
  │        |                    │
  │   ┌────┼──────┐             │
  │   │    │      │             │
  │   │ 时间片   I/O或      正常/异常
  │   │ 用完   事件等待     终止
  │   │    │      │             │
  │   │    │      v             │
  │   │    │  阻塞(Blocked)      │
  │   │    │      │             │
  │   └────┘  I/O完成或         │
  │           事件发生───────────┘
  │
  └── 被更高优先级抢占
```

**五种状态**：
1. **新建（New）**：进程正在被创建
2. **就绪（Ready）**：等待被 CPU 调度
3. **运行（Running）**：正在 CPU 上执行
4. **阻塞（Blocked/Waiting）**：等待某个事件（I/O 完成、获取锁等）
5. **终止（Terminated）**：执行完毕或被终止

### 1.2 线程（Thread）

线程是 **CPU 调度**的基本单位，同一进程的线程共享进程的内存空间。

**线程私有资源**：
- 线程 ID
- 程序计数器（PC）
- 寄存器集合
- 栈空间

**线程共享资源**（属于进程）：
- 代码段
- 数据段
- 堆空间
- 文件描述符表
- 信号处理函数

**用户线程 vs 内核线程**：

| 维度 | 用户线程 | 内核线程 |
|------|---------|---------|
| 管理者 | 用户空间的线程库 | 操作系统内核 |
| 切换开销 | 小（不需要陷入内核） | 大（需要陷入内核） |
| 并行性 | 一个进程只能用一个 CPU 核心 | 可以利用多核 |
| 阻塞影响 | 一个线程阻塞，整个进程阻塞 | 一个线程阻塞不影响其他 |

**线程模型**：
- **1:1 模型**：一个用户线程对应一个内核线程（Linux pthread）
- **N:1 模型**：多个用户线程映射到一个内核线程
- **M:N 模型**：M 个用户线程映射到 N 个内核线程（Go goroutine 的 GMP 模型）

### 1.3 协程（Coroutine）

协程是**用户态**的轻量级线程，由程序（而非内核）调度。

**特点**：
- 切换开销极小：只需保存/恢复少量寄存器，不涉及内核态切换
- 在单线程内通过协作式调度实现并发
- 可以主动让出执行权（yield）
- 内存占用小：Go goroutine 初始栈仅 2KB（线程通常 1~8MB）

**各语言协程实现**：

| 语言 | 实现方式 | 特点 |
|------|---------|------|
| Go | goroutine + GMP 调度器 | M:N 模型，可利用多核 |
| Python | asyncio / async-await | 单线程事件循环，基于生成器 |
| Java | 虚拟线程（Project Loom, JDK 21+） | M:N 模型，与现有 API 兼容 |
| Kotlin | Coroutines | 基于 CPS 变换 |
| Rust | async/await + tokio | 零成本抽象，编译期状态机 |

### 1.4 进程 vs 线程 vs 协程

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 调度者 | 操作系统 | 操作系统 | 用户程序 |
| 切换方式 | 内核态切换 | 内核态切换 | 用户态切换 |
| 切换开销 | 最大（~几ms） | 中等（~几十us） | 最小（~几百ns） |
| 内存占用 | 独立地址空间（MB~GB） | 共享进程空间，独立栈（1~8MB） | 极小栈（2KB~几十KB） |
| 数据共享 | IPC 机制 | 共享内存（需同步） | 共享内存（通常无竞争） |
| 并行性 | 多核并行 | 多核并行 | 取决于实现（Go 可多核） |
| 安全性 | 一个崩溃不影响其他 | 一个崩溃整个进程崩溃 | 一个崩溃整个线程崩溃 |
| 适用场景 | 隔离性要求高 | CPU 密集、需要并行 | I/O 密集、高并发 |

## 二、进程间通信（IPC）

### 2.1 管道（Pipe）

**匿名管道**：
- 半双工（数据单向流动）
- 只能在有亲缘关系的进程间使用（父子进程）
- 本质是内核中的一块缓冲区（通常 64KB）
- `pipe()` 系统调用创建

```c
int fd[2];
pipe(fd);
// fd[0] - 读端
// fd[1] - 写端
if (fork() == 0) {
    // 子进程：关闭写端，从读端读数据
    close(fd[1]);
    read(fd[0], buf, sizeof(buf));
} else {
    // 父进程：关闭读端，从写端写数据
    close(fd[0]);
    write(fd[1], "hello", 5);
}
```

**命名管道（FIFO）**：
- 以文件形式存在于文件系统中
- 无亲缘关系的进程也可以使用
- `mkfifo()` 创建

### 2.2 消息队列（Message Queue）

- 内核中维护的消息链表
- 进程可以向队列发送/接收消息
- 消息有类型，可以按类型选择性接收
- 独立于发送和接收进程的生命周期
- 缺点：消息有大小限制，拷贝开销大

### 2.3 共享内存（Shared Memory）

- 多个进程映射同一块物理内存到各自的虚拟地址空间
- **最快的 IPC 方式**：不需要内核中转，直接读写
- 需要配合同步机制（信号量、互斥锁）保证数据一致性
- `shmget()` / `shmat()` / `shmdt()` / `shmctl()`

```
进程 A 虚拟地址空间        物理内存          进程 B 虚拟地址空间
┌──────────┐          ┌──────────┐        ┌──────────┐
│          │          │          │        │          │
│  映射区  │ -------> │ 共享内存 │ <----- │  映射区  │
│          │          │          │        │          │
└──────────┘          └──────────┘        └──────────┘
```

### 2.4 信号量（Semaphore）

- 用于进程/线程间的**同步和互斥**
- 本质是一个计数器 + 等待队列
- **P 操作（wait）**：信号量 - 1，若 < 0 则阻塞
- **V 操作（signal）**：信号量 + 1，若 <= 0 则唤醒一个等待进程
- 二进制信号量（0/1）等价于互斥锁
- 计数信号量可用于控制资源并发访问数

### 2.5 信号（Signal）

- 一种**异步通知机制**
- 用于通知进程发生了某种事件
- 常见信号：SIGKILL(9), SIGTERM(15), SIGINT(2), SIGCHLD, SIGSEGV
- 进程可以忽略、捕获或使用默认处理
- SIGKILL 和 SIGSTOP 不能被忽略或捕获

### 2.6 Socket

- 可用于**不同机器**之间的进程通信
- 也可用于同一机器的进程通信（Unix Domain Socket）
- 支持 TCP/UDP/Unix 等多种协议
- 最通用的 IPC 方式

### 2.7 IPC 方式对比

| 方式 | 适用范围 | 数据流方向 | 速度 | 复杂度 | 典型场景 |
|------|---------|-----------|------|--------|---------|
| 匿名管道 | 父子进程 | 单向 | 中 | 低 | Shell 管道 `|` |
| 命名管道 | 同一机器 | 单向/双向 | 中 | 低 | 简单进程通信 |
| 消息队列 | 同一机器 | 双向 | 中 | 中 | 消息传递 |
| 共享内存 | 同一机器 | 双向 | 最快 | 高 | 大数据量传输 |
| 信号量 | 同一机器 | — | 快 | 中 | 同步/互斥 |
| 信号 | 同一机器 | 单向 | 快 | 低 | 事件通知 |
| Socket | 跨机器 | 双向 | 较慢 | 高 | 网络通信 |

## 三、进程调度算法

### 3.1 先来先服务（FCFS - First Come First Served）

- 按照进程到达顺序依次执行
- 非抢占式
- 优点：简单公平
- 缺点：平均等待时间长，对短进程不公平（**护航效应**：长进程后面的短进程等待很久）

### 3.2 最短作业优先（SJF - Shortest Job First）

- 优先调度预计执行时间最短的进程
- 非抢占式（SRTF 是其抢占式版本）
- 优点：平均等待时间最短
- 缺点：长进程可能**饥饿**；需要预知执行时间（实际中很难做到）

### 3.3 时间片轮转（RR - Round Robin）

- 每个进程分配一个固定时间片（如 10~100ms）
- 时间片用完后被强制切换到就绪队列末尾
- 优点：公平，响应时间短
- 缺点：时间片大小关键——太大退化为 FCFS，太小上下文切换开销大
- 适用于**分时系统**

### 3.4 优先级调度（Priority Scheduling）

- 每个进程有优先级，高优先级先执行
- 分为抢占式和非抢占式
- 缺点：低优先级进程可能**饥饿**
- 解决：**老化机制（Aging）**——等待时间越长，优先级越高

### 3.5 多级反馈队列（MLFQ - Multi-Level Feedback Queue）

**设计目标**：同时兼顾响应时间和吞吐量。

```
队列 0 [高优先级, 时间片=8ms]  → 新进程进入这里
    |（时间片用完降级）
    v
队列 1 [中优先级, 时间片=16ms]
    |（时间片用完降级）
    v
队列 2 [低优先级, 时间片=32ms]  → FCFS
```

**规则**：
1. 新进程进入最高优先级队列
2. 在当前队列中时间片用完，降到下一级队列
3. 在当前队列中主动放弃 CPU（如 I/O 等待），留在当前队列
4. 高优先级队列有进程时，低优先级队列不执行（可抢占）
5. 定期将所有进程提升到最高优先级队列（防止饥饿）

### 3.6 完全公平调度器（CFS - Completely Fair Scheduler）

Linux 默认的进程调度器（2.6.23 起）。

**核心思想**：
- 维护每个进程的**虚拟运行时间（vruntime）**
- 始终调度 vruntime 最小的进程
- 使用**红黑树**组织进程，最左节点就是 vruntime 最小的进程
- 高优先级进程的 vruntime 增长慢，低优先级的增长快
- 结果：高优先级进程获得更多 CPU 时间

**时间片计算**：
```
进程时间片 = 调度周期 * (进程权重 / 所有进程权重之和)
```

### 3.7 调度算法对比

| 算法 | 抢占 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| FCFS | 否 | 简单 | 护航效应 | 批处理 |
| SJF | 否 | 平均等待最短 | 饥饿、需预知时间 | 批处理 |
| RR | 是 | 公平、响应快 | 时间片大小敏感 | 分时系统 |
| 优先级 | 可选 | 灵活 | 饥饿 | 实时系统 |
| MLFQ | 是 | 综合最优 | 复杂 | 通用 OS |
| CFS | 是 | 公平、高效 | 实现复杂 | Linux |

## 四、死锁

### 4.1 死锁的定义

多个进程因竞争资源而互相等待，导致所有进程都无法继续执行。

### 4.2 四个必要条件

必须**同时满足**以下四个条件才会发生死锁：

1. **互斥条件**：资源一次只能被一个进程使用
2. **占有并等待**：进程持有至少一个资源，同时等待获取其他资源
3. **不可抢占**：已分配给进程的资源不能被强制收回
4. **循环等待**：存在进程的循环等待链 P1→P2→...→Pn→P1

### 4.3 死锁预防

**破坏其中一个必要条件**：

| 条件 | 破坏方法 | 代价 |
|------|---------|------|
| 互斥 | 使用无锁数据结构、读写锁 | 不是所有资源都能共享 |
| 占有并等待 | 一次性申请所有资源 | 资源利用率低 |
| 不可抢占 | 允许抢占资源（请求失败则释放已有资源） | 实现复杂，可能导致活锁 |
| 循环等待 | 资源编号排序，按序申请 | 编号困难，灵活性差 |

实际中最常用的是**破坏循环等待**：规定锁的获取顺序。

### 4.4 死锁避免——银行家算法

**核心思想**：在资源分配前检查系统是否处于**安全状态**。

**数据结构**：
- Available[m]：系统当前可用资源数
- Max[n][m]：每个进程的最大资源需求
- Allocation[n][m]：每个进程已分配的资源
- Need[n][m] = Max - Allocation：每个进程还需要的资源

**安全性检查算法**：
```
1. 初始化：Work = Available，Finish[i] = false
2. 找到一个进程 Pi，满足：Finish[i]=false 且 Need[i] <= Work
3. 假设 Pi 执行完毕：Work = Work + Allocation[i]，Finish[i] = true
4. 回到步骤 2
5. 如果所有 Finish[i] = true，则系统安全；否则不安全
```

**示例**：
```
3个进程，3种资源，Available = [3, 3, 2]

       Max    Allocation  Need    Available
P0   [7,5,3]  [0,1,0]   [7,4,3]  [3,3,2]
P1   [3,2,2]  [2,0,0]   [1,2,2]
P2   [9,0,2]  [3,0,2]   [6,0,0]

安全序列：P1 → P0 → P2
P1: Need[1,2,2] <= Available[3,3,2] ✓ → 完成后 Available = [5,3,2]
P0: Need[7,4,3] <= Available[5,3,2] × → 跳过
P2: Need[6,0,0] <= Available[5,3,2] × → 跳过
... 重新检查
P0: Need[7,4,3] <= [5,3,2] × → 仍不行
需要 P1 释放后重新评估...
```

### 4.5 死锁检测与恢复

**检测方法**：
- 资源分配图：检测是否存在环
- 定期运行死锁检测算法

**恢复方法**：
1. **终止进程**：
   - 终止所有死锁进程（代价大）
   - 逐个终止直到死锁解除（每次选代价最小的）
2. **资源抢占**：
   - 选择一个进程，抢占其资源给其他进程
   - 被抢占的进程回滚到安全状态

### 4.6 实际编程中避免死锁

```java
// 错误：可能死锁
synchronized(lockA) {
    synchronized(lockB) { ... }
}
// 另一个线程
synchronized(lockB) {
    synchronized(lockA) { ... }
}

// 正确：按固定顺序获取锁
synchronized(lockA) {    // 总是先获取 lockA
    synchronized(lockB) { ... }
}

// 更好：使用 tryLock 超时机制
if (lockA.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lockB.tryLock(1, TimeUnit.SECONDS)) {
            try { ... }
            finally { lockB.unlock(); }
        }
    } finally { lockA.unlock(); }
}
```

## 五、内存管理

### 5.1 虚拟内存

**核心思想**：每个进程拥有独立的**虚拟地址空间**，通过页表映射到物理内存。

**优点**：
- 进程隔离：每个进程有独立地址空间，互不干扰
- 内存共享：不同进程的虚拟页可以映射到相同物理页（共享库）
- 内存扩展：可以使用磁盘（swap）扩展可用内存
- 按需分配：只有被访问到的页面才会加载到物理内存

**地址转换过程**：
```
虚拟地址 → MMU（内存管理单元）→ 查页表 → 物理地址
                 |
            TLB 命中？
           /        \
         是          否
         |       查多级页表
         |           |
     物理地址    页面在内存中？
                /        \
              是          否
              |        缺页中断
          物理地址     → 从磁盘加载
                       → 可能触发页面置换
                       → 更新页表
                       → 重新访问
```

### 5.2 分页（Paging）

- 将虚拟内存和物理内存划分为固定大小的**页（Page）**和**页框（Frame）**
- 页大小通常 4KB（也有 2MB/1GB 大页）
- 虚拟地址 = 页号（VPN）+ 页内偏移（Offset）
- 页表记录虚拟页号 → 物理页框号的映射

**页表项（PTE）内容**：
- 物理页框号
- 有效位（Valid）：页面是否在内存中
- 脏位（Dirty）：页面是否被修改
- 访问位（Accessed/Referenced）：页面是否被访问过
- 保护位（Read/Write/Execute）：权限控制

### 5.3 多级页表

**问题**：32 位系统，4KB 页，需要 2^20 个页表项，每项 4 字节 → 4MB 页表/进程。
64 位系统下页表更大。

**解决**：多级页表，只为使用的虚拟地址空间分配页表。

```
二级页表（32位系统）：
虚拟地址 = [一级页号(10bit)] + [二级页号(10bit)] + [页内偏移(12bit)]

四级页表（x86-64，Linux）：
虚拟地址(48bit有效) = [PGD(9)] + [PUD(9)] + [PMD(9)] + [PTE(9)] + [Offset(12)]
```

**优点**：未使用的地址范围不需要分配页表，节省大量内存。
**缺点**：多次内存访问（每级页表一次），需要 TLB 加速。

### 5.4 TLB（Translation Lookaside Buffer）

- **页表缓存**：缓存最近使用的页表项
- 通常 64~1024 条目
- **全相联**或**组相联**结构
- 命中率通常 > 99%（利用局部性原理）
- TLB 未命中需要遍历多级页表（Page Walk），开销很大

### 5.5 分段（Segmentation）

- 按**逻辑结构**划分内存：代码段、数据段、栈段
- 段的大小可变
- 虚拟地址 = 段号 + 段内偏移
- 便于共享（共享代码段）和保护（不同段不同权限）
- 缺点：容易产生**外部碎片**

### 5.6 段页式（Segmentation with Paging）

- 先分段，再在段内分页
- 结合两者优点：逻辑结构清晰 + 消除外部碎片
- 地址转换：段号 → 段表 → 页表基址 → 页号 → 页表 → 物理地址

## 六、页面置换算法

当物理内存不足，需要将某个页面换出（swap out）到磁盘。

### 6.1 最优页面置换（OPT）

- 替换未来最长时间不会被访问的页面
- **理论最优**，缺页率最低
- 无法实现（需要预知未来），仅作为对比基准

### 6.2 先进先出（FIFO）

- 替换最先进入内存的页面
- 实现简单：用队列维护
- 性能差：可能替换频繁使用的页面
- **Belady 异常**：增加物理页框数反而可能增加缺页率

### 6.3 最近最少使用（LRU - Least Recently Used）

- 替换最长时间未被访问的页面
- 性能接近 OPT
- **实现方式**：
  - 方式一：每次访问记录时间戳，选最早的替换（开销大）
  - 方式二：链表，每次访问移到链表头部，淘汰链表尾部（常用）
  - 方式三：HashMap + 双向链表，O(1) 时间复杂度

**LRU 的代码实现（面试高频）**：
```java
class LRUCache {
    int capacity;
    Map<Integer, Node> map = new HashMap<>();
    Node head, tail;  // 虚拟头尾节点

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) return -1;
        moveToHead(node);  // 移到链表头部（最近使用）
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
        } else {
            if (map.size() == capacity) {
                Node removed = removeTail();  // 淘汰最久未用的
                map.remove(removed.key);
            }
            Node newNode = new Node(key, value);
            addToHead(newNode);
            map.put(key, newNode);
        }
    }
}
```

### 6.4 最不经常使用（LFU - Least Frequently Used）

- 替换访问次数最少的页面
- 访问次数相同时，替换最久未访问的（LRU）
- 缺点：新页面容易被淘汰（历史频率不代表未来）
- 改进：频率衰减，让历史频率随时间降低

### 6.5 时钟算法（Clock / Second Chance）

- LRU 的近似实现，开销更小
- 所有页面组成环形链表，指针指向当前位置
- 每个页面有一个**访问位（Reference Bit）**
- 淘汰时：
  1. 检查指针指向的页面
  2. 如果访问位 = 1，清零，指针前移（给它"第二次机会"）
  3. 如果访问位 = 0，淘汰该页面
- Linux 使用改进的 Clock 算法（考虑脏页优先级）

### 6.6 算法对比

| 算法 | 优点 | 缺点 | 复杂度 | 实际使用 |
|------|------|------|--------|---------|
| OPT | 最优 | 无法实现 | — | 仅作基准 |
| FIFO | 简单 | Belady 异常 | O(1) | 很少 |
| LRU | 性能好 | 实现开销大 | O(1)* | Redis 等 |
| LFU | 考虑频率 | 历史污染 | O(log n) | 部分缓存 |
| Clock | 开销小 | 近似 LRU | O(n) | Linux 内核 |

## 七、磁盘调度算法

### 7.1 先来先服务（FCFS）

- 按请求到达顺序服务
- 简单公平，但磁头移动距离长

### 7.2 最短寻道时间优先（SSTF - Shortest Seek Time First）

- 每次选择离当前磁头最近的请求
- 平均寻道时间短
- 缺点：可能导致远处请求**饥饿**

### 7.3 扫描算法（SCAN / 电梯算法）

- 磁头在一个方向上移动，服务沿途请求
- 到达一端后反向移动
- 两端请求等待时间不均匀

### 7.4 循环扫描（C-SCAN）

- 磁头只在一个方向上服务请求
- 到达一端后直接跳回另一端（不服务沿途请求）
- 等待时间更均匀

### 7.5 LOOK / C-LOOK

- SCAN/C-SCAN 的改进
- 磁头不需要到达最边缘，到最远请求位置就反向/跳回
- Linux 中 deadline、CFQ（Completely Fair Queuing）、BFQ 等 I/O 调度器

## 八、文件系统

### 8.1 inode（索引节点）

每个文件有一个 inode，存储**元信息**：

- 文件类型和权限
- 所有者（UID/GID）
- 文件大小
- 时间戳（atime, mtime, ctime）
- 硬链接计数
- 数据块指针（直接指针 + 间接指针 + 二级间接指针 + 三级间接指针）

**注意**：inode 不存储文件名，文件名存储在目录项中。

```
目录文件的内容：
┌────────────┬──────────┐
│ 文件名      │ inode 号 │
├────────────┼──────────┤
│ hello.txt  │   12345  │
│ world.txt  │   12346  │
└────────────┴──────────┘
```

### 8.2 软链接 vs 硬链接

| 维度 | 软链接（符号链接） | 硬链接 |
|------|-----------------|--------|
| 本质 | 独立文件，内容是目标路径 | 目录项指向同一个 inode |
| inode | 不同的 inode | 相同的 inode |
| 跨文件系统 | 可以 | 不可以 |
| 链接目录 | 可以 | 不可以（避免循环） |
| 原文件删除 | 失效（悬空链接） | 不受影响（inode 引用计数 > 0） |
| 创建命令 | `ln -s target link` | `ln target link` |
| 文件大小 | 路径字符串长度 | 与原文件相同 |

### 8.3 日志文件系统（Journaling File System）

**问题**：断电或崩溃时，文件系统可能处于不一致状态。

**解决**：先将操作写入**日志（Journal）**，再执行实际操作。

**三种日志模式**：
1. **Journal 模式**：元数据和数据都写入日志 → 最安全，性能最差
2. **Ordered 模式**（ext4 默认）：先写数据，再写元数据日志 → 安全性和性能平衡
3. **Writeback 模式**：只写元数据日志，数据写入顺序不保证 → 性能最好，可能丢数据

**常见日志文件系统**：ext3, ext4, XFS, Btrfs, NTFS

### 8.4 虚拟文件系统（VFS）

Linux 的 VFS 层提供统一的文件操作接口，屏蔽底层不同文件系统的差异。

```
应用程序
    |
   VFS（虚拟文件系统）
    |
┌───┴────┬──────┬──────┐
ext4   XFS   NFS   procfs
```

## 九、零拷贝技术

### 9.1 传统数据传输过程

从磁盘读取文件并通过网络发送（传统方式）：

```
1. read():  磁盘 → 内核缓冲区 → 用户缓冲区    （2次拷贝，2次上下文切换）
2. write(): 用户缓冲区 → Socket 缓冲区 → 网卡   （2次拷贝，2次上下文切换）

共计：4 次数据拷贝，4 次上下文切换
```

### 9.2 mmap（内存映射）

```c
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
```

- 将文件映射到用户空间虚拟内存
- 用户空间和内核空间**共享**同一块物理内存
- 减少一次拷贝：磁盘 → 内核缓冲区/用户映射区 → Socket 缓冲区 → 网卡
- **3 次拷贝，4 次上下文切换**

### 9.3 sendfile

```c
ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
```

- 直接在内核空间从文件描述符传输到 Socket 描述符
- 数据不经过用户空间
- **3 次拷贝（DMA→内核→Socket→DMA），2 次上下文切换**
- 如果网卡支持 SG-DMA（Scatter-Gather DMA），可以进一步优化为 **2 次拷贝**

```
sendfile + SG-DMA：
磁盘 --DMA拷贝--> 内核缓冲区
内核缓冲区 --SG-DMA--> 网卡
（只传文件描述符和长度到 Socket 缓冲区，无需数据拷贝）
```

### 9.4 splice

```c
ssize_t splice(int fd_in, off_t *off_in, int fd_out, off_t *off_out,
               size_t len, unsigned int flags);
```

- 在两个文件描述符之间通过**管道**传输数据
- 不需要内核/用户空间之间的拷贝
- 适用于管道和 Socket 之间的数据传输

### 9.5 零拷贝技术对比

| 方式 | 数据拷贝次数 | 上下文切换 | 适用场景 |
|------|------------|-----------|---------|
| 传统 read+write | 4 次 | 4 次 | — |
| mmap+write | 3 次 | 4 次 | 需要修改数据 |
| sendfile | 2~3 次 | 2 次 | 静态文件传输 |
| sendfile+SG-DMA | 2 次 | 2 次 | 静态文件传输 |
| splice | 2 次 | 2 次 | 管道/Socket 传输 |

**实际应用**：
- Kafka：使用 sendfile 实现高效消息传输
- Nginx：使用 sendfile 传输静态文件
- RocketMQ：使用 mmap 读写 CommitLog
- Java NIO：`FileChannel.transferTo()` 底层使用 sendfile

## 十、面试高频问题

### Q1：进程和线程的区别？
**答**：进程是资源分配的基本单位，有独立内存空间；线程是 CPU 调度的基本单位，共享进程内存。进程切换开销大（需要切换页表等），线程切换开销小。进程间通信需要 IPC 机制，线程直接共享内存。一个进程崩溃不影响其他进程，一个线程崩溃导致整个进程崩溃。

### Q2：线程和协程的区别？
**答**：线程由操作系统内核调度，切换需要陷入内核态；协程由用户程序调度，在用户态切换，开销极小。线程栈通常 1~8MB，协程栈可以很小（Go goroutine 2KB）。线程是抢占式调度，协程通常是协作式调度。协程适合 I/O 密集型的高并发场景。

### Q3：死锁的四个必要条件？如何预防？
**答**：互斥、占有并等待、不可抢占、循环等待。实际中最常用的是破坏循环等待：规定所有线程按相同顺序获取锁。也可以使用 tryLock 超时机制避免死锁。

### Q4：什么是虚拟内存？有什么好处？
**答**：虚拟内存为每个进程提供独立的虚拟地址空间，通过页表映射到物理内存。好处：进程隔离（安全）、内存扩展（可使用 swap）、按需加载（节省物理内存）、内存共享（共享库只需一份物理内存）。

### Q5：LRU 算法的原理？如何用 O(1) 实现？
**答**：LRU 淘汰最近最少使用的页面。使用 HashMap + 双向链表实现 O(1)：HashMap 存储 key→Node 映射实现 O(1) 查找；双向链表维护访问顺序，最近访问的在头部，最久未访问的在尾部。get 时移到链表头；put 时若满则移除链表尾。

### Q6：进程间通信有哪些方式？
**答**：管道（匿名管道/命名管道）、消息队列、共享内存（最快）、信号量（同步/互斥）、信号（异步通知）、Socket（可跨机器）。共享内存速度最快，因为不需要内核中转数据。

### Q7：什么是缺页中断（Page Fault）？
**答**：进程访问的虚拟页面不在物理内存中时，MMU 触发缺页中断。OS 的缺页处理程序从磁盘（swap 或文件）加载页面到物理内存，更新页表，然后重新执行导致缺页的指令。如果物理内存已满，需要先执行页面置换算法淘汰一个页面。

### Q8：什么是上下文切换？开销有哪些？
**答**：上下文切换是 CPU 从一个进程/线程切换到另一个的过程。开销包括：保存和恢复寄存器、切换内核栈、切换页表（进程切换）、TLB 刷新（进程切换）、CPU 缓存失效等。进程切换比线程切换开销更大，因为需要切换页表和刷新 TLB。

### Q9：什么是零拷贝？有哪些实现方式？
**答**：零拷贝是指在数据传输过程中减少 CPU 拷贝次数的技术。实现方式包括：mmap（文件映射到用户空间，减少一次拷贝）、sendfile（内核空间直接传输，不经过用户空间）、splice（管道传输）。Kafka 使用 sendfile，RocketMQ 使用 mmap。

### Q10：解释一下 Linux 的 CFS 调度器？
**答**：CFS（完全公平调度器）维护每个进程的虚拟运行时间（vruntime），始终调度 vruntime 最小的进程。使用红黑树组织进程，高优先级进程 vruntime 增长慢从而获得更多 CPU 时间。目标是让每个进程获得公平的 CPU 份额。

### Q11：软链接和硬链接的区别？
**答**：硬链接是目录项指向同一个 inode，删除原文件不受影响，不能跨文件系统，不能链接目录；软链接是独立的文件，内容是目标路径，删除原文件则失效，可以跨文件系统和链接目录。

### Q12：什么是内存泄漏？如何检测？
**答**：程序分配了内存但没有释放，导致可用内存持续减少。C/C++ 可以用 Valgrind 检测；Java 可以用 JVM 工具（jmap, MAT）分析堆转储；Go 用 pprof 分析内存使用。常见原因：未关闭的资源、无限增长的集合、未取消的监听器/回调。

### Q13：FIFO 页面置换有什么 Belady 异常？
**答**：FIFO 算法中，增加页框数量反而可能导致缺页率上升，这称为 Belady 异常。例如对访问序列 1,2,3,4,1,2,5,1,2,3,4,5，3 个页框缺页 9 次，4 个页框缺页 10 次。LRU 和 OPT 不会出现 Belady 异常。

### Q14：银行家算法的核心思想？
**答**：在资源分配前检查系统是否处于安全状态。安全状态是指存在一个安全序列，使得每个进程都能获得所需资源并完成执行。分配前模拟分配，如果分配后系统仍安全则执行分配，否则拒绝。

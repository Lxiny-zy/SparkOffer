# 高可用架构

## 1. 高可用核心指标

### SLA（服务等级）
| 可用性 | 年宕机时间 | 应用场景 |
|--------|------------|----------|
| 99% | 3.65 天 | 内部工具 |
| 99.9% | 8.76 小时 | 普通业务 |
| 99.95% | 4.38 小时 | 互联网常见 |
| 99.99% | 52.56 分钟 | 支付、金融 |
| 99.999% | 5.26 分钟 | 电信、银行核心 |

### MTBF / MTTR
- **MTBF**（Mean Time Between Failures）：平均无故障时间
- **MTTR**（Mean Time To Recover）：平均恢复时间
- **可用性 = MTBF / (MTBF + MTTR)**

提升可用性：**降低 MTTR > 增加 MTBF**（故障无法完全避免，快速恢复更实际）。

## 2. 高可用三大策略

### 1. 冗余（Redundancy）
消除单点，部件坏了还有备用。
- 多实例部署
- 主从复制
- 多活架构

### 2. 隔离（Isolation）
避免故障扩散。
- 限流熔断降级
- 线程池隔离
- 资源隔离
- 故障域隔离

### 3. 自愈（Self-healing）
故障发生后自动恢复。
- 健康检查
- 自动重启
- 自动切换
- 自动扩容

---

## 3. 冗余设计

### 无状态服务冗余

```
客户端 → LB → 多个应用实例
```

- 实例完全相同，任一挂可用其他
- 不存状态（Session → Redis）
- 横向扩展容易

### 有状态服务冗余

**主从复制**：
- Master 写，Slave 读 + 备份
- Master 挂 → Slave 晋升
- MySQL / Redis / MongoDB / Kafka

**多主**：
- 多个 Master 都可读写
- 冲突解决（时间戳、版本）
- 复杂但可用性最高

### 数据冗余
- 至少 2 副本
- 跨机房：防机房级故障
- 跨地域：防地域级灾难

---

## 4. 隔离设计

### 线程池隔离

```java
// 不同业务独立线程池
@Bean("payThreadPool")
ThreadPoolExecutor payPool() { ... }

@Bean("orderThreadPool")
ThreadPoolExecutor orderPool() { ... }
```

防止一个业务阻塞拖垮全站（Hystrix 的思想）。

### 数据库隔离
- 核心业务独立库
- 读写分离
- 冷热分离

### 租户隔离
- 独立资源（独立 DB/Redis）
- 共享资源 + 限流

### 故障域隔离
- 可用区（AZ）隔离
- 机房隔离
- 区域（Region）隔离

---

## 5. 多活架构

### 同城多活
```
同城两个机房（A/B），同时提供服务
数据同步（延迟 < 毫秒级）
故障时全部流量切另一机房
```

**挑战**：数据同步冲突、流量调度。

### 异地多活
```
北京 ↔ 上海 ↔ 深圳
每地独立服务，数据互相复制
```

**挑战**：
- 网络延迟（跨省 30-50ms）
- 数据一致性
- 流量路由（按用户地域）

### 单元化
用户划分到"单元"，单元内闭环（数据、服务都在一单元）。

**例**：支付宝、淘宝架构
- 用户按 UID 分片到单元
- 同单元内完成交易
- 跨单元走异步

### 读写分离
- 就近读：用户所在区域读
- 中心写：单中心写 + 异步同步到各地
- 适合读多写少

---

## 6. 故障检测与切换

### 健康检查
- **HTTP**：GET /health 200 OK
- **TCP**：端口可连
- **业务**：查 DB、Redis 通

### 心跳机制
- Consul / Zookeeper / Nacos
- 节点定期上报
- 超时未上报 → 摘除

### 故障切换

**主从切换**：
- MySQL MHA / Orchestrator
- Redis Sentinel / Cluster
- MongoDB Replica Set 选举

**切换时间**：
- 检测：几秒-几十秒
- 选主：几秒
- DNS 切换：几秒-几分钟
- 总计：通常 30 秒-几分钟

### 脑裂（Split Brain）
网络分区导致多主同时存活。

**防脑裂**：
- **Quorum**：多数派决策（N/2+1）
- **Fence**：强制隔离旧主（关机、断网）
- **奇数节点**：避免 50/50 分区
- **见证节点**：额外投票节点

---

## 7. 限流、熔断、降级

见高并发章节，核心：**保护自己 + 保护下游**。

### 限流（防入侵）
- 网关层：Sentinel、Gateway
- 应用层：Resilience4j
- DB 层：连接池限制

### 熔断（防扩散）
```java
@CircuitBreaker(name = "userService", fallbackMethod = "fallback")
public User getUser(Long id) { ... }
```

### 降级（保核心）
- 预案：活动期间关评论、推荐
- 工具：Apollo 配置开关
- 自动降级：依赖服务挂立即切

---

## 8. 服务治理

### 超时
**谁都要设超时**：
- DB 查询：5s
- Redis：500ms
- 下游 HTTP：3s
- MQ 消费：30s

**层叠**：调用链上超时要**上游 > 下游**。

### 重试
- 只重试**幂等**操作
- 指数退避
- 最多 3 次
- 区分可重试/不可重试错误

### 幂等
- 接口：唯一请求 ID
- DB：唯一索引 / 乐观锁
- Redis：SET NX

### 异步解耦
核心链路短，非核心异步（MQ）。

---

## 9. 容灾与备份

### 备份策略
- **全量**：定期（每日）
- **增量**：频繁（每小时）
- **日志**：binlog、WAL 连续归档
- **异地备份**：跨地域

### 恢复演练
- 定期演练（RTO/RPO 达标）
- **RTO**（Recovery Time Objective）：可接受的恢复时间
- **RPO**（Recovery Point Objective）：可接受的数据丢失量

### 灾难恢复等级
- **冷备**：备份存着，故障时恢复（小时级）
- **温备**：备用系统就绪但不跑（分钟级）
- **热备**：备用系统跑着同步（秒级）
- **多活**：备用系统承担流量（秒级无感）

## 10. 无状态化

**原则**：应用无状态，状态外置到 Redis / DB。

```
传统：
  Tomcat 内存 Session → 无法横向扩展

改造：
  Session 存 Redis → 任一实例处理任一请求

```

好处：
- 随意扩缩容
- 实例故障无感知
- K8s 滚动更新无损

### 滚动发布

- 节省资源

### A/B 测试
- 按用户特征分流（新老、地域、活跃）
- 对比业务指标
- 产品决策用

### 理念

### 实验类型

- 断网络
- 注入 CPU/内存压力

### 工具

- 阿里 **ChaosBlade**

### 原则

- 有止血开关
- 监控实时

## 14. 架构演进案例

### V1：单体
```
Nginx → Tomcat → MySQL
```
简单，但单点多，可用性低。

### V2：主从 + 负载均衡
```
Nginx（主备） → 多 Tomcat → MySQL 主从
```
消除 LB 和 Tomcat 单点，DB 主从。

### V3：微服务 + 集群
```
LB → API Gateway → 多微服务
                 ↓
             Redis / MySQL / MQ 集群
```
服务独立，故障隔离。

### V4：多机房
```
北京机房 ←同步→ 上海机房
每机房独立 API Gateway / 微服务 / DB 主 / Redis
流量按地域路由
```
机房级容灾。

### V5：单元化异地多活
```
北京单元 | 上海单元 | 深圳单元
用户按 UID 分单元
单元内闭环
跨单元异步
```
地区级容灾，无感切换。

## 15. 容量规划

### 当前容量
- 单机 QPS
- 机器数
- 峰值利用率

### 未来容量
- 业务增长预测
- 活动峰值

### 瓶颈识别
- CPU：压测找单机极限

### 扩容预案
- 应用：K8s HPA 自动扩
- DB：读从库水平加、写分库
- Redis：Cluster 加分片

## 16. 常见反模式

1. **单点**：无备份、无冗余
2. **无降级方案**：下游挂全挂
3. **无限重试**：雪崩
4. **同步阻塞调用链**：超时累积
5. **混合部署**：核心与非核心同机器
6. **配置硬编码**：改配置要发版
7. **缺乏监控**：出事不知道
8. **测试不充分**：线上踩坑
9. **无预案**：故障临时抓瞎
10. **忽视运维**：开发完就交给运维

## 面试高频问题

**Q1：如何设计高可用系统？**

三板斧：
- **冗余**：消除单点（集群、主从、多活）
- **隔离**：限流、熔断、降级，隔离故障域
- **自愈**：健康检查、自动重启、自动切换

关键：**假设任何组件都会挂**，设计时思考"这个组件挂了怎么办"。

**Q2：MTTR 和 MTBF 哪个更重要？**

两者都重要，但**降低 MTTR 更实际**。故障无法根除，关键是**快速恢复**：
- 监控告警及时（发现快）
- 自动切换（恢复快）
- 预案明确（执行快）

99.99% 可用 = 月宕机 4 分钟。即便 MTBF 很长，单次 1 小时故障就不达标。

**Q3：主从切换的核心问题？**

- **数据丢失**：主挂时未同步到从的数据丢
- **脑裂**：网络分区导致双主
- **切换时间**：检测 + 选主 + 路由
- **客户端感知**：连接池失效重连

解决：
- 半同步复制减少丢失
- Quorum 防脑裂
- VIP / DNS / Proxy 切换
- 客户端 retry

**Q4：如何做异地多活？**

核心：**单元化 + 数据分片 + 就近路由**。

- 用户按 UID 分单元
- 单元内闭环（UI → DB）
- 跨单元用异步
- 主库按单元分，各单元互相同步
- 流量网关路由到正确单元

难点：**数据一致性**（跨单元事务、热点用户切单元）。

**Q5：熔断器状态转换？**

- **CLOSED**（正常）：计数请求和失败
- 失败率超阈值 → **OPEN**
- **OPEN**（熔断）：所有请求直接失败
- 等待时间到 → **HALF_OPEN**
- **HALF_OPEN**（半开）：放行少量请求
- 成功率达标 → **CLOSED**；否则 → **OPEN**

目的：下游故障时**快速失败**，避免资源耗尽（雪崩）。

**Q6：降级和限流区别？**

- **降级**：主动，预知繁忙放弃非核心（关评论）
- **限流**：被动，超能力直接拒

限流保护自己；降级保护核心功能。大促期间通常两者并用。

**Q7：容灾等级如何选？**

根据业务价值：
- **非核心**：冷备（备份存着）
- **一般业务**：温备（备用系统待命）
- **核心业务**：热备（备用同步跑着）
- **关键业务**：多活（无感切换）

成本：冷备 < 温备 < 热备 < 多活。权衡成本和 RTO。

**Q8：混沌工程怎么开展？**

从小到大：
1. 测试环境注入故障，验证监控告警
2. 预发环境演练，验证恢复流程
3. 生产小范围实验（随机杀 1 个 Pod）
4. 逐步扩大到网络延迟、依赖故障
5. 全区域容灾演练

前提：完善监控、有止血开关、团队同步。

**Q9：SLI / SLO / SLA 区别？**

- **SLI**（Indicator，指标）：实际测量值（如 P99 延迟 = 200ms）
- **SLO**（Objective，目标）：内部目标（P99 < 300ms）
- **SLA**（Agreement，协议）：对用户承诺（可用性 99.9%，赔偿条款）

SLI 支撑 SLO，SLO 支撑 SLA。SLO 通常比 SLA 更严格（留 buffer）。

**Q10：K8s 如何支持高可用？**

- **多副本**：`replicas: 3`
- **反亲和**：Pod 打散到不同节点
- **健康检查**：livenessProbe（挂了重启）、readinessProbe（就绪才接流量）
- **滚动更新**：`maxSurge / maxUnavailable`
- **HPA**：自动扩缩容
- **Service**：LB 屏蔽 Pod 变化
- **PDB**（PodDisruptionBudget）：节点维护时保证最少可用数
- **多可用区**：跨 AZ 部署
- **故障转移**：节点挂 → Pod 重新调度

# 高并发系统设计

## 1. 高并发核心指标

### 关键指标
- **QPS**（Queries Per Second）：每秒查询数
- **TPS**（Transactions Per Second）：每秒事务数
- **RT**（Response Time）：响应时间（P50 / P95 / P99）
- **并发数**：同时处理的请求数
- **吞吐量**：单位时间处理的请求量
- **可用性**：SLA（99.9% / 99.99% / 99.999%）

### 关系
```
并发数 ≈ QPS × 平均 RT
```
如 1000 QPS × 100ms RT = 100 并发。

### 目标示例
- 日订单 1000 万 → 平均 QPS ≈ 115，峰值 10 倍 ≈ 1150 QPS
- P99 < 500ms
- 可用性 99.95%

---

## 2. 高并发三大策略

### 策略 1：分散压力（水平扩展）
- 负载均衡：多实例
- 分库分表：数据水平
- 分片：Redis Cluster、ES、Kafka
- 多活：多地部署

### 策略 2：削峰填谷（缓冲）
- 消息队列：流量洪峰转异步
- 请求合并：批量处理
- 限流：超出能力直接拒

### 策略 3：短路返回（缓存）
- 多级缓存：本地 + 分布式
- CDN：静态资源
- 预计算：冷数据提前算好

## 3. 缓存架构

### 多级缓存

```
用户请求
   ↓
[浏览器缓存] ← 私有，HTTP Cache-Control
   ↓
[CDN]       ← 静态资源、边缘
   ↓
[Nginx 缓存] ← proxy_cache
   ↓
[应用本地缓存] ← Caffeine/Guava（毫秒级）
   ↓
[分布式缓存] ← Redis（< 10ms）
   ↓
[数据库]
```

### 缓存策略

**Cache Aside（旁路缓存，最常用）**
```
读：
  查缓存 → 命中返回
         ↓ 未命中
  查 DB → 写缓存 → 返回

写：
  更新 DB → 删除缓存
```

**Read Through / Write Through**
缓存层封装 DB 读写，应用只操作缓存。

**Write Behind（异步写回）**
写缓存 → 异步批量写 DB。性能高但有数据丢失风险。

### 缓存三大问题

**缓存穿透**（查不存在的 key）
- 布隆过滤器
- 缓存空值（短 TTL）

**缓存击穿**（热点 key 失效）
- 互斥锁重建（Redis setnx）
- 永不过期 + 异步刷新
- 逻辑过期

**缓存雪崩**（大量 key 同时失效）
- TTL 加随机
- 多级缓存
- 熔断降级

### 热点 Key
- **本地缓存**：JVM 内存缓存热点（Caffeine）
- **多副本**：key + 随机数打散到多 Redis 节点
- **读写分离**：读走从节点

## 4. 数据库优化

### 读多场景
- **读写分离**：1 主多从
- **从库延迟**：关键写后读走主库
- **Redis 前置**：热数据走缓存
- **物化视图**：预计算复杂查询

### 写多场景
- **分库分表**：水平拆分
- **批量写**：合并多次写入
- **异步写**：MQ 削峰
- **LSM 树存储**（HBase、RocksDB）

### 分库分表

**垂直拆分**：
- 按业务拆（订单、用户、商品各独立库）
- 大字段单独表（text 列独立）

**水平拆分**：
- 按用户 ID hash 分 16/32/64 库
- 按时间范围（按月分表）

**路由**：
- 应用层路由（ShardingSphere、MyCAT）
- 代理层（ProxySQL）

**分布式 ID**：
- 雪花（Snowflake）
- 号段（Leaf/TinyID）
- Redis INCR

**跨库问题**：
- JOIN → 冗余数据 / 应用层聚合
- 事务 → 最终一致性（MQ、Saga）
- 分页 → 归并

## 5. 消息队列削峰

### 作用
- **异步**：主流程立即返回，非核心后台
- **解耦**：上下游独立演进
- **削峰**：洪峰转入队列慢慢消费

### 典型模式

**订单秒杀**：
```
前端 → 接入层 → Redis 扣库存 → MQ 发下单消息 → 返回"排队中"
                                    ↓
                             订单服务按能力消费
                                    ↓
                             DB 生成订单，WebSocket 推送结果
```

**批量写**：
```
100 次请求 → MQ 聚合 → 每秒批量 INSERT → DB
```

### 削峰量化
- 峰值：10000 QPS 持续 1 分钟
- 平均能力：1000 QPS
- 队列至少存 `(10000 - 1000) × 60 = 54万` 消息
- 恢复时间：`54万 / 1000 ≈ 9 分钟`

## 6. 限流

### 算法

**计数器**
```
简单但有临界问题
窗口交界处可能 2× 请求
```

**滑动窗口**
```
细分窗口（如 1s 分 10 份），按时间滚动
较精确
```

**漏桶**
```
固定速率流出，超出即溢出
平滑流量
```

**令牌桶**
```
按速率生成令牌，请求拿令牌
允许突发
推荐
```

### 实现

**单机**：
- Guava `RateLimiter`
- Resilience4j `RateLimiter`
- Semaphore（并发控制）

**分布式**：
- Redis + Lua（滑动窗口）
- Sentinel / Hystrix
- Nginx `limit_req`

### Redis Lua 滑动窗口

```lua
local key = KEYS[1]
local window = tonumber(ARGV[1])
local max_req = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < max_req then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, window / 1000)
    return 1
end
return 0
```

### 限流维度
- 全局：所有请求
- 接口：某 API
- 用户：UID
- IP：反爬
- 租户：多租户

## 7. 熔断与降级

### 熔断（Circuit Breaker）
下游故障时快速失败，避免雪崩。

**三态**：
- CLOSED（正常）
- OPEN（熔断）
- HALF_OPEN（试探）

**触发条件**：
- 错误率 > 50%
- 错误数 > 100/分钟
- 响应时间 > 阈值

**工具**：Sentinel、Resilience4j、Hystrix（废弃）

### 降级
系统繁忙时**主动放弃**非核心功能。

**层次**：
- **功能降级**：隐藏评论、推荐
- **服务降级**：返回兜底数据
- **数据降级**：返回静态页
- **业务降级**：只保下单，关商品详情

### 开关控制
Apollo / Nacos 配置中心动态开关。

## 8. 秒杀系统经典案例

### 特点
- 瞬时流量（峰值 10 万+ QPS）
- 库存有限（1000 件）
- 防超卖
- 防刷

### 方案

**1. 前端**
- 活动页静态化 + CDN
- 按钮倒计时前置
- 提交后按钮置灰
- 验证码（图片/滑块/行为）

**2. 接入层**
- Nginx 限流（IP）
- 缓存商品详情

**3. 业务层**
- 风控：黑名单、限购
- 请求合并：排队

**4. 库存预减**
```lua
-- Redis Lua 原子扣减
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
end
return 0
```
扣减失败立即返回，不走后续。

**5. 下单异步**
```
Redis 扣减成功 → MQ 发消息 → 前端返回"排队中"
消费者慢速处理 → DB 扣减 + 创建订单 → 通知结果
```

**6. DB 防超卖**
```sql
UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0
-- 乐观锁，WHERE qty > 0 保证不超卖
```

**7. 异步对账**
Redis 与 DB 不一致时，定时任务校对。

## 11. 压测与容量评估

### 压测工具
- **JMeter**：界面，功能全
- **wrk**：命令行，性能强
- **Gatling**：Scala，报表好
- **k6**：JS 脚本，云原生

### 压测步骤
1. 单接口压测：找瓶颈接口
2. 全链路压测：真实场景
3. 极限压测：找崩溃点
4. 持续压测：稳定性

### 容量规划
- **基础公式**：`需要机器数 = 峰值 QPS / 单机 QPS × 冗余系数（1.5-2）`
- **冗余因素**：GC、CPU 抖动、网络、故障

### 关键指标
- CPU 使用率 < 70%（留 GC 空间）
- 内存使用率 < 80%
- 磁盘 IO < 70%
- 网络 < 70%
- P99 延迟 < 目标

## 13. 常见陷阱

1. **缓存无 TTL**：数据不一致
2. **缓存雪崩**：同时过期导致 DB 打爆
3. **大 key**：Redis 大 value 阻塞
4. **热 key**：单节点被打爆
5. **长事务**：锁行时间长、影响并发
6. **N+1 查询**：循环里查 DB
7. **同步调用过多**：链路过长
8. **无降级**：下游挂导致全挂
9. **无限流**：流量洪峰瞬间打挂
10. **日志太多**：IO 阻塞主流程

## 面试高频问题

**Q1：高并发系统设计的核心思想？**

三板斧：
- **分散**：水平扩展（多实例、分库分表）
- **缓冲**：异步削峰（MQ、限流）
- **短路**：缓存（多级）

配合高可用（冗余、隔离、自愈）。

**Q2：缓存 Cache Aside 模式为什么先删缓存后更新 DB 有问题？**

场景：
- 线程 A 删缓存
- 线程 B 读，未命中，查 DB 旧值，写缓存
- 线程 A 更新 DB 新值
- 结果：缓存是旧值

**正确**：先更新 DB，再删缓存（依然有少量不一致窗口但概率极低）。

**补偿**：延迟双删（更新 DB → 删缓存 → 延时 500ms → 再删）。

**Q3：如何设计一个秒杀系统？**

分层过滤（每层淘汰 90% 请求）：
1. 前端：静态化、CDN、按钮置灰
2. 网关：IP 限流
3. 接入：验证码、风控
4. Redis：原子扣减（Lua）
5. MQ：异步下单
6. DB：乐观锁防超卖

关键点：预减库存用 Redis，下单异步化，数据最终一致。

**Q4：缓存击穿怎么解决？**

热点 key 失效的瞬间，大量请求穿透到 DB：
1. **互斥锁**：Redis setnx 抢锁，成功者查 DB 并回填，其他等待重试
2. **永不过期**：key 不设 TTL，异步更新
3. **逻辑过期**：value 内含过期时间，业务判断
4. **本地缓存**：Caffeine 再挡一层

**Q5：Redis 热 key 如何解决？**

- **本地缓存**：应用进程内缓存（Caffeine），减少 Redis 访问
- **副本**：key 分成 `key:0, key:1, ..., key:N`，客户端随机读一个
- **监控**：Redis `hotkeys` 命令、client side
- **Proxy 层**：代理做热 key 拦截

**Q6：分库分表如何选路由？**

- **Hash**：`user_id % N`（均匀但不便扩容）
- **Range**：按时间或 ID 范围
- **一致性 Hash**：扩容时迁移少
- **ID 分段**：号段映射表

实务：hash 为主，扩容用"成倍扩容 + 旧表保留"。

**Q7：如何设计限流？**

维度：
- 全局：保护系统
- 接口：保护下游
- 用户：防单用户滥用
- 租户：隔离

算法：令牌桶为主（允许突发）。

实现：
- 单机：Guava RateLimiter
- 集群：Redis Lua 滑动窗口
- 网关层：Sentinel / Spring Cloud Gateway

**Q8：熔断和降级的区别？**

- **熔断**：被动，下游故障时快速失败（电路保护）
- **降级**：主动，系统繁忙时放弃非核心功能

**例**：支付服务挂了 → 订单服务熔断支付调用（不打爆）；大促时主动降级商品评论（放弃加载）。

**Q9：如何评估系统容量？**

1. **业务预测**：日订单、峰值 QPS
2. **压测**：单机极限 QPS
3. **计算**：`机器数 = 峰值 / 单机 × 1.5`
4. **验证**：全链路压测，找木桶短板
5. **持续监控**：容量水位告警

**Q10：系统变慢如何排查？**

分层定位：
1. **前端**：浏览器 DevTools 看时间分布
2. **网关**：网关层延迟
3. **应用**：APM（SkyWalking）看 span
4. **DB**：慢查询日志、锁
5. **缓存**：Redis slowlog、大 key
6. **中间件**：MQ 积压、TCP 连接
7. **基础**：CPU/内存/IO/网络

工具：tracing + metrics + logs 三件套，还有 jstack、arthas、perf。

# 系统设计面试案例

本章收录 5 个高频系统设计题，均按"需求 → 容量估算 → 核心设计 → 关键优化 → 面试讨论点"结构展开。

## 通用答题框架

1. **澄清需求**（5 分钟）：功能需求、非功能需求（QPS、数据量、延迟、可用性）
2. **容量估算**（5 分钟）：QPS、存储、带宽
3. **High-Level Design**（10 分钟）：架构图、主要组件
4. **Deep Dive**（15 分钟）：关键模块细节、选型理由
5. **Scale / Trade-off**（10 分钟）：瓶颈、优化、取舍

# 案例一：短链系统

## 1. 需求
- 功能：长链 → 短链、点击跳转、统计点击
- 非功能：QPS 读 10k / 写 1k，延迟 < 50ms，高可用（99.99%）

## 2. 容量估算
- 日写入：1k QPS × 86400 = 8600 万/天
- 5 年：1600 亿
- 短码 6-7 位 62 进制可覆盖（62^7 ≈ 3.5 万亿）
- 读写比 10:1

## 3. 核心设计

### 短码生成

**方案 A：Hash + 冲突处理**
- MD5(longUrl) 取 6 位 → 冲突 rehash
- **问题**：冲突概率高

**方案 B：发号器 + 62 进制（推荐）**
- 分布式 ID（Leaf / 雪花）→ 62 进制字符串
- 无冲突、可预测
- 缺点：可被猜测

**方案 C：预生成**
- 离线生成 1000 万随机码
- Redis Queue pop
- 用完再补
- 避免热点 DB

### 存储
```sql
CREATE TABLE url_map (
    short_code VARCHAR(10) PRIMARY KEY,
    long_url VARCHAR(2048),
    created_at TIMESTAMP,
    expire_at TIMESTAMP,
    creator_id BIGINT,
    INDEX idx_creator (creator_id, created_at)
);
```
- 按 short_code hash 分 16/32 库 × 16 表
- 热数据 Redis 缓存（TTL 1-7 天）

### 跳转流程
```
GET /abc → Redis 命中？
         ↓ 是 → 301/302 跳转 + 异步记点击
         ↓ 否 → DB 查询 → 缓存 → 跳转
```

**301 vs 302**：
- 301 浏览器缓存，后续不发请求（统计不准但快）
- 302 每次发请求（统计准但慢）
- 常用 302 + CDN 缓存短时

### 点击统计
- 异步：Kafka → Flink 聚合 → 入 ClickHouse
- 实时面板 + 离线报表

## 4. 关键优化
- **布隆过滤器**：过滤不存在短码，防穿透
- **CDN**：热门短链跳转缓存在 CDN
- **恶意 URL 检测**：对接安全服务
- **限流**：防爬虫刷写

## 5. 面试讨论
- 为什么不用 UUID：太长，不适合短码
- 为什么不用自增 ID：安全（可预测）、分库困难
- 短码会重复吗：发号器保证唯一
- 自定义短码（custom alias）：独立表 / 标志位

# 案例二：秒杀系统

## 1. 需求
- 功能：限时抢购、库存有限（1000 件）、用户量 100 万
- 非功能：防超卖、防刷、公平、高并发（峰值 QPS 10 万）

## 2. 容量估算
- 瞬时 QPS：10 万
- 正常下单 QPS：1k-1 万
- 单机能扛：1-2 万 QPS

## 3. 核心设计

### 整体架构（从前到后层层过滤）

```
用户 → CDN（静态页面）
    → 前端限流 + 按钮置灰
    → LB + 网关（IP/UserId 限流）
    → 接入层（验签、业务限流）
    → 库存预扣（Redis）
    → 下单队列（MQ）
    → 下单消费（DB 扣减 + 生成订单）
    → 支付
```

### 关键点 1：静态化 + CDN
- 活动页纯 HTML / CDN
- 按钮倒计时前置，时间到才请求接口

### 关键点 2：多级限流
- **前端**：点击后按钮置灰
- **网关**：IP / UserId 限流（令牌桶）
- **接入层**：单机限流（Sentinel）
- **集群限流**：Redis + Lua

### 关键点 3：Redis 预减库存
```lua
-- deduct.lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
end
return 0
```
- **原子操作**，防超卖
- 库存为 0 立即返回失败，后续请求直接拒绝

### 关键点 4：MQ 削峰
- Redis 扣减成功后发 MQ 消息
- 消费者按 DB 承受能力异步下单
- 下单失败要**回滚 Redis 库存**

### 关键点 5：防刷
- 验证码（图形/滑块）
- 黑名单（高频失败 IP）
- 风控（设备指纹、行为分析）
- 一人一单（Redis SET NX + 订单表唯一索引）

### 关键点 6：防超卖
- **Redis 原子**：Lua 脚本扣减
- **DB 乐观锁**：`UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0`
- 双重保障

## 4. 数据一致性
- 最终一致：Redis 扣减 → MQ → DB
- 对账任务：定期校对 Redis 与 DB

## 5. 面试讨论
- 库存为什么放 Redis：DB 单表扛不住 10 万 QPS
- MQ 消费失败：死信队列 + 人工处理 + Redis 回滚
- 热 key 问题：本地缓存 + 客户端分散
- 超卖极端场景：分布式锁 + 审计对账

# 案例三：Feed 流（朋友圈 / 微博）

## 1. 需求
- 发布动态、看朋友动态
- 1 亿用户，人均关注 200
- 日活 3000 万，日发 5000 万条
- 读写比 100:1（看多发少）

## 2. 容量估算
- 日写：5000 万 / 86400 ≈ 600 QPS
- 日读：读写比 100 → 峰值 10 万 QPS
- 存储：每条 1KB × 5 亿/月 = 500GB/月

## 3. 核心设计

### Feed 流三种模式

**推模式（Push，Fan-out on Write）**
- 发布时写到所有粉丝的收件箱
- 读快（直接读自己收件箱）
- 写放大：明星发帖写 1 亿次
- 适合：粉丝少的普通用户

**拉模式（Pull，Fan-out on Read）**
- 发布时只写自己发件箱
- 读时聚合关注人的发件箱
- 写轻、读重
- 适合：粉丝多的大 V

**推拉混合（主流）**
- 普通用户推
- 大 V（粉丝 > 阈值）拉
- 读时合并：收件箱 + 关注大 V 的发件箱

### 存储

```sql
-- 发件箱（动态表）
CREATE TABLE posts (
    post_id BIGINT PRIMARY KEY,
    user_id BIGINT,
    content TEXT,
    created_at TIMESTAMP,
    INDEX idx_user_time (user_id, created_at)
);
-- 按 user_id 分片

-- 收件箱
CREATE TABLE inbox (
    user_id BIGINT,
    post_id BIGINT,
    author_id BIGINT,
    created_at TIMESTAMP,
    PRIMARY KEY (user_id, created_at, post_id)
);
-- 按 user_id 分片，只保留最近 3000 条
```

### 发布流程

```
POST /post
  ↓
写 posts 表
  ↓
异步：fan-out 服务
  ↓
查关注者列表
  ↓
if 粉丝 < 1 万: 推模式，写各粉丝 inbox
else: 拉模式（大 V），不写
```

### 读流程

```
GET /feed
  ↓
并行：
  - 读自己 inbox（推来的）
  - 读关注的大 V 发件箱（拉）
  ↓
归并排序（按时间）
  ↓
取 top 20
  ↓
富化（头像、图片、点赞数等）
```

## 4. 关键优化
- **缓存**：inbox 最新 100 条 Redis ZSet
- **大 V 限流**：发一条延时分发，不阻塞发布
- **读缓存**：Feed 结果缓存 30s
- **分页用游标**：不用 offset（翻到深页慢）
- **去重**：转发链路可能重复，按 post_id 去重

## 5. 面试讨论
- 推拉混合阈值：经验值 1-10 万粉丝
- 热点聚合：偶像发帖，所有粉丝同时刷 → 缓存穿透
- 一致性：发帖后几秒内粉丝才看到，可接受
- 数据倾斜：明星用户分片不均 → 独立集群

# 案例四：即时消息（IM）

## 1. 需求
- 1 对 1 聊天、群聊
- 离线消息、已读回执、消息推送
- 1 亿用户，日发消息 10 亿条

## 2. 容量估算
- 日消息 10 亿 → QPS 1 万+（峰值 5 万）
- 存储：10 亿 × 100B = 100GB/天
- 连接数：DAU 3000 万，同时在线 1000 万

## 3. 核心设计

### 架构

```
客户端 ←→ 长连接（WebSocket / 自研协议）
       ↓
   接入层（Gateway）：管理百万长连接
       ↓
   逻辑层（Logic）：鉴权、路由、推送
       ↓
   存储层：消息 DB + 关系 DB + 离线队列
       ↓
   推送层：APNs / FCM / 小米推送
```

### 长连接管理
- **Netty** 处理百万连接
- 用户 → 连接的映射存 Redis：`user_id: {gateway_ip, connection_id}`
- 心跳：30s，超时踢连接
- 消息路由：查 Redis 找目标网关，网关转发

### 消息协议
- 协议号（Login/Send/Ack/Heartbeat）
- 消息 ID：客户端生成 + 服务端生成（去重）
- Ack 机制：
  - Client → Server：ServerAck
  - Server → Client：ClientAck（用户回执）

### 消息存储
- **发件箱**：所有发送的消息
- **收件箱**：每个用户收到的消息（分片存）
- **会话**：user1 + user2 → 消息列表（单聊）
- 冷热分离：近 90 天热，更老归档到 OSS

### 群聊
- **读扩散**：每条消息只存一份，群成员各自拉
- **写扩散**：每个成员都存一份
- 超大群（1 万人）用读扩散，普通小群用写扩散

### 离线消息
- 用户离线：消息存离线队列（Redis List / Kafka）
- 上线：拉取所有离线消息
- 离线超长：超时丢弃最旧

### 已读回执
- 群读回执写放大（N 人的群要更新 N 次）
- 优化：只记自己 read_seq（已读到哪条）
- 显示时计算：`message.seq <= my_read_seq` 的都已读

## 4. 关键优化
- **多端同步**：手机、PC、Pad 都登录 → 每端独立 read_seq
- **消息可靠性**：客户端 ACK + 服务端重试
- **加密**：E2E 加密（Signal 协议）
- **限流**：单用户发消息上限（防刷）
- **敏感词**：DFA 过滤 + AI 检测

## 5. 面试讨论
- WebSocket vs 长轮询：长连一定更高效
- 如何实现百万连接：Linux epoll + Netty，参数调优（fd 上限、内核参数）
- 消息顺序：单聊用 seq，群聊用 server timestamp
- 全局已读到哪：存 min(all_devices_read_seq)

# 案例五：网盘

## 1. 需求
- 文件上传/下载/共享
- 秒传、断点续传
- 1 亿用户，每人 1TB 配额
- 非功能：海量存储、可靠性 9 个 9

## 2. 容量估算
- 单文件 10MB-1GB
- 日上传 PB 级
- CDN 流量 Tbps 级

## 3. 核心设计

### 架构

```
Client
  ↓
网关（鉴权、配额）
  ↓
元数据服务（MySQL + Redis）
  ↓
文件传输服务
  ├── 上传：分片上传 → 合并
  └── 下载：重定向到最近 CDN 节点
  ↓
对象存储（OSS / S3 / Ceph）
```

### 秒传
- 客户端计算文件 MD5
- 上传前先查：`SELECT * FROM files WHERE md5 = ?`
- 存在 → 只建立元数据引用，不实际上传（秒传）
- 不存在 → 正常上传

**问题**：MD5 碰撞、文件隐私
- 解决：MD5 + SHA256 双 hash
- 用户只能看到自己的元数据，物理存储共享（去重）

### 分片上传
```
1. Client: 初始化上传 → 返回 upload_id
2. 文件切分 N 片（如 4MB/片）
3. 并发上传各片
4. 每片独立 MD5 校验
5. 所有片完成 → 合并
```

### 断点续传
- Client 上传中断
- 重启时查询：`GET /uploads/{upload_id}/parts` 返回已上传的分片
- 只上传缺失的

### 存储去重
- 同一内容的文件只存一份（物理）
- 每个用户有自己的"链接"（逻辑文件）
- 删除时减引用计数，0 才真删

### 冷热分层
- 近 30 天：SSD
- 30-90 天：HDD
- 90+ 天：Archive（归档存储，取回需分钟级）

### CDN 加速
- 热门文件预热到 CDN
- 下载重定向到最近节点
- 带宽大头（90% 成本）

## 4. 关键优化
- **并发上传**：多线程分片
- **压缩**：文本/文档上传前压缩
- **病毒扫描**：上传后异步扫描
- **分享链接**：临时 URL + token，过期失效
- **权限**：只读 / 可编辑 / 密码访问
- **版本**：保留历史版本（付费用户）

## 5. 面试讨论
- 大文件分多少片：4MB-8MB，权衡并发和合并开销
- 合并怎么做：对象存储通常支持 multipart upload，自动合并
- 秒传的法律风险：平台不查看内容，hash 匹配即可
- 配额管理：用户总大小不等于物理存储（去重后）
- 文件加密：用户端加密 → 服务端只存密文，零信任

# 通用原则与套路

## 1. 常用组件选择
| 场景 | 组件 |
|------|------|
| 高并发读 | Redis + CDN |
| 海量存储 | 分库分表 / NoSQL |
| 海量写 | MQ 削峰 / 批量 |
| 搜索 | Elasticsearch |
| 计数器 | Redis INCR / 批量刷 DB |
| 限流 | 令牌桶 / Redis |
| 幂等 | 唯一索引 / Redis SET NX |
| 分布式锁 | Redis + Redlock / Zookeeper |
| 分布式 ID | 雪花 / 号段 |
| 异步任务 | Kafka / RabbitMQ |
| 延迟队列 | RocketMQ 延迟 / Redis ZSet |

## 2. 高可用三板斧
- **冗余**：多副本、多活
- **隔离**：限流熔断降级
- **自愈**：健康检查 + 自动切换

## 3. 高性能三板斧
- **缓存**：多级缓存
- **异步**：非核心路径异步化
- **并行**：独立任务并发

## 4. 高并发三板斧
- **分**：分库分表、分片
- **控**：限流、排队
- **准**：预计算、预热

## 5. Trade-off 常见取舍
- 一致性 vs 可用性（CAP）
- 强一致 vs 最终一致
- 空间 vs 时间
- 读放大 vs 写放大
- 同步 vs 异步
- 精度 vs 性能

## 面试加分项

1. **先澄清再设计**：主动问需求，别急着画图
2. **给数字**：QPS、存储、带宽都量化
3. **画图**：架构图是沟通利器
4. **讲 Trade-off**：任何设计都有代价，主动说
5. **讲演进**：v1 简单版 → v2 扩容版 → v3 高可用版
6. **举实例**：结合自己做过的项目
7. **识别瓶颈**：主动指出可能的瓶颈和解法
8. **不懂就问**：不知道就承认，面试官会解释
